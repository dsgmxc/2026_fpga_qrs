### 与推荐结构的差异

与指南 3.3.5.4 的推荐结构相比,本项目**新增 4 个目录**,其余目录与推荐结构一致:

| 新增目录 | 理由 |
|---|---|
| `llm-log/` | **从 `report/` 中拆出**。指南推荐结构把「设计报告 + 大模型协作记录」同放 `report/`,本项目拆开的原因:`report/` 留给**报告正文与参考文献**,而 `llm-log/` 是**逐条交互的流水档案**(单条 5~20 KB、条目持续增长),两者体量、更新频率、读者都不同 —— 混放会让报告正文被流水淹没。(指南第 188 行明文允许采用其他组织方式,但**须在 `README.md` 中给出目录对照说明**,即本表) |
| `board/measurements/` | `board/` 原已收录位流与运行脚本;本次把**逐次上板实测存档**单列子目录。理由:这些存档是 **M13「板上跑通并提供实测输出」与 M04「实测输出与参考结果的比对数据」的直接证据**,每份都自带位流 md5、预期 vs 实测对照与原始终端输出,与位流是**同一次上板**的产物,**跟着位流走比跟着报告走更能保证一致性** |
| `docs/` | 集中存放**器件与硬件的接口规格文档** —— 芯片命令与时序常量(如 DAC1220 的命令字、帧格式、`tXIN` 时序窗口)、开发板扩展口引脚表、量程与传递关系标定记录等。这些是设计报告「软硬件划分依据与接口设计」一节的**原始依据**,体量与更新频率都独立于报告正文,与 `report/` 混放会使报告正文被规格表淹没,也不便于脚本引用。<br>另收录 **`dev_workflow.md`(开发流程手册)** —— 串口连接、直连网线配置、`scp` 传输、板上运行命令与实测踩坑记录,即**从零复现本项目所需的操作步骤**(对应必做点 M5 / 加分项 B5) |
| `src/constrs/` | 引脚约束**单独成目录**而非并入 `src/rtl/`。理由:约束与 RTL 的**修改时机和验证方式都不同**(改端口 ⇒ 两个都要动;改球号 ⇒ 只动约束),且本工程实际存在**两个 `.xdc` 但只有一个生效**的陷阱,**混放会让人以为它们是平级的** |
| `src/c_ui/` | PS 侧界面**用 C 写**(LVGL),与 `src/python/` 的 Python 编排代码是**两个进程**、两套构建方式(C 侧在板上 `make`)。放进 `src/python/` 会造成"Python 目录里躺着 C 工程"的误导 |

> ⚠️ `docs/dev_workflow.md` 中的**串口参数与启动跳帽**引自《领航者ZYNQ之PYNQ开发指南_V3.2》p22,属**外部资料转述**;
> 其余条目(网络配置、`sudo -E` 用法、踩坑记录)均来自本项目**板上实测**,原始证据见 `board/measurements/`。

### ⚠️ `sim/logs/` 当前为空 —— 这是**有意**的

`sim/` 收录的是**仿真平台本身**(`tb_spi_master.v` / `tb_dac_1220.v` / `tb_adc_9833.v` / `tb_lcd_rgb_colorbar.v`)
与**整理后的验证报告**(`spi_master_verification.md` / `dac_1220_verification.md` / `adc_9833_verification.md`)。
**仿真器输出的原始 `.log` 没有入库** —— 验证报告里已经逐项引用了它们的关键行(含变异测试的
FAIL 行),原始文本属于"跑一次就能再出来"的中间产物,不入库以免把证据淹在噪声里。

⇒ `sim/logs/` 目录**保留占位为空**。若要连同原始日志一起提交,把它们从工作区拷进来即可,
`.gitignore` **不会**拦截(`*.log` 未做全局忽略,原因见 `.gitignore` 内的说明)。

### 关于文档间的交叉引用(重要)

`docs/` 下的规格文档与 `llm-log/` 下的记录之间**大量互相引用**(引用各次上板存档、决策条目、
寄存器映射表)。为免读者点开是死链,这里说明本仓库对引用的处理规则:

| 引用指向 | 处理 |
|---|---|
| 上板实测存档 | ✅ 可用,已统一改写为 `board/measurements/…` |
| 大模型交互记录 | ✅ 可用,已统一改写为 `llm-log/…` |
| `report/source_design_checklist.md`(设计清单;**含寄存器映射表 §3**) | ⚠️ **未随本仓库发布**,保留在工作区 |
| `docs/project_state.md`(项目状态活文档) | ⚠️ **未随本仓库发布**,保留在工作区 |

> 上表后两项**不是遗漏** —— 它们是本项目**内部的过程文档**(状态流水、逐条排障记录、内部
> 编号体系),体量大且更新频繁,与交付物混放会让报告正文被流水淹没。正文中凡引用到它们的
> 地方,均已连同**具体条目号**(如「§六 决策 D22」「§九 Q05」)一并写出,读者据条目号即可
> 定位到该结论的归属,不依赖文件本身。
>
> ⚠️ 另需注意:`llm-log/` 与 `board/measurements/` 收录的是**历史存档**,其正文中出现的
> `report/measurements/`、`report/llm-log/` 等路径是**当时**的位置。存档按原样保留、不做
> 改写(改写存档等于篡改记录),**当前**位置以上表为准。

## `build/` 收录的 4 份综合与实现报告

对应必做点 **M3「综合与实现报告:资源占用、时钟频率、关键性能指标」**。取自 Vivado 工程
`qrs.runs/impl_1/`(顶层 `system_wrapper`),四份各回答 M3 的一项:

| 报告 | 回答 M3 的哪一项 |
|---|---|
| `system_wrapper_utilization_placed.rpt` | **资源占用** —— LUT / FF / BRAM / DSP 实际用量与占比 |
| `system_wrapper_timing_summary_routed.rpt` | **时钟频率** —— WNS / TNS / 失败端点数(布线后最终结果) |
| `system_wrapper_clock_utilization_routed.rpt` | 各时钟域扇出与资源分布(时钟方案佐证) |
| `system_wrapper_drc_routed.rpt` | 设计规则检查 —— 「DRC 0 error」的出处 |

⚠️ 这 4 份对应的是**当前入库位流**(`board/qrs.bit`)那一版实现,**两者须同批更新**。
⚠️ 工程目录里另有 7 份 `.rpt`(`power` / `bus_skew` / `control_sets` / `route_status` 等),
与 M3 三项无关,未入库。

### `build/bd_add_dac_dds.tcl` —— Block Design 侧改动脚本

对应必做点 **M5「可复现的构建脚本」**。RTL 侧 `cv_sys.v` 新增 6 个端口、AXI4-Lite 地址宽度
由 7 位扩到 8 位后,**BD 不会自动跟上** —— `cv_sys_0` 是 `module_ref`(HDL 模块引用),
BD 把旧的端口清单与 `ADDR_WIDTH=7` 缓存住了,不刷新就看不到新端口。

脚本做 5 件事:移除 `io.xdc`(`IS_ENABLED=0`,内容已并入 `led.xdc`)→ 刷新 `cv_sys_0` 的
module reference → 把 6 个新端口引出成顶层端口(名字与 `led.xdc` 一致)→ 接 pin → 校验。
**在 Vivado Tcl Console 里 `source` 执行**,脚本正文写清了每步的实测依据。

> ⚠️ 本脚本**不是**「一键从零重建工程」的完整构建脚本,只覆盖 BD 侧那一处改动;
> 从零复现的完整步骤见 `docs/dev_workflow.md`。

## `llm-log/` 大模型协作记录

对应必做点 **M11「大模型协作记录(提示词、模型回答、自我纠错轨迹)」** 与加分项
**B2「智能体工作流设计」**。`INDEX.md` 为索引,`LLM-0NN.md` 为逐条记录,
`_TEMPLATE.md` 是撰写模板(不计入条目数)。

记录纪律:每条「来源」均回指**具体的事件、文件或上板次数**,不写泛化结论;
**失败与推翻的条目与成功条目同等保留** —— 该必做点要的正是那份自我纠错轨迹。
