## 0. 这次改了什么(一句话)

**显示架构从「PL 生成整屏」改为「PS 出画面 + PL 只负责扫描输出」。**

| 项 | 原方案(D22,2026-09-25) | **现方案(2026-10-02)** |
|---|---|---|
| 画面来源 | PL 实时算:每像素比较 `y == curve[x]` | PS 渲染进 DDR 帧缓存,PL 读出 |
| 帧缓存 | **无** | **双帧,RGB565,DDR** |
| 曲线缓存 | 唯一数据源 | **降级为 PL 硬件画线加速器** |
| 能显示什么 | 一条 C-V 曲线 | **任意画面**(页面/控件/中文/图形) |

**为什么改**:D22 的前提是「本项目要显示的就是一条 C-V 曲线」。该前提**被产品的实际界面推翻** ——
前序系统的 `ui_demo.c` 有 **5367 行**(6 个页面、LVGL 控件、中文字库、双指缩放、二维码页),
曲线缓存**在范畴上**承载不了(它只会画 `y = f(x)`)。

⚠️ **D22 的推理本身没有错**:"1024×600 RGB888 帧缓存 = 14.75 Mb > XC7Z020 全部 BRAM 4.9 Mb" 是事实。
错的是**从 BRAM 装不下推出"所以不要帧缓存"** —— **DDR 存在**。前序系统在只有 8 MB HyperRAM 的
STM32 上都做了双帧。**当时选曲线缓存的真实理由是回避 DDR/VDMA 复杂度,不是不能做。**

#### 「点按键左边才触发」的排查结论(2026-10-03 第 36 次)

用户报告「画面整体稍微向右平移,但按键位置是对的,点按键左边才触发跳转」。
此症状由**两项合成**,而**两者的临床表现完全相同**,必须靠绝对参考才能分开:

```
δ_total = δ_display(扫描输出把画面整体右移) + δ_touch(触摸把坐标整体报大)
```

| 项 | 结论 | 依据 |
|---|---|---|
| `δ_display` | **恒为 0 —— 结构上不可能不为 0** | `lcd_timing.v` 输出级 `assign lcd_hs = 1'b1;`(HSYNC 恒高)+ DE 模式 ⇒ 屏**没有行同步脉冲可数**,唯一的列参考是 **DE 的上升沿**;源极驱动从 DE 拉高那刻起往移位寄存器灌像素 ⇒ **x=0 必然落在第 0 列**。这不是"测了没测到",是**没有物理通路** |
| `δ_touch` | **\|δ\| ≤ 11 px** | 见下 |
| 全链路缩放 | **零** | `gt911_ctrl.v` **不下载配置表**(只轮询 `0x814E`/`0x814F`),坐标取 `{rbuf[3][3:0], rbuf[2]}` 原样 12 位;`pynq_touch.c` / `pynq_indev.c` 零变换;`lv_indev.c:332` 只在 `rotated != 0` 时变换,当前 `rotated = 0` |

**判据(不依赖手指精度)**:首页两张大卡各 **453×156**、中间**只有 22 px 缝隙**
(左卡 x∈[48,501]、右卡 x∈[523,976])。按缝正中 x≈512:

| 现象 | 结论 |
|---|---|
| 两张卡都不进按下态 | **\|δ\| ≤ 11 px** ← **实测结果** |
| 右卡进按下态 | δ > +11 px(触摸报得偏右) |
| 左卡进按下态 | δ < −11 px(触摸报得偏左) |

⇒ **触摸不需要做任何标定修正。** 用户定性:「之前那个应该是个例外,先不管了」。

> 🔴 **为什么不用"点已知竖条中心再比坐标"那种方法** —— 这是本轮走过的弯路,记下来避免重犯:
> 5 根已知位置的竖条,让用户逐条点中心,反推 δ = 红 **+8.5** / 绿 +15.5 / 白 **+7.5** / 黄 +3.5 / 蓝 **+0.5**。
> **单调递减,看着像约 1.4% 的欠标定** —— 差点写进结论。
> **但同一根蓝条,上一轮量到 +10.5,这一轮 +0.5** ⇒ **手指瞄准的重复性就是 ±10 px**,
> 与要测的效应**同量级** ⇒ **这套量具没有分辨力,数字不能当结论用。**
> (绿色那条 y=285,其余四条 294~304 —— 它本身就是瞄歪的,连进拟合都不该。)
> 📌 **教训:给人做"测一下"的测试之前,先算清它能分辨多小的量。分辨力不够就换量具,不要解读数字。**
> 📄 `report/llm-log/LLM-037.md`

### 上电那一下的画面漂移(🟡 领先假设,未证实)

- **现象**:同一套显示通路,有时上电后画面整体偏移,有时正常;用户称「之前那个应该是个例外」。
- **领先假设**:`main.py` 的顺序是 `Overlay()` 加载位流 → `apply_fclk0()`;
  此时 **PL 已经在驱动 `lcd_clk` / DE**,把 FCLK0 从 27.78 跳到 50.000 等于给屏的时序参考抽一下,
  而 **HSYNC 恒高 ⇒ 屏没有第二根参考线可以重新锁相**。
- **反证(未消除)**:早先 `fbhold.py` 那次也在同序下调了 `apply_fclk0()`,当时目视**无漂** ⇒
  要么是随机滑移(滑多少取决于撞在帧里哪个位置),要么真因不是它。**两种都未排除。**
- **正解所需、但未做(属 RTL,归用户)**:`cv_sys.v:448-449`

  ```verilog
  assign lcd_bl  = 1'b1;
  assign lcd_rst = 1'b1;
  ```

  **背光与复位恒 1 硬连,没有寄存器** ⇒ 软件**没有任何办法**在改像素时钟前把屏按住。
  建议加寄存器位,让 `main.py` 能走「加载位流 → 按住屏 → `apply_fclk0` → 放开屏」。

### 上电自启动(2026-10-03 落地)

部署件:`board/qrs-ui.service`(装到板 `/etc/systemd/system/`,已 `enable`)。
三条约束写进了单元注释,**改之前必须先读**:

1. **`Restart=no` 是故意的** —— 自动重启 = 第二次加载位流 = 踩过的挂死路径(`lcd_fb_reader` 是活跃 AXI 主机)。
2. **解释器必须写全路径** `/usr/local/share/pynq-venv/bin/python3` ——
   `/home/xilinx/pynq` 只是**指向 venv 的软链**,`/usr/bin/python3` 能 import pynq
   **纯粹因为 SSH 的 cwd 恰好是 `/home/xilinx`**(`sys.path[0]` 撞上了),而 systemd 的 cwd 是 `/`。
3. **`XILINX_XRT` / `VIRTUAL_ENV` / `PATH` 必须显式给** —— systemd **不读** `/etc/profile.d/`
   (实测 `bash -lc` 也不设这三个);少 `XILINX_XRT` 会报 `RuntimeError: No Devices Found`。

✅ **2026-10-03 端到端验证通过**(用户断电重启):`Main PID 546 main.py` + 子进程 `630 c_ui`,

## 2. 架构与数据通路

```
┌───────────────── PS(Linux / PYNQ)─────────────────┐
│  LVGL 渲染 ──► 后台帧缓存(DDR)                     │
│  写 LCD_SWAP ────────────────┐                     │
│  读 TOUCH_* ◄──────────┐     │                     │
└────────────────────────┼─────┼─────────────────────┘
                         │     │ AXI-Lite
┌────────────────────────┼─────▼─────────────────────┐
│ PL                     │  cv_axi_lite_slave        │
│  gt911_ctrl ◄─ i2c_master ◄── GT911                  │
│  lcd_vblank_ctrl ──► 前台索引                        │
│                        │                             │
│  lcd_fb_reader ──AXI3 read──► DDR(帧缓存)            │
│         │ 行数据                                     │
│         ▼                                            │
│  ping-pong 行缓冲(2 × 2 KB)                         │
│         │                                            │
│  lcd_timing ──► lcd_hs/vs/de/clk + px_x/px_y         │
│         │                                            │
│  RGB565 → RGB888 展开 ──► lcd_rgb[23:0]              │
└──────────────────────────────────────────────────────┘
```

**关键点**

1. **PS 画帧缓存 = CPU 直接写 DDR**,不需要 DMA 写通道。
2. **PL 侧只有「读」这一个方向的 AXI 主机** ⇒ 是单向顺序读,AXI 主机逻辑最简形态。
3. **换址只发生在 VBlank** —— 由 `lcd_vblank_ctrl` 保证,PS 无法在扫描中途改前台。

## 3. 帧缓存布局与格式

### 3.1 格式:RGB565

| 理由 | 说明 |
|---|---|
| 与 LVGL 天然一致 | `lv_conf.h` 实测 `LV_COLOR_DEPTH = 16` ⇒ `lv_color_t` 就是 16 bit,**前序 UI 全部按 16 bit 写** |
| 带宽减半 | 100 MB/s(RGB565)vs 150 MB/s(RGB888) |
| 引脚不用动 | PL 输出端把 RGB565 **展开**成 24 bit 送 `lcd_rgb[23:0]`(每色 MSB 对齐,低位补 0) |

> ⚠️ **与清单 §2.3b 的「24-bit 并行 RGB」不冲突**:那是**物理接口位宽**,本行是**帧缓存存储格式**。二者独立。

### 3.2 尺寸与对齐

| 项 | 值 |
|---|---|
| 一帧 | 1024 × 600 × 2 = **1 228 800 B**(1.17 MiB) |
| 双帧 | **2 457 600 B**(2.34 MiB) |
| 对齐 | **64 KB**(`LCD_FRAME_BUFFER_ALIGNMENT = 0x10000`) |
| 单槽 | `((1228800 + 65535) & ~65535)` = **1 245 184 B** |

### 3.3 地址由 PS 分配,不写死

`LCD_FB_BASE0` / `LCD_FB_BASE1` 是**寄存器**,PS 分配好内存后写入物理地址。
⇒ PL 侧**不得**把帧缓存地址做成编译期常量。

> 📌 前序系统的地址是写死的(`0x70000000` / +64 KB),因为那是 STM32 的固定 HyperRAM 映射。
> **Zynq 上不该照搬** —— DDR 由 Linux 管理,写死地址会与内核分配冲突。

## 4. 时序与带宽预算

### 4.1 时序(与清单 §2.3b 一致,不变)

| 参数 | 值 |
|---|---|
| PCLK | **50 MHz**(屏窗口 40.8 ~ 67.2 MHz) |
| 行 | 20 + 140 + 1024 + 160 = **1344** DCLK ⇒ 行周期 **26.88 µs** |
| 帧 | 3 + 20 + 600 + 12 = **635** 行 ⇒ 帧周期 **17.069 ms** |
| 刷新率 | **58.59 Hz** |
| 消隐 | 行消隐 **320 DCLK = 6.4 µs**(hblank) |

> ⚠️ **PCLK = 50 MHz 是本设计取的值**,不是厂商值。厂商例程与前序系统用 **45 MHz**。
> 两者都在屏的允许窗口内,且 50 MHz 是本工程 `clk_wiz` 的现成输出、**彩条已在该频率上点亮过**。
> ⇒ 保持 50 MHz 不变,但**报告里必须写明这是我们的取值**。

### 4.2 带宽

| 项 | 值 |
|---|---|
| 像素率 | 50 Mpx/s |
| **DDR 读带宽(必需)** | 50 M × 2 B = **100 MB/s** |
| 一行 | 1024 × 2 = **2048 B** |
| 行突发 | 2048 B / 8 B = **256 拍**(64-bit) |

**AXI 侧余量核算**

| clk_axi | 64-bit 峰值 | 100 MB/s 占比 |
|---|---|---|
| **设计值 50 MHz / 真值 50.000 MHz**(IO PLL 1000 / DIV0 20) | 400 MB/s | **25%** |

> 🔴 **口径已更正(2026-10-03)**:本节曾按「实测 41.6667 MHz / 333 MB/s / 30%」计算 ——
> **该值已被推翻**。41.6667 是 PYNQ 按**假定的** IO PLL 1500 做的除法(`1500/6/6`),
> **从来不是任何仪表的读数**。2026-10-03 用时基独立实测(帧率法)得
> **IO PLL = 1000 MHz、`apply_fclk0()` 后 FCLK0 = 50.000 MHz**。
> 证据:`report/measurements/20261003_fclk0_real_measured.md`。
>
> ⚠️ **但有一个真实的前置条件**(不能省):板上 `BOOT.BIN` 把 FCLK0 留在 **27.78 MHz**,
> 且 `Overlay()` 会把 `FPGA0_CLK_CTRL` **整个复位**回该值 ⇒ **50 MHz 只在 `main.py`
> 调过 `apply_fclk0()` 之后成立**。在那之前 PL 跑在 27.78 MHz(低于面板窗口下限)。
> ⇒ 本节的 25% 是**稳态口径**;开机头几百拍不适用(表现为"上电闪一下")。
>
> 25% 占用**可接受**,但 DDR 还要承受 PS 侧 CPU 写帧缓存的流量 ⇒ 见 §9 风险。

### 4.3 行缓冲(ping-pong)

```
BRAM18 × 2(≈ 1 个 BRAM36):256 深 × 64 bit = 2048 B,两块轮流
```

**取数时序必须是"边扫边取",不能等消隐期**

| 做法 | 可用时间 | 256 拍 @50 MHz = **5.12 µs** |
|---|---|---|
| ❌ 只在行消隐取 | 6.4 µs | 余量 **25%** —— 一有 DDR 争用就欠载 |
| ✅ **在上一行有效扫描期内取下一行** | **20.48 µs** | 余量 **~4×** |

⇒ **`lcd_fb_reader` 必须在行 N 扫描期间发起行 N+1 的突发**,这是设计约束不是优化。

## 5. 寄存器映射(新增 7 个)

沿用 `cv_axi_lite_slave.v` 现有译码(`ADDR_WIDTH = 7`,`a[6:2]` 5 位字索引 ⇒ **32 个**)。

### 5.1 占用核对(实测)

| | 数量 | 地址 |
|---|---|---|
| 已定义 | **22** | `0x00` ~ `0x54` |
| **本次新增** | **7** | `0x58` ~ `0x70` |
| 余量留给 P4 安全链 | 3 | `0x74` / `0x78` / `0x7C` |
| **合计** | **32** | 满 |

### 5.2 新增寄存器

| 偏移 | 名称 | R/W | 位域 | 说明 |
|---|---|---|---|---|
| `0x58` | `LCD_FB_BASE0` | RW | `[31:0]` | 帧缓存 0 物理基址,由 **PS 分配后写入** |
| `0x5C` | `LCD_FB_BASE1` | RW | `[31:0]` | 帧缓存 1 物理基址 |
| `0x60` | `LCD_SWAP` | RW | 写 `[0]`目标索引;读 `[0]`当前前台 `[1]`pending | 写 ⇒ **下一 VBlank 生效** |
| `0x64` | `LCD_FB_STATUS` | RO | `[0]`front `[10:2]`vblank_cnt `[18:11]`swap_cnt `[19]`underrun `[20]`axi_err | 诊断 |
| `0x68` | `TOUCH_STATUS` | RO | `[2:0]`触点数 `[3]`pen_down `[4]`err `[15:8]`seq | **★ 一次触摸事件的提交点** —— PS **必须最先读它** |
| `0x6C` | `TOUCH_PT0` | RO | `[11:0]`x `[27:16]`y | 触点 0(**读的是快照,非直连上报字**) |
| `0x70` | `TOUCH_PT1` | RO | `[11:0]`x `[27:16]`y | 触点 1(同上) |

> 🔴 **★ `0x68` → `0x6C` → `0x70` 的读序是硬前提(2026-10-02 第 31 次定,不可调换)**
>
> PS 要读满 3 个寄存器才拼得出一次触摸事件,而 `gt911_ctrl` 是**自由运行**的 ——
> 来一帧就刷新上报字。三次读之间若跨过帧边界,就会读出
> "**状态说 1 个点、坐标却是下一帧的**"这种**撕裂**。
> 撕裂**不报错**,只让界面**偶尔跳一下** —— 是最难归因的那类 bug。
>
> **做法**:从机把"**读 `0x68`**"当**提交点**,那一拍把 `pt0`/`pt1` 一并锁进 hold
> (`cv_axi_lite_slave.v` 的 `tch_pt0_hold`/`tch_pt1_hold`);`0x6C`/`0x70` 读的是**快照**。
> **代价:PS 端读序固定 `0x68` 在先。** 先读坐标再读状态 → 拿到的是**上一拍的快照**,
> 对不上刚读到的 `seq`。
>
> ⚠️ 本条**只在仿真层面成立**(语法过 + 逻辑走查),**未上板**。
>
> 📌 附:`seq` 的语义**(2026-10-02 第 31 次定案)** —— 由 `gt911_ctrl` 持有,
> **每产生一个新坐标帧递增一次**,不是"读一次递增一次"
> (第 29 次曾记为"待决",现按**控制器持有**落地)。
> **证据**:`gt911_ctrl` 临时 TB 实测 —— 连读两次、第二次状态 `0x00` 时
> `seq` **不递增**;来新帧(`0x80`/`0x81`)才 `seq→2`、`→3`。
> PS 判新旧的方式:比较两次读到的 `seq` 是否不同。

**预留(P4 安全链,本次不实现)**

| 偏移 | 名称 | 用途 |
|---|---|---|
| `0x74` | `WATCHDOG_KICK` | PS 心跳 |
| `0x78` | `FAULT_LATCH` | 故障锁存 |
| `0x7C` | `SAFETY_STATE` | 安全状态 |

### 5.3 ⚠️ 两条约束

1. **`LCD_SWAP` 读回的是"已生效"值,不是"已请求"值** —— 请求与生效必须分开,
   否则 PS 会在换址尚未发生时就宣称切换完成。同一原则适用于将来的 `RELAY_REQUEST/APPLIED`。
2. **地址已满**。若后续还需要寄存器,**必须把 `C_S_AXI_ADDR_WIDTH` 从 7 改成 8**
   (64 个寄存器)。⚠️ 该改动会动到已跑通的 BD:`module_ref` 的 `.xci` 是**端口边界快照**,
   改参数后**必须 Refresh Module Reference**。**本次不动。**

### 5.4 触摸为什么只用 2 点

前序 `ui_demo.c` 的交互只有:单击、沿曲线拖动、**双指缩放**、双击。
⇒ **≤ 2 点足够**。GT911 支持 5 点,但寄存器位置不够,且 UI 用不上。

| **职责** | AXI **读**主机:从当前前台帧缓存取出一整行,写入 ping-pong 行缓冲 |
| **输入** | `clk`、`rst_n`、`fb_base[31:0]`(当前前台基址)、`frame_start`、`line_start`、`de_req`、`px_x` |
| **AXI3** | **只读**:`araddr[31:0]`、`arlen[3:0]`、`arsize`、`arburst`、`arvalid/arready`、`rdata[63:0]`、`rvalid/rready/rlast/rresp`。**无写通道** |
| **突发** | 每行 **16 次 × 16 拍**,64-bit ⇒ 128 B/次 × 16 = **2048 B/行**。**串行**(一次收满再发下次) |
| **输出** | `px_data[15:0]`(RGB565,寄存输出,与 `de_act` 同拍) |
| **行为** | 行 N 扫描期间发起行 N+1 的读(见 §4.3);`rready` 在 `S_DATA` 常开(顺序无重排,不需反压) |
| **异常** | `rresp != OKAY` 或行缓冲欠载 ⇒ 置粘滞 `axi_err` / `underrun`;**看门狗超时后回 `S_IDLE`,不得死等** |
| **验收** | ① 静态测试图(彩条/棋盘/渐变)上板图案正确;② `underrun` 长时间运行后仍为 0;③ ILA 抓一次行突发的 `arvalid/arready/rvalid` 握手 |

> 🔴 **协议必须是 AXI3,不是 AXI4**(2026-10-02 实测,不可推翻)
>
> Zynq-7000 的 **HP/GP 口就是 AXI3**。把 `M_AXI` 声明成 `PROTOCOL AXI4` 后 BD **直接拒绝连线**:
> ```
> ERROR: [BD 41-1285] The protocols of the interfaces '/cv_sys_0/M_AXI'(AXI4)
>        and '/processing_system7_0/S_AXI_HP0'(AXI3) are incompatible.
> ```
> 且 **AXI3 单次突发上限 16 拍**(AXI4 才放宽到 256)⇒ `MAX_BURST_LENGTH` 只能是 16、
> `ARLEN` 只有 4 位,"一行 256 拍"必须拆成 16 次突发。
>
> **备选方案(已否决)**:在 BD 里插一个 `axi_protocol_converter` 把 AXI4 转成 AXI3。
> 否决理由:HP 是**实时数据路径**,而它有**每行硬截止**(行消隐只有 6.14 µs,
> 取一行要在上一行扫描期内完成)。转换器会在这条路径上再引入**一级不确定延迟**,
> 且多一个不可控的 IP。**延迟可预测 > 少写几行代码。**
> 代价:状态机多一个 4 bit 突发计数 + 一个比较器,约十几 LUT。

> **为什么自写而不用 AXI VDMA**:PS 画帧缓存是 **CPU 直写 DDR** ⇒ VDMA 的**写通道用不上**,
> 而读通道要配上 `v_tc` 才能用。本设计需要与 `lcd_timing` **紧耦合**(行节拍、欠载处理),
> VDMA 的 FIFO 深度不可控。**且 AXI 突发读握手正是赛题「接口协议」考察点。**

### 6.6 `i2c_master.v` + `gt911_ctrl.v`

✅ **2026-10-02 第 31 次已写完并进了位流**(xsim 两 TB 全过,**未上板**)。

| 模块 | 接口要点 |
|---|---|
| `i2c_master.v` | **字节级 op 接口**(`go` / `op[2:0]` / `tx_byte` / `rx_byte` / `ack_rx` / `busy` / `done` / `err`),**不是**"读一个寄存器"的高层接口 —— GT911 的事务形状不规整(写 2 字节地址 → 重启 → 读 N 字节),把 op 序列交给上层拼才可复用。含**时钟拉伸等待 + 超时自退**、**9 脉冲总线恢复**。参数 `CLK_FREQ_HZ` / `SCL_FREQ_HZ` / `STRETCH_TIMEOUT` |
| `gt911_ctrl.v` | 复位序列(**INT 拉高锁器件地址 `0x14`**)/ 16 位寄存器寻址 / 轮询 `0x814E` / 读 2 触点 / **两级错误容忍**(连错 3 → 总线恢复,连错 5 → 重走复位序列 + 地址自愈)。`touch_int` 是 **inout** |

> 🔴 **`touch_int` 是双向的,不能当纯输出**:GT911 用"**复位释放瞬间 INT 的电平**"
> 锁存 I2C 器件地址(高 → `0x14`,低 → `0x5D`)⇒ **主机在复位期间必须驱动它、之后必须释放**。
> 三个三态口(`scl`/`sda`/`int`)在 `cv_sys.v` 里**必须保持 `inout` 原样引出** ——
> 拆成 `o`/`oe`/`i` 会变成 3 个外部端口,而物理上各只有 1 个引脚,`io.xdc` 无法对同一引脚写三条约束。IOBUF 由综合器在顶层推断。

⚠️ **`i2c_master` 放在 `clk_axi` 域**:位速率由 `CLK_FREQ_HZ` 分频而来,没有非它不可的频点;
且上报字直连 AXI 从机寄存器,**同域 ⇒ 不需要 CDC**。

> 🔴 **本节原写「`clk_axi` 实测 41.6667 MHz ⇒ 所有毫秒慢 20%」—— 该前提已作废(2026-10-03)。**
> `apply_fclk0()` 之后 `clk_axi` 真值就是 **50.000 MHz**,与 `CLK_FREQ_HZ` 的假定一致 ⇒
> **稳态下没有缩放误差,IIC 的毫秒是真毫秒。**
> 唯一不成立的是**开机头几百拍**(`BOOT.BIN` 留在 27.78 MHz,`Overlay()` 又把
> `FPGA0_CLK_CTRL` 复位回该值)——那时 IIC 会慢 `50/27.78 ≈ 1.8×`。
> GT911 的复位/配置序列发生在 `apply_fclk0()` **之后**,故不受影响。

`gt911_ctrl` **必须带上 §7 的语义**,否则长按闪烁会复现。

## 7. GT911 触摸语义(🔴 前序踩出来的,必须照搬)

| 规则 | 说明 |
|---|---|
| **`status.bit7 = 0` 只表示「没有新坐标帧」,不等于松手** | bit7 在两帧之间会暂时为 0。**此时必须保持上一按压状态** |
| 只有 `bit7 = 1` 且触点数 = 0 的新帧,才是明确松手 | |
| 活动触摸轮询 | **10 ms** |
| 兜底轮询 | **100 ms** |
| 最近活动触摸保持窗口 | **150 ms** |
| 连续 3 次总线错误 | 执行 **I2C 恢复** |
| 连续 5 次错误 | **复位触摸控制器** |

> ⚠️ **若把"无新数据"直接映射成 release,会重现按钮闪烁、拖动中断、双指缩放不稳定。**
> IIC 地址 `0x14` 或 `0x5D`(取决于复位时 INT 电平)。

### 8.3 🔴 不要用 LVGL 自带的 fbdev 后端

LVGL 的 Linux fbdev 后端**直接写 `/dev/fb0`**,**不做双缓冲、不等 VBlank**。
直接用它 ⇒ 前序辛苦修掉的**撕裂 + 长按闪烁会全部回来**。

⇒ **必须用 §8.2 的自定义 flush cb**,参照前序 `lv_port_disp.c` 的
「换址 + 只同步无效区域 + 超时兜底 + 错误计数」。**已照此实现。**

⚠️ 连带一条前序没写下来的坑:**`direct_mode = 1` + `full_refresh = 0` 时必须做「矩形同步」** ——
LVGL 只重画失效区域,其余像素指望缓冲里还是上一帧;可**换址之后新后台是更早的那一帧**
⇒ 不把本次失效矩形从新前台补到新后台,界面会一块块"退回两帧前"。
**这个 bug 只在局部刷新时显形,极难归因**(实现见 `pynq_disp.c` 的 `sync_invalid_areas()`)。

### 8.4 🔴 Cache 一致性(头号坑)

PS 写完帧缓存后,PL 通过 AXI 读 DDR —— **可能读到 cache 里的旧数据**。
**表现**:画面偶尔不更新 / 花屏,**极难查**。

**本设计的处置:让这条路径上的写不走 cache。**

| 谁 | 做什么 | 为什么 |
|---|---|---|
| **Python**(`drivers/lcd.py`) | 用 `pynq.allocate` 从 **CMA** 分配两块 64 KB 对齐缓冲,**只分配、不写像素** | C 侧拿不到物理连续内存;C 需要的是**物理地址** |
| **C**(`c_ui`) | 用 `/dev/mem` mmap 这两块**物理地址**,LVGL 的重绘直接落在这段映射上 | ARM 上 `/dev/mem` 的 mmap 走 `ioremap`,映射属性为 **Device(非缓存)** ⇒ PL 读 DDR 直接看到 PS 的写 |
| **PL** | 照常读 | — |

⇒ **D1 在这条路径上不成立** —— 但这是**设计依据,不是实测结论**:
「非缓存」取决于内核的 `ioremap` 行为,**本板未验**。
若上板发现缓存依然存在,处置依次是:`DMA_BUF_IOCTL_SYNC` → 换 `/dev/dma_heap/system`。

⚠️ 因此 **§9 的 D1 在首轮上板时仍是必测项**,只是"预期会过"而不是"没法过"。

**四条关键设计判断**(都是取舍,不是照抄):

1. 🔑 **帧缓存必须由 Python 分配。** C 侧拿不到物理连续内存(`pynq.allocate` 走 CMA 是最可靠的路径),

   将来接测量数据时,用 pipe/socket 替换前序的 UART7 协议层,**不污染 UI 代码**。
3. 🔑 **`ui_demo.c` 一行不改,靠 `-Iport` 路径别名树。** 让它编过有两条路 ——
   改它几行 include,或让 `port/BSP/LCD/lcd_panel_config.h` 顶上前序路径。
   **选后者** —— 改一行,"与前序工程逐字一致"这句话就再也说不出口,而那是报告里可辩护的资产。
   ⇒ `port/BSP/LCD/lcd_panel_config.h`(54 行)/ `port/BSP/TOUCH/lcd_touch.h`(118 行)/
   `port/BSP/LVGL/lv_port_disp.h`(55 行)/ `port/BSP/LVGL/lv_port_indev.h`(35 行)。
   📌 其中**只有 `lv_port_disp.h` 与前序有接口差异**(`Init` 收两个物理地址而非 LTDC 句柄),
   `lv_port_indev.h` 与前序**逐字相同**。
4. 🔴 **`err` 是粘滞位,不是实时故障信号。** `gt911_ctrl.v:588` 置位、**`:264` 只在复位/重配时清**
   ⇒ 语义是"**开机以来曾出错**"。若按实时故障处理,**一次上电噪声会让触摸永久失效**,
   且症状(按了没反应)会把排查引到外部上拉/底板上这些**无关方向**。
   ⇒ `pynq_touch.c` 只**报一次**然后照常读。

**`display_protocol` 的处置**(本轮不接通):`.c` 换成一个空实现,**9 个 `DisplayProtocol_Request*`
一律返回 `false`**。

> 🔴 **为什么不返回 `true`**:返回 `true` 会让状态栏谎称「指令发送完成」,
> `RequestSweep` 还会清 `g_sweep_inspection_ready` 并切页 —— 即**假装测量已启动**。
> 宁可显示失败也不假装成功。
>
> ⚠️ **预期现象**:点测量按钮时状态栏显示「UART7发送失败」。
> 这是**如实报告"指令没发出去"**,**不是触屏坏了** —— 触屏好不好看 `tools/touch_probe.py`。
> 页面之间的**导航**不走这一层(纯 LVGL),不受影响。

**FCLK0(决策 F1 结案)**:`Clocks.fclk0_mhz = 50` 固化进 `main.py`(具体做法见
`board.py apply_fclk0()`:设完**再覆盖 `DIV0 = round(1000/X)`**,因为 `Clocks` 假定 IO PLL = 1500)。

⚠️ **口径(2026-10-03 实测,已更正)**:`BOOT.BIN` 留 **27.78 MHz**,`Overlay()` 会把它复位回该值,
`F2` 因此规定**设定必须在 `Overlay()` 之后**;**`apply_fclk0()` 之后真值 = 50.000 MHz**。
⛔ **不得再写「41.6667 MHz(实测)」** —— 那是 PYNQ 按假定 IO PLL 做的除法,不是仪表读数。

| # | 风险 | 说明 | 处置 |
|---|---|---|---|
