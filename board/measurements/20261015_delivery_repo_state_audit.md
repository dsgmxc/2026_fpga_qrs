## 一、方法(以及为什么不能只看 `git status`)

`git status --short` 为空 **只能证明"已提交",不能证明"与源头同步"**。
真正的源头有三个,方向各不相同:

```
Vivado 工程   /home/hyp/Desktop/fpga_pro/qrs/qrs.srcs/…   ← RTL 的真源头
     ↓ (综合)
部署位流      qrs.runs/impl_1/system_wrapper.bit            ← 板上跑的那份
     ↓
交付仓库      ~/Desktop/qrs_fpga_2026/                      ← 发布物
```

⛔ **`rsync -rcn` 报"有差异"不指示方向**(本项目已踩过三次,
见 `llm-log/LLM-068.md` 纠错轨迹第 6 条)。
⇒ 本次**逐文件**核 **md5 + mtime + 内容 diff**,方向靠时间链定,不靠工具输出。

## 三、★ 真缺口:交付仓的 RTL **建不出**它自己发布的位流

**症状**:`src/rtl/adc_capture.v` 在交付仓与 Vivado 工程里**不是同一份**。

| | md5 | 时间 | 状态 |
|---|---|---|---|
| Vivado 工程 | `4c98f8035bafda15962af99a63ca8699` | 2026-10-14 **23:39** | 含「**记录起点恒取 A 的刻度**」修复 |
| 交付仓 | `cc5dccf4f2dac71d0d20aa03c7cacba8` | 提交 `1eeec9e` 2026-10-14 **22:35** | **修复之前**那一版 |
| 部署位流 | `c92c7ed5b7d695dee73d86abc1c6089c` | 2026-10-15 **18:21** | 由**工程那一份**建成 |

### 判据:时间链把"源码 → 位流"钉死

```
源码 mtime   10-14 23:39   ─┐
                            ├─⇒ 位流 mtime(10-15 18:21)晚于源码
位流 mtime   10-15 18:21   ─┘   ⇒ 【位流里一定含这一版源码】

交付仓提交   10-14 22:35   ⇒ 【交付的是修复之前那一版】⛔
```

**这条推理不用打开 Vivado、不用重跑综合**,只需要三个时间戳。
⚠️ **方向只能单向用**:位流比源码**晚**能证明"含";
位流比源码**早**证明不了"不含"(可能是改完没重建)。

### 修复内容(为什么这不是"无关紧要的一版")

被漏掉的改动把采集记录窗口的起点从「GO 之后**第一个命中的刻度**」
改成「**恒取 A 的刻度**」。原写法下 GO 撞在采样周期内的位置是**硬币**:
先撞上 A ⇒ 两路的第 0 个样本同属转换 X(配对正确);
先撞上 B ⇒ B₀ 在转换 X、A₀ 在转换 X+1,**错开一整个转换**,
⇒ 文件头「两路第 k 个样本来自同一个转换 k」的**相位原点不变式当场失效**。

文件自己记了实测指纹(DIV=4):两簇间距 **11.070°** vs 预测 **11.077°**(差 0.007°),
`|VH|/|VL|` **逐位不变**(整数样本平移不改 DFT 幅值)
⇒ **Re Z 只动 ~1.5%,而 Im Z / Cs / D 跳 30–70%** —— 即用户报告的**「读数比较跳跃」**。

### 处置

把**工程那一份**拷进交付仓(**不是反过来**),两边 md5 现已一致
(`4c98f803…`);并在 `skill/stale-artifact-silent-reuse/` 记为**第五种形态**。

> ⚠️ **诚实标注**:这次修复**没有任何 `llm-log` 记录**。
> 全库检索 `start_tick` / `rec_go` / `记录起点` / `11.070` **均 0 命中**;
> 它的设计依据**只写在 RTL 文件自己的头注释里**。
> ⇒ 本次**只同步 + 如实记载,不代写交互记录**(`CLAUDE.md` §6.2 红线)。

**为什么入库**:仓库 `board/` 里**已有**它们的 5 个同类
(`adc_probe.py` / `adc_timing.py` / `fb_dump.py` / `relay_hold.py` / `relay_rw.py`),
md5 逐一对齐(全一致);**只缺这 5 个** ⇒ 补齐才成套(M4 实测输出 / B5 复现性)。

### 🔴 `board_run.py` 的写死口令 —— **入库前已改掉(本次的一处真拦截)**

原文件把口令**以字面量写死在源码里**(用的是 **PYNQ 出厂默认口令**,此处不复述其值)。
虽然出厂默认本身是公开信息,但把它**提交进公开仓库**等于**发布一份可用凭据**,
而且**提交过一次就永久留在 git 历史里** —— 之后再改文件也删不掉。

**改法**(不改工具能力,只去掉内置口令):

```python
HOST = os.environ.get("QRS_BOARD_HOST", "192.168.2.99")   # 拓扑:有默认值
USER = os.environ.get("QRS_BOARD_USER", "xilinx")
PASS = os.environ.get("QRS_BOARD_PASS")                   # ⛔ 口令:无默认值
PORT = int(os.environ.get("QRS_BOARD_PORT", "22"))
```

`connect()` 开头加一道守卫:口令为空时**明确报错并提示怎么设**,而不是回落到任何默认值。

**顺带做的**:全仓扫一遍「**赋值型口令字面量**」
(即 `口令变量 = "…字面量…"` 这种形状,`--include` 限定 `*.py|*.c|*.h|*.sh|*.tcl`)
——**零命中**;本次新增的 5 个工具逐个单独扫,**全部干净**。
> 📌 本条**只记手法、不复述被扫出来的值** —— 见下面那条教训。

> 📌 **教训一**:**"这是个调试脚本"不是"它可以带凭据"的理由。**
> 判断标准是**它会不会被提交 / 被发布**,不是它重不重要。
>
> 📌 **教训二(本次自己又踩了一次)**:**"把口令写进修复说明文档"和"把口令写进源码"
> 是同一件事。** 我第一版这份核对记录里,为了说清"原来错在哪",
> 把那个口令**逐字抄进了正文**;commit message 里也抄了一遍 ——
> **那等于换个文件、换次提交,再泄漏一遍。**
> ⇒ 正确写法:**只描述形状,不复述值**(本段现在就是这么写的)。
> **"引用"不是"泄漏"的豁免理由。**
