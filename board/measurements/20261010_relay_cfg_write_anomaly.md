## 1. 结论摘要

### ✅ 最终结论(2026-10-10,见 §10)

**PS 侧写寄存器时用 `struct.pack_into` 会产生两笔 AXI 事务**(先写 `0x00000000`,再写载荷),
**而不是一笔**。于是:

* 笔①`0x00` 在 `relay_ctrl` 白名单里(`COSS_DISCHARGE`)⇒ **被受理**,`relay_reg ← 0x00`,arm busy 40 ms;
* 笔②真值 ⇒ 撞 `busy` ⇒ `ERR_BUSY(0x03)`;
* ⇒ **写什么合法值,硬件都停在 `0x00`。**

`settle = 0`(无互锁)时后写覆盖前写 ⇒ 一切正常 —— **这正是"为什么只有 `0x1C` 显形"**:
它是唯一带稳定时间互锁的命令寄存器。其它寄存器同样被多写一笔零,但后写胜出,看不出来。

**PL 无缺陷:** `relay_set_r` 一笔事务一拍脉冲,行为与源码一致。
修法是改 PS 侧那一行调用方式(`_DevMemRegs.write` 用切片赋值),不是改 RTL、不用挂 ILA。

### ❌ 以下是被推翻的旧结论(保留供追溯)

## 2. 四组对照实验(全部为实测)

| # | `0x24` settle | 写 `0x1C` | 合法? | 读回 `0x1C` | `0x04` STATUS | **源 RTL 预测** |
|---|---|---|---|---|---|---|
| 1 | 0 ms | `0x3C` | ✓ | **`0x3C`** ✓ | err=0x00 busy=0 | relay=0x3C, err=0x00 ✓ 一致 |
| 2 | 0 ms | `0x80` | ✗ | **`0x00`** ✗ | err=0x01 busy=0 | relay **不变=0x3C**, err=0x01 |
| 3 | 2000 ms | `0x51` | ✓ | **`0x00`** ✗ | err=0x03 busy=1 | relay=0x51, err=**0x00** |
| 4 | 40 ms | `0x1E` / `0x61` | ✓ | **`0x00`** ✗ | err=0x03 busy=1 | relay=0x1E/0x61, err=0x00 |

对照组 1 与 2 **只差写入值**,`settle` 均为 0(busy 不可能置起)。

### 为什么只有「两次脉冲」能同时解释对照组 2

- `0x1C` 从 `0x3C` 掉到 `0x00` ⇒ 必有一次**被受理**的 `relay_reg ← 0x00`
  (`relay_reg` 只在该受理分支被写;复位分支写的是 `RELAY_RESET=8'h10`,不是 0)。
- 同一次写里 `err = 0x01`(ERR_RELAY)⇒ 必有一个**非法值**被送进 FSM(`0x80`)。
- 一个脉冲不可能同时是 `0x00` 和 `0x80`。⇒ **至少两个脉冲。**

对照组 1 亦是佐证:`settle=0` 时 busy 不置起,两次脉冲**都被受理**,
后一次(真值)覆盖前一次 ⇒ 读回恰好等于写入值,因此看起来「正常」。

## 4. 为什么本记录不给出根因

已核对到源 RTL 的每一处相关逻辑(握手寄存器、`do_write`、
`relay_set_r` 脉冲生成、FSM 受理/拒绝分支、白名单、读回路径),
**在源 RTL 中每次写只可能产生一拍 `relay_set_r`**:

```
wire do_write = aw_hs & w_hs & ~bvalid_r;      // bvalid_r 在 do_write 当拍下一拍即置 1
                                               // ⇒ do_write 只可能高 1 拍
relay_set_r <= 1'b0;                           // 默认清
if (do_write && (awaddr_r[7:2] == IDX_RELAY_CFG)) relay_set_r <= 1'b1;
```

⇒ 源 RTL 无法产生「两拍脉冲」。**需要仿真或网表级核对才能继续**,
不宜凭推理下结论。

## 5. ⚠️ 安全相关(比上面更该先处理)

`0x00` = `COSS_DISCHARGE`,与 `0x10` = `ALL_OFF` 是**两个不同的物理组合**。
既然第一次脉冲总携带 `0x00` 且总被受理,则:

> **一个「被拒收」的写(例如非法值 `0x80`)仍会把继电器组合实际拨到 `0x00`。**
> —— 源 RTL 的设计备忘明确承诺相反的行为(「拒收:relay_reg 一位都不动」)。

实测证据见对照组 2(`relay_reg` 由 `0x3C` 变为 `0x00`)。

⚠️ **继电器的物理触点从未用万用表量过** —— 以上全部是**寄存器侧**的读数。
「`relay_reg` 变了」与「继电器真的动了」是两件事,后者需要实测触点确认。

## 7.3 ★ 决定性证据:`done` 当独立计数器 —— **写入值相同也照样是两次脉冲**

`relay_ctrl` 里 `done_r` 只在**一次被受理的继电器写**之后、稳定计时走完时置 1。
而 `0x00`(COSS_DISCHARGE)在**白名单里**,单独一次写必然被受理 ⇒ 必然 `err=0x00`。

**把 `settle` 设成 1 ms,然后写 `0x1C = 0x00`(注意:写入值就是 `0x00` 本身):**

```
写前  0x04=0x00000002  0x1C=0x00   settle=1ms
写 0x1C <- 0x00
写后  0x04=0x00000306  0x1C=0x00   ⇒  err=0x03 (BUSY)
```

| 模型 | 预测 |
|---|---|
| **一次脉冲** | `0x00` 合法 ⇒ 受理 ⇒ `err=0x00`、`busy` 走 1 ms 后 `done=1` |
| **两次脉冲** | 第一次受理(arm busy)⇒ 第二次撞 busy ⇒ **`err=0x03`** |
| **实测** | **`err=0x03`** ⇒ **两次脉冲** |

**这一条把"读回 0x00 是因为数据陈旧/被 0x00 覆盖"的解释全部排除** ——
写入值本身**就是 `0x00`**,两次脉冲携带的是**同一个值**,仍然撞出 BUSY。

## 7.4 结论(本次能确定的 / 不能确定的)

**✅ 已坐实:**

1. **一次 AXI 写 → `relay_ctrl` 收到 ≥2 个 `cfg_relay_set` 脉冲。**(7.3,数据无关,板上实测)
2. **PL 侧不具备这个能力。** `relay_set_r` 只有一个 FF,`~bvalid_r` 在锥内,
   一次 `do_write` 只可能高 1 拍。(7.1,已实现网表核对)
3. **⇒ 只能是 ≥2 次 AXI 写事务(≥2 组 AW+W 握手)到达 `cv_sys` 的 `S_AXI`。**
4. **第一次携带的 `WDATA = 0x00000000`** —— 由 ③ 反推:`relay_reg` 从 `0x3C` 掉到 `0x00`,
   而 `relay_reg` 只在**受理分支**被写;复位分支写的是 `0x10`。所以必有一次
   **被受理的、值为 `0x00`** 的写。
5. **异常绑定在 `0x1C` 这个地址上**:写 `0x18` 时 `0x1C` 纹丝不动(⑤)。
6. **故障在 `cv_sys` 之外** —— PS 写通路(Zynq `M_AXI_GP0` → BD 里的 `axi_smc` → `S_AXI`)。
   上一次"源/位流不一致"的怀疑,现在有了**正面证据**排除:网表就是源。

**❌ 仍不能确定(不下结论):**

- **是谁、为什么把一个写变成两个。** 候选:Zynq GP0 端口 / BD 里的 `axi_smc`
  (含 `s00_si_converter` 的 AXI4→AXI4-Lite 转换、`s00_mmu`)/ `/dev/mem` 通路。
  **寄存器回读已经问不出更多了** —— 要区分只能在片上抓 AXI 写通道。

**⚠️ 顺带发现的一处潜伏隐患(与本异常无直接因果,但该记):**
`cv_sys.v:66` 是 `C_S_AXI_ADDR_WIDTH = 8`(地址只有 8 位),
而 BD 里给 `cv_sys_0/S_AXI/reg0` 分的段是 **`0x43C00000`,range `4K`**。
RTL 只译码 `awaddr_r[7:2]`(高 6 位被丢掉),所以 `0x1C` 与 `0x11C`、`0x21C`……
**会落到同一个寄存器**。当前 PS 只写低 256 字节,踩不到;但地址宽度和段范围对不上,
将来扩寄存器时是个陷阱。

# 8. 【2026-10-10】软件绕法 —— **已验证可用,P4 不必等根因**

既然异常只在 **`settle != 0`** 时暴露(`settle = 0` 时两次脉冲都被受理,后一次(真值)覆盖前一次),
就可以把"等稳定时间"这件事**从硬件搬到 PS 侧自己等**:

```
写 0x1C = V 的正确时序
  1) 写 0x24 = 0x0000_0000        # settle ← 0
  2) 写 0x1C = V                  # 两次脉冲都被受理 ⇒ relay_reg = V,err = 0
  3) 写 0x24 = 0x0028_05DC        # settle 恢复 40 ms
  4) PS 自己 time.sleep(0.040)    # 等继电器稳定(硬件不再代劳)
```

**板上实测(同一目标值、两种 settle 直接对照):**

| settle | 写 `0x1C` | 读回 `0x1C` | STATUS |
|---|---|---|---|
| 40 ms(默认) | `0x51` | **`0x00`** ✗ | err=0x03 |
| **0 ms** | `0x3C` | **`0x3C`** ✓ | err=0x00 |
| 40 ms(默认) | `0x61` | **`0x00`** ✗ | err=0x03 |
| **0 ms** | `0x61` | **`0x61`** ✓ | err=0x00 |

**代价 / 前提(要写进代码注释,不然将来踩):**

1. **PS 必须自己 sleep 够稳定时间** —— 硬件不再置 `busy`、不再置 `done`,超时/错误保护都没了。
2. 中间会有一拍(**20 ns @50 MHz**)把继电器组合瞬时拨到 `0x00`(COSS_DISCHARGE)。
   机械继电器吸合是 ms 级,**20 ns 不足以让它动**;但这是"靠继电器的时间常数兜着",不是设计出来的。
3. 这是**绕法,不是修法**。根因仍在(§7),`relay_ctrl` 的 `busy/done/err` 三个保护全部失效。

⚠️ 本节只是"能往下走",不等于 §7 的结论可以不管 —— 报告里必须两者都写。

### 9.3 第一嫌疑:紧挨着的两次 AXI 写

### 10.2 关键否证:两个后端的**映射开法完全相同**

原本的假设是"PYNQ 的映射不是 `/dev/mem`" —— **错**。板上读源码:

```python
# /home/xilinx/pynq/pl_server/embedded_device.py:523  (pynq.MMIO 就是走这里)
mmap_file = os.open('/dev/mem', os.O_RDWR | os.O_SYNC)          # ← 与 poke_relay.py 逐字相同
mem = mmap.mmap(mmap_file, length + virt_offset, mmap.MAP_SHARED,
                mmap.PROT_READ | mmap.PROT_WRITE, offset=virt_base)
array = np.frombuffer(mem, np.uint32, length >> 2, virt_offset)  # ★ 唯一差别:包成 uint32 数组
```

⇒ 同一个 `/dev/mem`、同一个 `O_SYNC`、同一组 flag。
**唯一差别是"写下去的那一笔到底多宽、发了几笔"** —— 即调用方式,不是映射属性。

### 10.3 性质隔离(每次只改一个性质,写 `0x1C`)

| 变体 | 结果 |
|---|---|
| ① `pynq.MMIO.write`(numpy `uint32` 整字存) | `0x61` / err `0x00` ✓ |
| ② `mmap` + `struct.pack_into`,带 `O_SYNC` | `0x00` / err `0x03` ✗ |
| ③ `mmap` + `struct.pack_into`,**去掉** `O_SYNC` | `0x00` / err `0x03` ✗ ⇒ **`O_SYNC` 无关** |
| ④ `mmap` + **切片赋值** `m[a:b] = bytes` | `0x61` / err `0x00` ✓ |
| ⑤ 手工四次**单字节**存 | `0x61` / err `0x00` ✓ |

⇒ **判别式就是 `struct.pack_into` 与其它所有写法。**

### 10.4 公平四路对照(每次先把 busy 清干净并核对基线)

前面几轮的对照**不公平** —— `settle = 40 ms` 而脚本只 sleep 了几十 ms,
上一笔的 busy 窗口可能还没退。补齐基线后:

| 写 `0x1C = 0x61`,基线 `relay=0x10 busy=0 err=0x00` | 结果 |
|---|---|
| ① `pynq.MMIO` 整字 | `0x61` / err `0x00` ✓ |
| ② 裸 mmap **单字节** `m[0x1C]` | `0x61` / err `0x00` ✓ |
| ③ 裸 mmap **切片赋值** | `0x61` / err `0x00` ✓ |
| ④ **`struct.pack_into`** | **`0x00`** / err **`0x03`** ✗ |

再把 `settle` 设成 **0**(没有互锁):**四种写法全部得到 `0x61` / err `0x00`。**
⇒ ④ 的**最后一笔**是对的 —— 问题不在"值送错",在**发送笔数**。

### 10.5 收口:`struct.pack_into` 的第一笔写下去的是常数 `0x00000000`

用 `0x4C SCRATCH` 当证人(它整字锁存 `wdata_r`、读回原值,不受 relay 合法性/互锁干扰):

```python
mio.write(0x4C, 0x11223344); mm[0x4F] = 0xAA ; mio.read(0x4C)
# → 0xAA223344   (不是 0xAA000000 也不是 0xAAAAAAAA)
```

⇒ 窄写**确实**被模拟成"读-改-写"(其余字节来自器件现值)。**但**这条只解释 0x4F,
**不解释 `0x1C` 归零** —— RMW 会**保住** `bits[7:0]`。

决定性的一步:在 `0x1C` 上遍历 (基线, V):

| 基线 | V | 读回 |
|---|---|---|
| `0x10` | `0x00000061` | `0x00` |
| `0x61` | `0x00000061` | `0x00` |
| `0x7F` | `0x00000061` | `0x00` |
| `0x10` | `0x0000007F` | `0x00` |
| `0x61` | `0x0000007F` | `0x00` |
| `0x7F` | `0x00000000` | `0x00` |

**与基线无关、与 V 无关** ⇒ 第一笔不是 RMW(否则应等于基线),也不是 V,而是**常数 `0x00000000`**。

于是机制完整:

```
struct.pack_into("<I", mm, 0x1C, V)
   ├─ 事务①  WDATA = 0x00000000   → cfg_relay_set 脉冲①  → 0x00 合法 → 受理,relay_reg←0x00,busy←1
   ├─ 事务②… WDATA = …载荷…        → 脉冲②…              → busy ⇒ ERR_BUSY(0x03)
   └─ (settle=0 时无互锁 ⇒ 最后一笔胜出 ⇒ 结果正确,这就是为什么这个坑只在 0x1C 显形)
```

`0x00` 在 `relay_ctrl.v:216` 的白名单里 —— 这一步是**必须**的:若 `0x00` 不合法,
第一笔会被 `ERR_RELAY(0x01)` 拒收、`relay_reg` 不动、后续笔照常受理,**缺陷就不存在了**。

### 10.8 本文件该留下的一条方法论
