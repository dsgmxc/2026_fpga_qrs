## 二、🔴 前置条件(不满足会直接挂死整机,不是"读不到"而是"CPU 停摆")

**板上 `BOOT.BIN` 不含位流**(860396 B,位流同步字 `aa995556`/`aa995566` 出现 **0 次**;
`dmesg` 里 `fpga_manager` 无任何加载记录)⇒ **每次上电 PL 都是未配置的**。

```
PL 未配置 ⇒ GP0 读 0x43C00000 时 AXI 事务永远等不到从机响应
          ⇒ CPU 卡在总线上 ⇒ 整机挂死,**只能断电**  (GP 口无超时)
```

本轮**为这条规律付出了 3 次断电**。判据如下表,**新增第一条硬规则**:

| 情形 | 结果 |
|---|---|
| 一次开机内**先做且仅做一次** `Overlay()` 后再读寄存器 | ✅ 正常(本轮及 2026-10-03 全程) |
| **没做** `Overlay()` 就直接读 `0x43C00000` | ❌ 挂死(本轮第 2、3 次) |
| 一次开机内做**第二次** `Overlay()`(PL 已被前一次配好且 `lcd_fb_reader` 在动) | ❌ 挂死(本轮第 1 次) |

> **规则:一次上电只加载一次位流;寄存器访问必须排在那一次之后。**

### 2.1 ⚠️ 判据必须用 `INT_STS`,不能用 `STATUS`

本次实测同时得到一个**更正**:`devcfg STATUS`(0x14)**里没有 PCFG_DONE 这一位**。
权威出处 `xdevcfg_hw.h`(devcfg_v3_9):

| 寄存器 | 位 | 定义 |
|---|---|---|
| `STATUS` (0x14) | bit4 | `XDCFG_STATUS_PCFG_INIT_MASK = 0x10` — INIT_B 拉高,**只说明 PL 就绪** |
| `STATUS` (0x14) | bit5 | **无定义**(保留位) |
| `INT_STS` (0x0C) | bit2 | `XDCFG_IXR_PCFG_DONE_MASK = 0x04` — **DONE 在这里** |

实测:`INT_STS = 0x00020000` ⇒ PCFG_DONE = **0**(加载前,符合"PL 未配置");
`STATUS = 0x40000A30` ⇒ 我此前误当成 DONE=1 的,是那个保留位 bit5。

### 3.2 时钟 —— FCLK0 = 像素时钟

| 步骤 | `FPGA0_CLK_CTRL` | DIV0 / DIV1 | FCLK0 |
|---|---|---|---|
| `BOOT.BIN` 默认 | `0x00600600` | 6 / 6 | **27.7778 MHz**(**低于面板窗口下限 40.8**) |
| 只改 DIV0(❌ 我漏了 DIV1) | `0x00601400` | 20 / 6 | 8.3333 MHz |
| **DIV0=20 且 DIV1=1** | **`0x00101400`** | 20 / 1 | **50.0000 MHz** ✓ |

`0x00101400` 与 CLAUDE.md §八 记录的值**逐位一致**。

**帧率法独立复测**(帧几何 1344×635 = 853440 是常量):

| FCLK0(寄存器推算) | 场频实测 | PCLK(帧率法) | 偏差 |
|---|---|---|---|
| 27.7778 MHz | 32.5 Hz | 27.74 MHz | — |
| 8.3333 MHz | 9.657 Hz | **8.2414 MHz** | **1.10%** |
| 50.0000 MHz | 58.606 Hz | **50.0170 MHz** | **0.03%** |

> 🔴 中间那一行是**本轮额外得到的独立证据**:
> 若 IO PLL = 1500 MHz,推算应为 12.5 MHz,而实测 8.24 ⇒ 差 **52%**;
> 只有 IO PLL = **1000 MHz** 才对得上。这是 IO PLL = 1000 的**第四个独立确认点**。

### 3.3 ⭐ 界面端到端(用户手动点屏,后台 150 ms 轮询取证)

后台脚本 `tools/ui_watch.py` 只读关键寄存器、只打印**变化**、每行 `fsync`。

| 观测 | 次数 / 数值 |
|---|---|
| `0x68 TOUCH_STATUS` 变化 | 68 次(`seq` 递增、`pen` 有升降) |
| `0x6C TOUCH_PT0` 坐标更新 | 33 次 |
| `0x60 LCD_SWAP` **front 翻转** | 109 次(双缓冲换址在真跑) |
| **`0x14 BIAS_CODE` 变化** | **62 次** = 2 次手动调偏压(`0x8020C` 0.1 V → `0x86666` 5.0 V)+ **60 次扫压**;62 条里**不同码值只有 60 个** |
| `UNDERRUN=1` / `AXIERR=1` 出现行数 | **0 / 0** |

**扫描那 60 点逐点核对**(c_ui 自报「扫压开始:CISS,0.10 V → 5.00 V,60 点,每点 300 ms」):

| 检查 | 结果 |
|---|---|
| 点数 | **60** |
| 首点 | `0x8020C` = **0.100 V** 栅偏压(正是文档写的 0.1 V 下限码) |
| 末点 | `0x86666` = **5.000 V** |
| 单调递增 | ✅ 严格递增,`重复点 = 0` |
| 耗时 | 16:31:27 → 16:31:45 = **18.0 s** = 60 × 300 ms |

**首点不塌**(转换后):`0.1000 0.1069 0.1142 0.1220 0.1304 0.1393` V。
若走了 0.1 V 量化(`cv_bias_tenths_to_code`),前 6 点会**塌成同一个 0.1 V**
—— 而 `cv_regs.py` / `pynq_regs.h` 里正是为此警告过。实测 60 点**零重复** ⇒
**走的是全精度 `cv_bias_volts_to_code`**,该坑未复现。

### 3.4 步进规律 —— 硬件实测**逐点**验证了设计公式

实测步长**不是等距**:首步步长 **6.9 mV**,末步 **320.8 mV**,**相差 46.7×**。
对照源码 `pynq_protocol.c::sweep_bias_volts_at`:

```c
/* 扫压页 X 轴是 log10(V),范围 −1…+2(即 0.1 V … 100 V) */
/* 起止之间等比,和扫压页的 log 横轴一致 —— 曲线才会均匀铺满,不会全挤在左边。 */
ratio = (float)(index_1based - 1u) / (float)(total - 1u);
volts = SWEEP_START_VOLTS * powf(stop_volts / SWEEP_START_VOLTS, ratio);
```

**等比步进是有意设计**(匹配界面的对数横轴),不是手滑。把 60 个码按
`V = (−10 + 20·code/1048575) × 10` 换算回栅偏压后逐点核对:

| 项 | 值 |
|---|---|
| 逐点电压比值(59 个) | min `1.06780` / max `1.06959` / **mean `1.06855`** |
| 理论值 50^(1/59) | **`1.06855`** ← **吻合到小数点后 5 位** |
| 最大单点偏差 | **0.097%**(即 20 位码的量化台阶,无系统性偏差) |
| 端点 | `#1 = +0.1000 V`、`#60 = +5.0000 V`(与 clamp 一致) |

逐点抽样对照:

| 点 | 理论 | 实测 | 差 |
|---|---|---|---|
| #1 | 0.1000 V | 0.1000 V | 0.041% |
| #2 | 0.1069 V | 0.1069 V | 0.048% |
| #29 | 0.6402 V | 0.6402 V | 0.006% |
| #31 | 0.7309 V | 0.7310 V | 0.007% |
| #59 | 4.6792 V | 4.6792 V | 0.000% |
| #60 | 5.0000 V | 5.0000 V | 0.000% |

> **意义**:这条链路上「C 算出的浮点电压 → 20 位 DAC 码 → 回读」的**整条换算
> 与 RTL/C 两侧的实现是自洽的**,不是"差不多"。等比两端的 clamp 也生效。
> 依据是**板上真实下发的 60 个码**,不是仿真。

## 五、🔴 自我纠错轨迹

### 5.1 我编了一个寄存器位,并用它推出了错误结论

前三次挂死时,我用 `devcfg STATUS` 的 **bit5** 当 `PCFG_DONE`,读到 1 就断言
「PL 已配置」,再由此推出「PL 里留着上一轮的残留位流」,并进一步**要求用户
"真正断电"、质疑他上次是按了复位键**。

**两条都错**:
1. `STATUS` 里没有 PCFG_DONE —— 那是一位保留位,**bit5 = 1 毫无含义**;
2. 因此「残留位流」这条推理链整条不成立,对用户的质疑也应当撤回。

### 5.2 错在哪一步

不是算错,是**没有查出处**。这一条在 `CLAUDE.md` 与我自己的记忆里都写着
(「规则类结论必须出示出处」),而我在写判据时凭印象用了一个常见但**不适用于
这个寄存器**的位定义(Linux 的 `zynq-fpga.c` 也只在 `INT_STS` 上等 DONE)。
**更正方式是回到本机安装里的权威头文件** `xdevcfg_hw.h`,而不是再凭印象。

### 5.3 代价

这个错误没有直接弄坏硬件,但它**让诊断绕了一整圈**:真因其实更简单
——「PL 未配置 ⇒ GP0 无从机 ⇒ 读寄存器挂死 CPU」。**先查出处,能省一整轮。**

### 5.4 ✅ 收尾复查时,又推翻了一条我们自己写下的旧结论

技能包 `skill/pynq-overlay-bringup/` 里原有这么一条:

> ⚠️ `/sys/class/fpga_manager/fpga0/state` **不可作为"位流已进 PL"的证据** ——
> 本项目实测**加载前后都读 `unknown`**,原因未查明。

**本轮收尾做只读复查时实测:这条是错的。**

| 时刻 | `state` | `dmesg \| grep -i fpga` |
|---|---|---|
| 开机、未加载(§二) | `unknown` | 只有 `registered` / `probed` |
| **`Overlay()` 之后** | **`operating`** | 多一行 **`writing qrs.bin to Xilinx Zynq FPGA Manager`**(时间戳 `127.939679`) |

那行 dmesg 的时间戳**正好落在 `Overlay()` 调用的那一刻**(本次开机 `probe_all` 起于
uptime 122.94 s,B 区 `Overlay()` 约在 +5 s)⇒ 两者是同一事件的两个侧面。
⇒ **`state` 是可用判据**,已更正进技能包 §0.1 与 §失效条件。

**教训**:**"我测过、不行"这类旧结论,也要能追到那一次测量。**
追不到就很可能是「**没测就下了结论**」—— 本例正是。
(这是本轮第 2 次「自己写过的东西被自己的实测推翻」。)

## 六、本轮**没有**证明的事(不得越界引用)

- ⛔ **没有**用**万用表/示波器**验证 `dac_1220` 模块输出端真的出了对应电压,
  也**没有**验证 `adc_9833` 真的出了 1 MHz 正弦。**寄存器回读只证明 AXI 通路。**
- ⛔ **没有**测 `dac_init_done`(该信号**未导出为寄存器**,软件看不见);
  按 RTL 推算应在位流加载后约 800 ms 就绪,但**这是推算不是实测**。
- ⛔ **没有**验证 DLIA / ADC 采集通路(本轮范围之外)。
- ⛔ 满量程端点(±100 V 栅偏压)**未测** —— 本轮实测最大只到 **+5.0 V** 栅偏压,
  `0x14` 只在 `0x70001`~`0x90000` 附近(±12.5 V)与 0.1→5.0 V 扫压区间内摆动过。
- ⛔ `0x68` 的 `err` 粘滞位**全程为 1**,但触摸坐标与事件都正常。
  这是**历史累计标志**,不影响功能;成因未查。

## 七、复现步骤

```bash
# 0) 前置:qrs-ui.service 必须 disabled,保证本次上电 PL 未被加载
systemctl is-enabled qrs-ui.service          # 期望 disabled
sudo rm -f /home/xilinx/probe_all.log

# 1) 一次上电内唯一一次位流加载(必须有 XILINX_XRT,否则 PYNQ 报 No Devices Found)
export XILINX_XRT=/usr
/usr/local/share/pynq-venv/bin/python3 -u tools/step_all.py     # A 安全区 → B Overlay → C 探针

# 2) 把 PCLK 补到 50 MHz(BOOT.BIN 默认 27.78 低于面板窗口下限)
/usr/local/share/pynq-venv/bin/python3 -u <把 FPGA0_CLK_CTRL 写成 0x00101400 的脚本>

# 3) 起界面 + 后台取证
setsid nohup /home/xilinx/c_ui_src/c_ui --axi-base 0x43C00000 --poll-ms 10 \
        --fb0 0x38100000 --fb1 0x38230000 > /home/xilinx/ui_run.log 2>&1 &
WATCHSEC=900 setsid nohup python3 -u tools/ui_watch.py &   # → /home/xilinx/watch_ui.log
# 4) 手点屏幕,看 watch_ui.log 里 0x14 / 0x60 / 0x68 是否变化
```

### 7.1 本轮踩的三个**环境**坑(与硬件无关,但都会伪装成硬件故障)

| 现象 | 真因 | 处置 |
|---|---|---|
| `Overlay()` 报 `RuntimeError: No Devices Found` | `sudo` 不读 `/etc/profile.d`,`XILINX_XRT=/usr` 没被导出 | 显式 `export XILINX_XRT=/usr`(或照 `qrs-ui.service` 的 `Environment=`) |
| `import pynq` 抛 `UnicodeDecodeError`,崩在 `pkg_resources` 扫发行版 | `/usr/lib/python3/dist-packages/transitions-0.7.2.egg-info/PKG-INFO` 第 30722 字节非 UTF-8 | 走服务那套环境(`VIRTUAL_ENV` / `PATH` 齐全);或如本轮,直接手写 SLCR 寄存器绕开 pynq |
| 只改 `DIV0` 得到 8.33 MHz 而非 50 | **`DIV1` 也要置 1**(PYNQ 的 `Clocks` 会顺手设,手写容易漏) | 一次同时写 `DIV0=20` / `DIV1=1` |
