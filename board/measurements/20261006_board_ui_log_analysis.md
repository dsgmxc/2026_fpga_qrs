## 二、★ 发现 A:「100 kHz + 10 MSPS」单点测量 100% 失败

### 2.1 原始日志(逐字)

```
[touch] 按下 (341,339) 点数 1
[touch] 抬起
[mc] 激励 → 0.100 MHz(0x80 = 0x10624E)          ← 用户把激励频率切到 100 kHz
...
[proto] 点测 CISS+COSS+CRSS @ 5.00 V:偏压已下发,300 ms 后采一次
[adc] 🔴 单点测量:采集或解调失败 —— 解调不可用:每周期 100 点,超出参考表上限 64
      ⚠️ 此后不再重复打印这一条。
      ⇒ 依次查:
         ① 位流是不是含 0x88–0x98 的那一版;
         ② 0x90[0] mmcm_locked 是不是 1(没锁就是 MMCM 没起来);
         ③ 采样率档位是不是太低 —— 每周期点数 < 4 时本层拒绝解调 …;
         ④ 冒烟看 [adc] 那行的「峰峰」—— 个位数说明输入没信号。
```

### 2.2 机理

| 量 | 值 | 出处 |
|---|---|---|
| 采样率 | 10 MSPS(DIV=13) | `0x88`,用户**没改** |
| 激励频率 | 0.100 MHz | `0x80`,用户**改成了这个** |
| 每周期点数 `N = f_s / f_e` | **100** | — |
| 解调参考表上限 `ADC_DEMOD_MAX_N` | **64** | `adc_sample.c` |
| 结果 | `build_table(100)` 返回 false ⇒ **拒绝解调** | `AdcSample_Demodulate()` |

`ADC_DEMOD_MAX_N = 64` 的注释写的是「DIV=2(65 MHz)时每周期有 65 点,取 64 不够 —— 但那一档
本来就采不出可用波形」⇒ **它的余量是按 DIV 从 1 MHz 反推的**,没考虑**用户把激励频率调低**这条路径。

### 2.3 ★ 报错文案的排查指引 ③ **方向反了**

日志的指引是「③ 采样率档位是不是**太低**」。而本次的真实原因是
**采样率相对激励频率太高**(100 点/周期 > 表上限 64)。
⇒ 该文案只覆盖了 `N < 4` 那一支,**漏了 `N > 表上限` 这一支**。
按它排查会往反方向走(去调高采样率,而那样 `N` 只会更大)。

### 2.4 静默重复

`adc_report_failure()` **只打印一次**("此后不再重复打印这一条"),防的是扫压时刷 60 行。
代价:本次 5 次失败里**只有第 1 次有日志**,后 4 次**屏上无反馈、日志里没有**。
⇒ 唯一的兜底是停服务时的 `dump_stats()` 计数 `ADC 采集 失败=5`(见 §三)。
**若服务一直不停,这次失败在证据上就是不可见的。**

### 2.5 影响范围(要说清)

- ✅ **扫压不受影响**:本次 6 轮扫压**全部**在 1 MHz 下跑的(`激励 → 0.100 MHz` 之后**没有**再发起扫压)。
- ⛔ **但隐患是真的**:若在 100 kHz 下发起扫压,60 点会**全部失败且只打 1 行**,
  而 `[proto] 扫压结束:60 点已下发到 DAC` **照常打印** —— 看起来像"跑完了",曲线是空的。

```

  0x64 = 0x000D53E4  underrun=1  axierr=0  vblank_cnt=249  swap_cnt=170
```

| 项 | 日志实测 | 与计数器对账 |
|---|---|---|
| `[adc] 扫压` 行 | **326** | 5 轮完整扫压 × 60 = 300,加被停的 `27/60` 那轮约 26 点 ⇒ **326** ✓ |
| `[adc] 单点` 行 | **6** | — |
| 两者合计 | **332** | **= `成功=332`** ✓ |
| `[adc] 🔴` 失败行 | **1**(打印一次) | — |
| 100 kHz 窗口内的点测请求 | **5** | **= `失败=5`** ✓ |
| 本周期点测请求总数 | **11**(2 单路 + 9 三路) | **11 = 6 成功 + 5 失败** ✓ |
| 无归属的 `[adc]` 行 | `333 − 326 − 6 = 1` | 正是那条 🔴 失败行 ✓ |

⇒ **每一路数字都能闭合**:扫压 326 点全成功、单点 6 成 5 败、失败全部落在 100 kHz 窗口内。

## 四、⚠️ 发现 B:`underrun=1`(粘滞)

```
0x64 = 0x000D53E4  underrun=1  axierr=0  vblank_cnt=249  swap_cnt=170
⚠️  underrun 已置起(粘滞,写 0x60 清):PL 取数时帧缓存还没备好。
    上板判据是「跑 60 s 后必须为 0」,见 display_probe.py。
```

- 本工程自己的判据是「**跑 60 s 后必须为 0**」,而本次服务跑了约 **31 分钟**,`underrun` 仍为 1。
- ⚠️ **但它是粘滞位** ⇒ **无法只凭这一条判断是"启动时置起"还是"运行中置起"**。
- 🟡 **最可能的解释**(需实测确认,不写成结论):`F1` 已知的**上电头几百拍 PL 跑在 27.78 MHz**
  (出面板窗口,屏上表现为"上电闪一下")—— 那一瞬 `lcd_fb_reader` 的取数节拍不对,足以置起 underrun。
- **本轮没做**:清零(`写 0x60`)后跑满 60 s 再读 —— 做到那一步才能区分。
  ⛔ 且**本轮已无法补做**:服务已停,再 `start` 就是本上电周期的第 2 次 `Overlay()`(已知会锁死 HP 口)。
