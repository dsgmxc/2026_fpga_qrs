## 三、本条位流相对上一版的唯一改动(0x74 拆位)

第 33 次位流已证明**拍数是满帧**(153600),却仍全黑 ⇒ 说明"拍数"只证明**握手发生了**,
**看不见数据本身**。故本轮把 `0x74` 拆成两段:

| 位 | 字段 | 含义 |
|---|---|---|
| `[17:0]` | `beats_cnt` | 本帧 `m_axi_rvalid` 拍数(满帧 **153600** = 256 拍 × 600 行) |
| `[19:18]` | `rresp_lat` | 本帧最后一次非 OKAY 响应:`00` 无 / `10` SLVERR / `11` **DECERR** |
| `[20]` | `axi_or_nz` | 本帧**任一拍 `rdata` 有任一比特为 1** |
| `[21]` | `px_or_nz` | 本帧 `px_data` 出现过非零(**行缓冲确实读出了东西**) |
| `[31:22]` | — | 保留 |

> 🔑 **为什么要这样拆**:`DECERR` 时 AXI 从设备会回 **全零数据**,而**握手照常完成**。
> 只看拍数,「拿到了 153600 拍零」和「拿到了 153600 拍真图像」**读数完全一样**。

## 四、原始实测数据

### 4.1 三个工况(`tools/lcd_ddr_debug.py`,每点连采 300 次取最大值)

| # | 工况 | `beats_cnt` | 占满帧 | `rresp_lat` | `axi_or_nz` | `px_or_nz` | 屏上(用户目视) |
|---|---|---|---|---|---|---|---|
| 1 | `src=0` 厂商彩条(基线:不该取数) | **0** | 0.0% | `00`(无错) | 0 | 0 | 🟢 正常彩条 |
| 2 | `src=1` 整屏填充 | — | — | — | — | — | 🟢 正常纯色 |
| 3 | `src=2` fb0 = `0x38100000`(内容:整屏绿+中间红横带) | **153088** | 99.7% | **`11` DECERR** | **0** | **0** | 🔴 **全黑** |
| 4 | `src=2` fb0 = `0x00100000`(内核镜像,内容必然非零) | **153121** | 99.7% | **`11` DECERR** | **0** | **0** | 🔴 **仍然全黑** |
| 5 | `src=2` fb0 = `0x38230000`(自己的 fb1:整屏蓝) | **153600** | 100% | **`11` DECERR** | **0** | **0** | 🔴 **仍然全黑** |

> 第 3/4/5 行的 99.7% 是**帧内随机采样**的产物(`0x74` 每个 `frame_start` 清零),
> 不是欠载。第 5 行采到 100%。

🟢 **第 1 行是干净的对照组**:不取数时 `rresp_lat = 00`,`axi_or_nz = 0`。
⇒ **DECERR 是我方读事务的响应**,不是背景噪声。

🔴 **第 4 行是最有判别力的一行**:地址换成**内核镜像**(内容当然是任意非零字节)。
若通路只是"取错了块 DDR",屏上应出现**花屏/噪声**;
实际是**仍然全黑**且 `axi_or_nz=0` ⇒ **一个非零比特都没回来过**。

### 4.2 `DBG_ARADDR` 地址生成器核对(证明"地址算对了")

`0x78` 采到 **`0x381EDF80`**,按 fb0 = `0x38100000` 拆:

```
0x381EDF80 - 0x38100000 = 0x000EDF80 = 974 720 (十进制)
974 720 = 456 × 2048 + 15 × 128
          └ 行号 456    └ 该行内第 15 个突发 × 128 B(16 拍 × 8 B)
```
⇒ 行首对齐 ✅、128 B 对齐 ✅、落在 fb0 的 1,245,184 B 范围内 ✅。

### 4.3 地址扫描(`tools/lcd_fb_sweep.py`)—— **决定性的一轮**

把 `fb_base0` 依次指向 9 个地址,每点采 120 次:

| 地址 | 指向 |
|---|---|
| `0x00000000` | OCM(**必然可读**) |
| `0x000F0000` | DDR 低端 |
| `0x00100000` | 内核镜像起始 |
| `0x01000000` | DDR 中段 |
| `0x10000000` | DDR |
| `0x20000000` | DDR |
| `0x30000000` | DDR |
| `0x3FF00000` | DDR 顶端(1 GB 边界内) |
| `0x40000000` | **越界**(HP0 的 MEMRANGE 上界 = `0x3FFFFFFF`) |

**结果:9 个地址无一例外,全部 `rresp_lat = 11 (DECERR)` 且 `axi_or_nz = 0`。**

🔑 **这一轮的作用**:`0x00000000`(OCM)和越界的 `0x40000000` **给出完全相同的读数**
⇒ **拒绝发生在端口层面,与地址译码无关。**
"地址映射配错了""帧缓存不在 DDR 里""PS 没 flush cache"这一类假设**全部作废**。

## 10.1 「AFI 读通道被位流关掉了」—— 作废

把官方那份**厂商已验证**的位流烧进同一块板,读同一组寄存器(全程**只读**):

| 地址 | 名称 | 我方 `qrs.bit` | 官方 `pl_rw_ddr.bit` |
|---|---|---|---|
| `0xF8008000` | AFI0_RDCHAN_CTRL | `0x00000000` | `0x00000000` |
| `0xF8008004` | AFI0_RDCHAN_ISSUINGCAP | `0x00000007` | `0x00000007` |
| `0xF8008010` | AFI0_RDDATAFIFO_LEVEL | `0x00000000` | `0x00000000` |
| `0xF8008024` | AFI0_WRCHAN_CTRL | `0x00000000` | `0x00000000` |
| `0xF8000240` | `FPGA_RST_CTRL`(只读) | `0x00000000` | `0x00000000` |

⇒ **四种读数逐条相同。** 「读通道被位流关掉/位流改了 AFI 状态」**不成立**。

## 10.2 🔴 修正 §六:那两行 AFI 读数**不是稳定值**,不是"配置"

同一条 `qrs.bit`、同一块板,两个会话:

| 地址 | §六 存档(同日早些时候) | 本节复测 |
|---|---|---|
| `0xF8008010` | `0x0000001A`(= 26) | `0x00000000` |
| `0xF8008024` | `0x00000F00` | `0x00000000` |

⇒ **这两个寄存器读的是「当时的活动状态」,不是「配置」。**
§六 表里这两行的**「解读」列作废**(`0xF00`→"64 位读通道"、`26`→"队列里有 26 项" 均属过度解读)。
§五 第 8 条(用 `RDCHAN_CTRL = 0` 排除 32 位配置)**结论恰好仍成立**(官方也是 0),
但**理由要换成 10.1 的对照** —— 不是"读到 0 即 64 位"。

## 10.3 🔴🔴 本节最强推论:AFI 不可能成为根因

`ps7_init.c`(厂商例程那份,7450 行)**对 AFI 寄存器一次写都没有**
—— `grep -cE "0XF8008[0-9A-F]{3}"` = **0**,三段 AFI 段(`AFI0/1/2 REGISTERS`)全空。
而**位流无法写 PS 侧寄存器**。

```
⇒ 任何位流烧进来,AFI 都停在同一个上电默认值
⇒ 若厂商那份 HP0 能工作(它是随板已测试例程),则该默认值【是可工作的】
⇒ DECERR 不可能是 AFI 配错
```

**这一条把 §七 的方向表砍掉一半:根因不在 PS7 的 HP0 配置里。**

## 10.5 🆕 唯一找到的拓扑差异:官方**过 SmartConnect**,我们**直连**

官方 `system.bd` 的 `interface_nets`:

```
axi4_rw_test_0/M_AXI  →  axi_smc/S00_AXI          ← 过 SmartConnect
axi_smc/M00_AXI       →  processing_system7_0/S_AXI_HP0
```

我方 `qrs.gen/sources_1/bd/system/synth/system.v:355-389`:

```
.S_AXI_HP0_ARADDR (cv_sys_0_M_AXI_ARADDR),   ← 直连,中间没有任何 IP
.S_AXI_HP0_ARID   ({6{1'b0}})
.S_AXI_HP0_AWVALID(1'b0), .S_AXI_HP0_WVALID(1'b0), .S_AXI_HP0_BREADY(1'b0)
```

**官方那只主机**:`DATA_WIDTH 32` / `ID_WIDTH 1` / `BURST_LEN 16` / AXI4,
BD 里 `C_M_AXI_TARGET_SLAVE_BASE_ADDR = 0x10000000`(合法,在 1G 段内)。
⇒ 它**必须**过 SmartConnect:数据宽度 32→64、ID 1→6、AXI4→AXI3 三样都要转。

**我们这只**:自声明 AXI3 / 64 位 / ID 0 / `MAX_BURST_LENGTH 16`
(`cv_sys.v:132`)⇒ IPI 判定可直连,**没插互联**。

> ⚠️ **这是本轮唯一找到的、能区分两个设计的东西,但它【不是已证明的根因】。**
> 直连在 AXI 语义上合法;要证它不行,得把"插了互联的版本"跑起来比。
> 已排成实验(10.7)。

## 10.7 🆕 已备好的判决实验:厂商位流当"金标准",**判读不靠人眼**

本轮查明(出处 `~/Desktop/zdyz/3_开发板原理图和硬件相关文件/NAVIGATOR_ZYNQ_IO.xdc`,GBK 编码):

```
L14 = key[0]  = PL_KEY0
H15 = led[0]  = PL_LED0
L15 = led[1]  = PL_LED1
```

⇒ 官方 `20_pl_rw_ddr` 位流**在本板上按一下 KEY0 就能跑**。已 staged 在板上:
`/home/xilinx/pl_rw_ddr.bit` + `.hwh`(`Overlay("/home/xilinx/pl_rw_ddr.bit")`)。

**触发链**(唯一入口,PS 侧够不着):

```
key_init(L14) → key_debounce_0/key → util_vector_logic_0 → axi4_rw_test_0/m_axi_init_axi_txn
```

**判读改用 DDR 指纹,不靠 LED** —— 厂商 RTL 写的是**自增数**
(`axi4_rw_test_v1_0_M_AXI.v:457-461`:`axi_wdata <= 1, 2, 3 … 16`),
地址 `M_AXI_AWADDR = 0x10000000 + 偏移`(16 拍 × 4 B = 64 B)。

**已实测基线**(PL 未触发,该处是 Linux 的 DTB):

```
0x10000000 = 0xEDFE0DD0   0x10000004 = 0xD0E95900   0x10000008 = 0x38000000
0x1000000C = 0xC4E55900   0x10000010 = 0x28000000   0x10000014 = 0x11000000
```

**判决表**:

| 按 KEY0 之后 `0x10000000…3C` | 含义 |
|---|---|
| 变成 `0x1, 0x2, 0x3 … 0x10` | ✅ **HP0 写+读都通** ⇒ DECERR 出在**我方 PL 侧**(10.5 或主机协议) |
| 仍是 DTB 那几个字 | 🔴 **厂商设计也读不出来** ⇒ 问题在**板子 / PS 状态**,与我方 RTL 无关 |

> ⚠️ **副作用**:这一步会覆盖 `0x10000000` 处 64 B 的 DTB。
> 内核启动时已解析完 DTB,**预期无影响 —— 但这是推断,不是实测。**
