## 一、被推翻的假设

### 1.1 假设怎么来的

上一轮"对读"我方主机与厂商已验证主机
(`/tmp/lcd_ref/rtl/axi4_rw_test_v1_0_M_AXI.v:277-278`)时,发现二者**唯一的差异**是事务属性常量:

| 字段 | 厂商(能工作) | 我方 | 差异位 |
|---|---|---|---|
| `ARCACHE` | `4'b0010` | `4'b0011` | bit0 |
| `ARPROT` | `3'h0` | `3'b010` | **bit1 = NS(非安全)位** |

推理链:`ARPROT[1]=1` 是非安全访问 ⇒ 内存子系统做安全检查,安全位不匹配可在**地址译码之前**
拒答 ⇒ 这能解释「**连 `0x00000000`(OCM,必然可读)都 DECERR**」这条别的假设都解释不了的现象。

> ⚠️ 当时已自我标注:**机理无出处**(本机无 UG585/TRM),按"与已验证参照物逐字段对齐"做实验。
> 取值出处是本机 Vivado 里的 Xilinx AXI master 模板两处同源副本
> (`$XILINX_VIVADO/data/emulation/hw_em/ip_repo/sim_xdma_2.0/hdl/sim_xdma_v2_0_M_AXI.v:278-279`、
> `.../me_config_1.0/hdl/me_config_v1_0_M0_AXI.v:278-279`)。

### 1.2 A/B 实测表(全部同一块板、同一个 boot、相邻几分钟)

| # | 位流 md5 | `ARPROT` | `ARCACHE` | `rresp_lat` | `axi_or_nz` | `px_or_nz` | `beats` |
|---|---|---|---|---|---|---|---|
| 0 | `f45cb175…`(上一轮,boot **-1**) | `010` | `0011` | **11 DECERR** | 0 | 0 | 满帧(全零) |
| 1 | `a9636e0d…` | `000` | `0010` | 0 **OKAY** | 1 | 1 | 99.8% |
| 2 | `cdfbe0f5…` | **`010`** | **`0011`** | 0 **OKAY** | 1 | 1 | **100%** |
| 3 | `298c8f1f…` | **`010`** | **`0011`** | **3 DECERR** | 0 | 0 | 100%(全零) |
| 4 | `298c8f1f…` 重载 | `010` | `0011` | **3 DECERR** | 0 | 0 | 100%(全零) |
| 5 | `298c8f1f…` 重载 | `010` | `0011` | **3 DECERR** | 0 | 0 | 100%(全零) |

**第 2 行与第 3 行 `ARPROT`/`ARCACHE` 取值完全相同,结果相反** ⇒ **假设被推翻**。
`ARPROT` 不是决定因素。

> ⚠️ 第 3–6 行的 `ARPROT=010` 已在**综合后网表**里逐位核对过
> (`write_verilog` 后 `.S_AXI_HP0_ARPROT({1'b0,1'b1,1'b0})`、`.S_AXI_HP0_ARCACHE({1'b0,1'b0,1'b1,1'b1})`),
> 不是"改了没进位流"。第 1 行的 `000`/`0010` 同样在网表里核过。
> ⇒ **不是构建问题,是结果本身在两种取值下都出现过。**

## 二、推翻之后,故障的性质变了

### 2.1 它是**粘滞二态**,不是确定性错误

- 表第 3–6 行:**同一份位流连续重载 4 次,4 次全 DECERR**(3/3 复测 + 首测)⇒ 一旦进入 DECERR 态,**重载位流不能恢复**。
- 表第 1–2 行:同样在 DECERR 之前几分钟,连续两次读到 **OKAY** ⇒ 这个态**确实可以存在**。
- 表第 2 行与第 3 行**取值相同、结果相反** ⇒ 状态的翻转**不由 RTL 内容决定**。

⇒ 结论:**DECERR 是 PS 侧(HP 端口 / AFI)的一个粘滞状态**,PL 位流的内容只决定"要不要用这个端口",
不决定"端口当前能不能用"。这与上一轮存档 §五 第 6 条的自我警告完全吻合 ——
**「`FPGA_RST_CTRL` 读回干净 ≠ 该寄存器控制的硬件已复原」**,那条"排除"当时就标注了"保留"。

### 2.2 🔴 一个此前一直搞错的事实:上一次的 DECERR 读数**不在同一个 boot 上**

`journalctl --list-boots`:

```
-1 f4ff9eec… Wed 2021-11-17 21:55:34 UTC—Wed 2021-11-17 22:26:13 UTC
 0 3e044649… Wed 2021-11-17 22:26:13 UTC—Wed 2021-11-17 22:53:47 UTC   ← 本次
```

- **`20261003_ddr_hp0_decerr.md` 里全部 DECERR 读数,发生在 boot `-1`。**
- boot `-1` 于 22:26:13 结束,与 boot `0` 的起始**同一秒** ⇒ 板子在两次会话之间**重启过**。
- 本轮所有实测(表 1–6)都在 boot `0` 上。

⇒ 之前"DECERR 一直存在、跨会话不变"的印象是**跨 boot 得到的**,属于把两个 boot 的读数当成一条时间线。
**LLM-034 结论"下一动作是断电重启"的那一步,事实上已经(以某种形式)发生过一次** —— 而它并没有让故障消失(表 3–6 仍是 DECERR)。
⚠️ **是上电冷启动(POR)还是热重启,`journalctl` 分不出来** —— 只有用户知道,已去问。

### 2.3 时间线(boot 0,`t` = 开机秒数,取自 dmesg)

```
 t= 166/178  qrs.bin         (第 34 次会话)
 t= 275      pl_rw_ddr.bin   (AFI 对照读数)
 t= 490      qrs.bin
 ───────────── 本会话开始(uptime 865 s)─────────────
 t=1100      pl_rw_ddr.bin   (厂商位流,复测 DTB 基线)
 t≈1100-1257 【用户按下 PL_KEY0】← 唯一一次"厂商主机的成功 HP0 事务"
 t=1257      qrs.bin  a9636e0d  →  OKAY     ← 本 boot 上的第一次 0x74 读数
 t=1415      qrs.bin  cdfbe0f5  →  OKAY
 t=1596      qrs.bin  298c8f1f  →  DECERR   ← 翻转发生在这两次重载之间
 t=1619/1631/1643  同一份重载 ×3 → DECERR
```

⚠️ **在 t≈1100(厂商位流加载)之前,本 boot 上从未测过 `0x74`** ⇒
**"故障是什么时候好的"没有观测,不能把 OKAY 归因给 KEY0 按下**。
"KEY0 按下"与"加载厂商位流"与"进入 OKAY 态"三者在时间上重叠,**目前分不开**。

## 四、沉淀(供 `skill/` 与报告 §优化过程 引用)

| 教训 | 说明 |
|---|---|
| 🟢 **"与参照物逐字段对齐"是好方法,但必须配对照实验才能下结论** | 找到唯一差异 ≠ 确认因果。本轮把"唯一差异"当成了"根因",**十分钟后就被自己的对照组推翻** |
| 🟢 **A/B 必须**改回旧值再测一次**** | 只测"改了之后好了",无法区分"改动生效"与"别的因素变了"。本次正是靠**改回旧值也好了**才抓住 |
| 🟢 **位流 md5 不是"改动是否生效"的合格判据** | 两份**逻辑完全相同**的构建(仅注释不同)md5 分别为 `cdfbe0f5…` / `298c8f1f…`。本次靠**综合后网表逐位核对**才真正坐实。**md5 变了不能证明改动进去了,md5 没变也不能证明没进去** |
| 🟢 **跨 boot 的读数不能拼成一条时间线** | 上一轮"DECERR 跨会话稳定存在"的印象,实为 boot `-1` 与 boot `0` 两组读数被并置。**测板子前先记 `uptime` / `journalctl --list-boots`,把读数钉到 boot 上** |
| 🟢 **"粘滞状态"与"配置错误"要用不同手段查** | 配置错误:改配置 → 复现。粘滞状态:改配置**无效**,要的是复位/清状态。**判据是"重载同一份是否结果一致"** |
