## 纠错轨迹

1. **模型错在哪(第一轮推断)**
   模型读用户的 `io.xdc`,把 `dac_cs=W13` / `dac_mosi=Y14` / `dac_sclk=W15` 与官方
   `NAVIGATOR_ZYNQ_IO.xdc` 对照,查到 `W13 = cam_data[5]`、`Y14 = cam_data[7]`,
   而 **`W15` 在官方引脚表里完全不存在** → 据此推断:
   「这三个脚是**摄像头接口专用**,DAC 模块根本没接到,所以输出恒 0」。
   **这个推断是错的。**
2. **是怎么发现错的**
   推断的过程里模型注意到一件事**自己解释不通**:正点原子不该把三个不相关的脚
   放在一起。于是改去查**底板原理图第 5 页**,在 J4(Header 20X2)表里找到了
   `W13`/`Y14`/`W15` —— **三个脚是 J4 的第 32 / 34 / 36 脚,同一列,物理上完全相邻**。
   J4 把它们也接到了摄像头接口,所以底板网络名叫 `CMOS_D5` / `CMOS_D7` / `CMOS_XCLK`,
   官方 XDC 才把它们命名成 `cam_data[*]`。
3. **怎么交叉验证的(两处独立吻合 + 一处第三方佐证)**
   - 用 J4 表反推:`W14 = J4-33 = CMOS_PCLK`,与官方 XDC 的 `cam_pclk = W14` **吻合**;
   - `W13 = J4-32 = CMOS_D5`,与官方 XDC 的 `cam_data[5] = W13` **吻合**;
   - 核心板走线长度 CSV 里 `21:BANK_34:X4.55:U1.W13` 的 **X4.55** 与 J4 表第 55 脚一致。
   → 确认 J4 表的映射方向读对了。
4. **改完还有没有问题**
   有。**模型犯这条错的根源是使用了一条错误的规则**:
   「官方 XDC 里没有这个脚 ⇒ 板上没有这个脚」。
   实际开发指南原文写明该引脚表是「**上表列出了除扩展口外**,开发板上所有 PL 功能外设
   所对应的 IO 引脚号」—— **扩展口引脚本来就不在官方 XDC 里**。
   这条已作为结论写入 `docs/board_pins.md` 的「已知陷阱」。
5. **最终根因不是模型给出的**
   模型把票押在"引脚接错",用户自查才是对的:**位流没更新**。
   与 LLM-009/LLM-011 同源 —— **模型的所有静态推导都建立在"板子跑的是我以为的那版程序"
   这个未验证的前提上**。
6. **模型在本次记录里先写错了读数,同日自己回读报告改正(第三次交互)**
   模型把加 ILA **之前**那份实现报告的数字(布线 **246/246**、DRC **仅 `ZPS7-1` 一条**)
   写进了本文件和 `project_state.md`,而当时盘上已是**加了 `ila_0` 之后**的新报告。
   发现方式:写完之后**重新回读 `qrs.runs/impl_1/` 的原始 `.rpt`**,读出
   **布线 2817/2817、DRC 无 Error(5 条 Warning,其中 `PDCN-1569`×3 与 `RTSTAT-10`×1
   全部落在 `dbg_hub/...` 内部,与用户 RTL 无关)** → 逐处回改。
   **教训**:引用报告数字时**必须当场读文件**,不能凭"我记得刚看过"复用 ——
   与第 5 条同型(前提未复核),也与 LLM-005 的"静默复用过期产物"同源。
7. **模型先守住边界、随后又踩了同型的坑,最后自己实测收口(本次最值得记的一段)**
   - **正面**:被问"把 `create_clock` 补上有什么问题"时,模型**没有凭印象断言**,
     而是明确写出"未实测,不下结论"。与 LLM-003(把推断说成规定)相反的做法。
   - **反面**:但同一条回复里,模型**断言了"本机未装 Vivado"** ——
     这只是搜了 `/tools/Xilinx`、`/opt/Xilinx`、`~/Xilinx`(**大写**)就得出的**全称否定结论**,
     **漏了小写 `~/xilinx`**(实际安装位置)。更讽刺的是,**模型自己的 memory
     `vivado-cli-for-verification` 里就写着正确路径**,只是没去读。
   - **与主线错因同型**:「官方 XDC 里没有 ⇒ 板上没有」= 一次不充分的搜索 → 一个全称否定结论;
     「`/tools` 等目录里没有 ⇒ 本机没装 Vivado」= **完全同一个模式**。
     同一天里同一模式犯了两次,说明这不是偶发,是**默认推理习惯**。
   - **收口**:模型随后自己在 `/tmp/cc_test/` 用 Vivado 2025.2 batch 实测,拿到确定答案
     (不报 Error,后者覆盖前者;同名 `WARNING 18-619` / 不同名 `CRITICAL WARNING 18-1056`),
     并把文档里"未实测"的说法**逐处回改**。**"结论未定 → 去实测 → 改写文档"这个闭环是正的。**

## 追加(同日第三次交互):三点实测 + `locked` + `create_clock` 释义

**用户输入**(原文见上第 6 条提示词):贴回对照表并说「测量结果跟这张表一样」;
要求 Claude **代写 `locked` 部分**;并问 `create_clock` 那条「**这个问题什么意思**」。

**① 三点实测 —— 这次测量比 Claude 原方案更有价值**

Claude 原先建议量 `0x00000 / 0x80000 / 0xFFFFF`(两端点 + 中点)。
用户实际量的是 **`0x40000` / `0x80000` / `0xC0000`**(1/4、1/2、3/4 满量程)——
**用户选点更好**:端点容易被模块输出轨钳位,1/4–3/4 三点既避开饱和,又能同时看线性度和单调性。

| 码值 | 实测字节序 | 预期:模块层 | 预期:芯片层(VREF=2.5 V) |
|---|---|---|---|
| `0x40000` | `40 40 00 00` | −5.00 V | 1.25 V |
| `0x80000` | `40 80 00 00` | 0.00 V | 2.50 V |
| `0xC0000` | `40 C0 00 00` | +5.00 V | 3.75 V |

**实测结果与表一致** ⇒ 反向坐实 **LLM-010 修的那个位切片缺陷在硬件上确实修对了**
(符合实测的字节序正是 DIR left-justified 规则算出来的:
`cmd=0x40` + `code[19:12]` + `code[11:4]` + `{code[3:0],4'b0}`)。

⚠️ **Claude 没有追问到位的一点**:用户说"跟这张表一样",而**该表有两列电压**
(模块层 −5/0/+5 V 与芯片层 1.25/2.5/3.75 V)。**到底哪一列对上,Claude 事后才补问**,
而这正是判断 `docs/dac1220_interface.md` 里「模块量程 −10~+10 V」这条**未核实假设**
是否成立的关键。

**✅ 用户答复(同日收工前)**:**「我测得都是模块层输出电压,都是对上的」** ⇒

- `docs/dac1220_interface.md` **U2(模块量程 −10~+10 V)升级为"已证实"**;
- **U3(传递关系)升级为"已证实"**:`V = −10 + 20 × code / 1048575`
  在 **1/4 / 1/2 / 3/4 满量程**三点成立,PS 侧可据此反算码值;
- ⚠️ **但端点 `0x00000` / `0xFFFFF` 仍未测** —— 模块输出级通常在轨附近提前饱和(运放输出摆幅
  一般比电源轨少 1~2 V),故「**满量程恰好 ±10.00 V**」**仍不得断言**;
  已把"补测端点、必要时用实际端点重新拟合"写进两处待办。

**这一步的意义**:U2/U3 从 2026-09-16 建立接口文档起就挂着"未核实",
**四天后由一次三点万用表测量闭环** —— 可作为报告里「接口规格是如何被验证的」的样本
(呼应 B06:不只呈现结果,还要呈现**判断依据是怎么被证实/推翻的**)。

**② `locked` —— 用户明确要求代写(CLAUDE.md §6.0 的例外口子)**

改动 3 行,最小 diff:

| 位置 | 改动 |
|---|---|
| `qrs.v` 新增 | `wire rst_n_sys = rst_n & locked;`(在 `clk_wiz_0` 例化之后) |
| `init_done_d` 的 always 块 | `negedge rst_n` → `negedge rst_n_sys`,`if(!rst_n)` → `if(!rst_n_sys)` |
| `dac_1220` 例化 | `.rst_n(rst_n)` → `.rst_n(rst_n_sys)` |
| **保持不动** | `clk_wiz_0.resetn(rst_n)`(**不能**改成 `rst_n_sys`)、`ila_0.probe0(rst_n)` |

**关键理由(写进报告用)**:`clk_wiz` 的 `.resetn` 若也接 `rst_n_sys`,就构成
**`locked` 依赖 `resetn`、`resetn` 又依赖 `locked` 的组合死锁**,MMCM 永远锁不上 ——
比原来的 bug 更严重。`ila_0` 的 probe0 保留原始 `rst_n` 是为了还能在波形里看到按键状态。

⚠️ **Claude 主动声明的一处不完美**:`rst_n_sys` 是**组合信号**,用作异步复位存在
**释放沿与 `spi_clk_50m` 不同步**的理论风险(复位撤销的恢复/移除时间)。
本项目风险极低(FSM 复位后还要等 200 ms 才动作),故未加复位同步器;
若要写成"规范做法",应补一级同步。**这是 Claude 的判断,不是实测结论。**

**③ `create_clock` —— 用户问"这个问题什么意思"**

现状核查(读盘,非推断):`qrs.gen/sources_1/ip/clk_wiz_0/clk_wiz_0.xdc` 里**确实有**

```tcl
create_clock -period 20.000 [get_ports clk_in1]
set_input_jitter [get_clocks -of_objects [get_ports clk_in1]] 0.200
```

**所以今天不缺约束**(时序报告里 `clk_in1` 确为 50 MHz、3873 endpoint 全部被分析)。
真正的三点是:

| 点 | 内容 |
|---|---|
| 位置问题 | 约束住在**生成目录** `qrs.gen/`,不在用户自己的 `constrs_1/io.xdc`。评审打开 `io.xdc` 只看得到 5 条 `set_property`,**看不到输入时钟周期** |
| 来源问题 | `20.000 ns` 由 IP 配置项 **`PRIM_IN_FREQ = 50`** 推出。**若板上晶振不是 50 MHz,IP 照样按 50 MHz 约束,时序报告照样 passing —— 但那是假的** |
| 事实核查 | 本项目该假设**已查证为真**(`U18 = 50 MHz`,官方 XDC + 开发指南两处) |

**给用户的第一版结论:建议不要重复加**;并明确写出「**重复定义同一 port 的 `create_clock`
会发生什么,本机未装 Vivado、未实测,故不下结论**」。

⚠️ **但这个"本机未装 Vivado"是错的 —— Claude 自己发现并纠正了**:
Claude 只搜了 `/tools/Xilinx`、`/opt/Xilinx`、`~/Xilinx`(**大写 X**),漏了**小写 `~/xilinx`**。
Vivado 2025.2 实际就在 **`/home/hyp/xilinx/2025.2/Vivado/bin`**(见 memory
`vivado-cli-for-verification` —— **那条 memory 里本来就写着正确路径,Claude 没去读**)。

**→ 于是当场实测(在 `/tmp/cc_test/` 跑 Vivado 2025.2 batch,未碰用户工程):**

| 情形 | 结果 |
|---|---|
| 两条 **同名同周期**(`clk_in1`,均 20.000 ns) | `WARNING: [Constraints 18-619] A clock with name 'clk_in1' already exists, overwriting the previous clock with the same name.` |
| 两条 **不同名**(`clk_in1` 20 ns vs `my_clk` 15 ns) | `CRITICAL WARNING: [Constraints 18-1056] Clock 'my_clk' completely overrides clock 'clk_in1'.` |
| `report_clocks` | **两种情形都只剩一个时钟**(后者覆盖前者),**不报 Error** |

**修正后的结论:加注释就够了,不建议真加约束** ——
加约束的唯一好处是"评审能在 `io.xdc` 里看到周期",注释同样能做到;真加会多一条 WARNING,
而且 **IP 那条还带 `set_input_jitter`,覆盖后抖动设置是否随之丢失,Claude 未测**。
要做到"自己管",干净做法是 `set_property is_enabled false [get_files clk_wiz_0.xdc]` 关掉 IP 那条再自己写。

**这一段的双重价值(可写进报告第 5 节)**:
① **正面**:被问到不确定的事时,先如实说"未实测、不下结论",**没有凭印象断言**;
② **反面**:但"本机未装 Vivado"这个前提**本身就是没核实的断言** ——
只做了一次浅搜索就下了全称否定结论,而且**自己写的 memory 里就有正确路径却没去读**。
与 LLM-012 主线的错因(「官方 XDC 里没有 ⇒ 板上没有」)**完全同型:一次不充分的搜索 → 一个全称否定结论**。
