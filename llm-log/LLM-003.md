# LLM-003: 模型把"自己的推断"说成了"赛题指南的规定",被用户一句追问戳穿

- **日期**: 2026-09-13
- **模型**: Claude Code / DeepSeek-V4-Flash(以会话环境报告为准,定稿前请用户核对)
- **任务**: 审查用户的 Vivado 工程(PS7 + AXI Quad SPI),判断用厂商 IP 实现 SPI 是否合适,并给出下一步

## 提示词

用户在看完模型对工程的审查意见后追问(原文):

```
文档有说明ip核不计入工作量吗，主要是这样做ps和pl端数据交互会不会轻松一点
```

## 模型回答

模型在上一轮审查里给出了这样一句结论:

> "它是**厂商 IP,不计入你自己的设计工作**。本赛道考察侧重是逻辑设计/状态机/接口协议,
> D14 也定了'每个模块本身就是评分对象'"

用户追问后,模型检索 `Task_Requirement/AMD赛道选题指南.pdf` 全文(3.3 节 173 行),
确认**指南通篇未提及 IP 核**,既无"不计入"的折算规则,也无任何禁用厂商 IP 的条款。
模型随后更正为:

> 用 AXI Quad SPI **不违规、不扣分**。真正的风险是考察侧重写的是"逻辑设计/状态机/接口协议",
> 而厂商 IP 把这部分遮住了:功能分照拿,但想展示的能力没地方展示。

## 结果

☐ ✅ 直接可用   ☑ ⚠️ 部分可用   ☐ ❌ 不可用

(审查结论里对工程客观状态的描述可用;涉及"评分规则"的判断不可用,已更正)

## 验证方式

- **反证检索**:`pdftotext -layout Task_Requirement/AMD赛道选题指南.pdf` 转文本后,
  在 3.3 节全文(行 825–1000)检索 `IP|IP核|知识产权|第三方|厂商` —— **零命中**
- **佐证原文**(指南确有此文,已逐句核对):
  - 3.3.1.1:「逻辑设计、状态机、时序约束、接口协议等基本 FPGA 设计能力」
  - 3.3.2:「实现方式不作限定。RTL、Vitis HLS、AI Engine、PS 侧软件及其任意组合均可」
  - 3.3.5.5 权重:创新性 30 / 性能与资源 20 / 功能正确性与设计完整性 20 / 大模型协作与技能包 15 / 文档可复现 15

## 纠错轨迹

1. **模型错在哪**:把"考察侧重是逻辑设计/状态机/接口协议"这条**真实存在**的表述,
   外推成了一条**不存在**的规则 ——「厂商 IP 不计入工作量」。而且用了文档规定的口吻陈述,
   没有标注这是推断。
2. **用户怎么发现的**:直接追问「文档有说明 ip 核不计入工作量吗」。
   —— 用户没有接受模型的结论,而是要求出示依据。
3. **怎么改的**:模型把指南 PDF 转文本,按关键词全文检索,确认零命中;
   然后区分开两件事:**"违规/扣分"**(文档没有)与**"考核点被遮蔽"**(是真实风险),
   并撤回原结论,给出修正后的两段式建议(先用 IP 打通基础设施,再换自写模块)。
4. **改完还有没有问题**:
   - 修正后的建议仍然带有模型的主观权衡,**是否采纳应由用户判断**,模型不替用户拍板
   - 同一轮回答里,模型对工程客观状态的描述(BD 零连线、无 wrapper、无 XDC、顶层未综合)
     是**只读检查得到的事实**,当时未经用户复核 —— 状态类结论仍需用户确认

## 观察:这是本项目里最有价值的一类失败

这条记录的价值不在于"模型最后答对了",而在于**失败模式很典型**:

> **把推断包装成依据。** 模型的结论往往方向不错(用厂商 IP 确实会削弱设计能力的展示),
> 但一旦把"我认为"说成"文档规定",就会让用户**基于一个不存在的前提做决策** ——
> 而且因为方向不错,用户很可能不会去查。

**有效的防线是用户这一问:「文档有说明吗?」** —— 把模型的每一条"依据"都要求出示出处。
这条防线成本极低,但能挡住整类错误。

**对模型自身的要求(已记入本项目的协作纪律)**:凡是引用评分规则、赛题条款、器件参数、
引脚时序的结论,**必须标出出处行号**;查不到就写明"这是推断,文档未规定"。
