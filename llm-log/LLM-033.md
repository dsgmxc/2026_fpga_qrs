## 模型回答

产出分两半,中间有一条**硬边界**:

**A. PS 侧 Python(编排层)** —— 新建 `src/python/` 四层:
`cv_regs.py`(寄存器/位域/面板参数的**唯一事实源**)→ `cv_monitor.py`(唯一的 mmio 层)
→ `drivers/{lcd,touch,board,ui_process}.py`(语义层,每个模块一个驱动库)
→ `main.py`(**薄装配层**,只串流程)→ `tools/{display_probe,touch_probe}.py`(独立自检)。
另固化 `Clocks.fclk0_mhz = 50`(F1 结案)。

**B. LVGL C 侧(界面层,独立进程)** —— 新建 `src/c_ui/`:
前序 LVGL 8.2.0 + `ui_demo.c` 全家桶**逐字搬**(9 个文件 md5 已核),
靠 `port/BSP/...` **路径别名树**让 `ui_demo.c` **一行不改**就能编译;
新写的只有 `app/` 下 7 个文件(`lv_conf.h` / `pynq_regs` / `pynq_disp` / `pynq_touch` /
`pynq_indev` / `pynq_protocol_stub` / `main.c`)。

**架构判断**:帧缓存**必须**由 Python 用 `pynq.allocate` 分配(走 CMA),
把**物理地址**传给 C 进程,由 C 用 `/dev/mem` mmap —— 该映射**非缓存**,
PL 读 DDR 直接看到写,**顺带把风险 D1 绕开了**。C 进程拿不到物理连续内存,
所以"Python 分配、C 消费"不是风格选择,是**唯一可行路径**。

## 纠错轨迹

> 本轮**错误密度不低**,且**多数是被"回源核对"或"跑一下"抓到的,不是目测抓到的**。
> 按价值排序。

### ① 🔴 最有价值:**一个粘滞状态位被我当成了实时故障信号**(自查,非工具)

`pynq_touch.c` 初稿写的是:只要读到 `err` 位为 1,就**每次都**返回 `LCD_TOUCH_ERROR_BUS`。

写完回头读 `gt911_ctrl.v` 才发现:**这个位的唯一清零点在 `gt911_ctrl.v:264`,即复位** ——
它回答的是"**开机以来曾经**出过错",**不是"此刻在错"**。

⇒ **后果是灾难性的且想不出症状**:上电时但凡有一次 I2C 噪声把该位置起,
**触摸就永久失效** —— 之后手指怎么按都不响应,而硬件、接线、驱动**全都正常**。
这种 bug 在演示现场是灾难,而且排查方向会被"触摸坏了"引到完全错误的地方(去量上拉、换底板)。

**修法**:加一个 `s_err_reported` 闩锁 —— 只在**第一次**看到它置起时报一次 BUS,
之后照常读正常路径。**代价写清楚**:真正的"此刻是否在错"需要 PL 提供一个可读的
**连续错误计数**,PL 目前没有,那是 RTL 改动,超出本轮范围 ⇒ 记进候选 skill。

### ② 🔴 **计划里的"错误位置"本身是错的**(回源核对抓到)

本轮的实现计划(已批准)里有一条写了:

> 🔴 纠错 1:…**文档写错了**:`docs/display_subsystem.md` §5.2 写 `0x50 LCD_CTRL … [0]src_sel`

**照着去改的时候发现:§5.2 整节根本不提 `0x50`** —— 它只列 `0x58`~`0x70` 那 7 个新寄存器。
真正过时的位置是**另外两处**:

| 位置 | 原文 | 实情 |
|---|---|---|
| `cv_axi_lite_slave.v:10`(文件头寄存器表) | `0x50 LCD_CTRL RW [0]src_sel 0=厂商彩条 / 1=PS 填充` | 字段是 `[1:0]`,缺 `2=DDR 帧缓存` |
| `cv_axi_lite_slave.v:140`(端口注释) | `// 0x50 [0]src_sel` | 同上 |
| `report/source_design_checklist.md:408` | `[0]` / `0 = 厂商彩条 / 1 = 填充` | 同上 |

**权威出处**是消费者 `cv_sys.v:289`:`wire [1:0] lcd_src_sel = cfg_lcd_ctrl[1:0];`,
且 `cv_sys.v:281-284` 已写明 `2 = DDR 帧缓存`——**`cv_sys.v` 早就改对了**,
只有从机那侧的注释没跟着改。硬件的 `lcd_ctrl` 寄存器本来就存 32 位(`lcd_ctrl <= wdata_r;`),
所以**只有注释是错的,逻辑一直是对的**。

**教训**:**"文档哪一处写错了"也是断言,动手前要回源核一次** ——
否则会出现"照计划去改,到了发现不在那儿",而如果不核对就直接翻文件找相似字样,
很可能**改到一处本来正确的地方**。⇒ 候选 `skill/plan-claim-is-also-a-claim/`。

### ④ `-std=c11` 编不过 —— **靠真跑编译抓到,不是读代码**

`pynq_regs.c` 用 `clock_gettime(CLOCK_MONOTONIC)` 与 `nanosleep`,
`cv_millis` 是 tick 的来源。用 `-std=c11` 时 gcc 报
`implicit declaration of function 'clock_gettime' / 'nanosleep'`,`CLOCK_MONOTONIC` 未定义。
根因:POSIX 接口要 `_POSIX_C_SOURCE`,而 `-std=c11` **不定义**它(严格 ISO 模式);
`-std=gnu11` 会自动带上等价的 `_DEFAULT_SOURCE`。

**处置**:Makefile 定死 `-std=gnu11`,并在文件头把这个坑的**两面**都写清
(要么 gnu11、要么显式 `-D_POSIX_C_SOURCE=200809L`,两者择一)。
⚠️ 这是个**静默隐患**:若是 `implicit declaration` 能被看到还算好的,
真正危险的是"函数被当成返回 `int` 而恰好能链上"的那种 —— 所以**必须真编一次**。

### ⑤ 前序路径别名:先怀疑"要改 `ui_demo.c`",实测不必

`ui_demo.c` 里写的是前序工程的路径(`#include "BSP/LCD/lcd_panel_config.h"` 等)。
**我最初的倾向是"改它几行 include"** —— 那样就能编,但会**破坏"与前序逐字对照"的可辩护性**
(报告里"原样搬"这句话就不成立了)。

**改选方案**:建 `port/BSP/...` **路径别名树**,Makefile 加 `-Iport`。
**结果 9 个文件字节不变、`ui_demo.c` 一行不改、编译 0 warning 通过。**
⇒ 判断依据:**"能编过"有两条路,选那条不会在报告里留下债务的**(与 B6 相关)。

### ⑧ 一处**设计取舍**的判断依据(供 B4 / B6)

**"矩形同步"用 CPU memcpy,不在 PL 里加矩形搬运器。**
`direct_mode + full_refresh=0` 时 LVGL 只重画失效区,换址后新后台是更早的帧 ⇒
必须把本次失效矩形从新前台补到新后台,否则界面会"一块块退回两帧前"。

前序 STM32 用 **DMA2D** 硬件搬;PYNQ 上没有。**可选**:自己写地址发生器 + 突发状态机,
或用 AXI CDMA。**没做**的理由:该模块**只会被 UI 用到**,主测量路径完全不需要它 ⇒
属于「以显著的资源代价换取有限的性能收益」。**先用 CPU 路径把实测数据拿到手再决定** ——
代价(1.2 MB 非缓存同步的现实耗时)写进风险 R2,由实测决定是否回头加。

### ⑨ 🔴 **首次上板第一步就挂:驱动里绑的是已不存在的顶层实例名**(用户实测暴露 + 自查二次纠错)

**现象**(用户贴回的原始输出):

```
drivers.board.BoardError: 位流里没有 `cv_axi_lite_slave_0`。
现有 IP:['cv_sys_0', 'processing_system7_0']
```

**我一开始诊断错了。** 这条报错的**建议**部分("⇒ 多半是 .bit 与 .hwh 不是同一次综合")
是我自己在 `board.py` 里写的,而它**指向了错误的方向** —— `.bit`/`.hwh` 本来就好好的。

**真因**:`cv_axi_lite_slave` 在 2026-10-01 被包进 `cv_sys.v`(`cv_sys.v` 头注释原文:
「把两边一起包进 `cv_sys`,BD 里只挂 `cv_sys` 这一个 module_ref 即可」)⇒
**顶层实例名从 `cv_axi_lite_slave_0` 变成了 `cv_sys_0`**。
RTL 改了,而 `cv_monitor.CVMonitor.bindto` 与 `drivers/board.py` 都没跟着改。

**一手证据(hwh 对撞,不是推测)**:

| 日期 | `.hwh` | 顶层 module_ref | 出处 |
|---|---|---|---|
| 09-29 | 154 543 B | `cv_axi_lite_slave_0` | `report/measurements/20260929_scratch_loopback.md:66-70,126` |
| 10-01 | 129 596 B | **`cv_sys_0`** | 仓库 `board/qrs.hwh` |
| 10-02 | 145 267 B | **`cv_sys_0`** | 工作区 `board/qrs.hwh` |

⇒ 09-29 那份 ip_dict 是真的有 `cv_axi_lite_slave_0`。**驱动是照着那天写的,之后再没对齐过。**

**🔴 二次纠错(修的时候我又错了一次)**:我第一版改成
`bindto = [f"xilinx.com:module_ref:{cv_regs.TOP_MODULE}:1.0"]`,即**从实例名推 VLNV** ⇒
拼出 `…:module_ref:cv_sys_0:1.0`,而 `.hwh` 里是 `…:module_ref:cv_sys:1.0`。
**实例名带 `_0`,VLNV 用模块名不带 —— 两者不相等、不可互推。**
这次不是读代码看出来的,是**跑了一个检查**看出来的:

```python
print(cv_monitor.CVMonitor.bindto)
# ['xilinx.com:module_ref:cv_sys_0:1.0']   ← 与 hwh 的 VLNV 不一致,当场暴露
```

**最终修法(3 文件)**:`cv_regs` 里定义**两个**常量(`TOP_MODULE` 实例名 /
`TOP_MODULE_VLNV` 模块名,相邻放置并注明不可互推);`cv_monitor.bindto` 读后者;
`board.py` 读前者,**并新增一条 `isinstance(ip, CVMonitor)` 断言** ——
因为 `bindto` 失配时 PYNQ **静默**退化成 `DefaultIP`,不报错、只是没有 `link_check()`,
这正是本轮坑的第二形态。

**离线复核(可复跑)**:用脚本把 `cv_regs` 的四个常量与**两份真实 `.hwh`** 对撞 ——
`TOP_MODULE` / `TOP_MODULE_VLNV` 均命中,且该实例的 `MEMRANGE` = `0x43C00000~0x43C00FFF`
与 `BASE_ADDR` 一致。⚠️ **这是静态对撞,不等于板上验证** —— 板上仍待用户复跑。

**教训(已提炼)**:`bindto` 这类"必须与外部产物逐字相符的字符串",**不能靠推导**,
必须在改完后**打印出来与产物对撞**。同理,报错信息里的"⇒ 多半是……"若本身没被验证过,
会把下一个人引向错误方向 —— **诊断性文字也是一种断言,也要有出处。**
