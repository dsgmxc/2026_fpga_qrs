## 模型回答

七轮交互,主线三条:

1. **PL 还是 PS?** —— 查板级 IO 分配表,确认 LCD 30 根 + 触摸 4 根**全部接在 PL 的
   BANK34/35**,PS MIO 无连接 ⇒ 时序发生器**必须**在 PL,"写 PS 端"物理上不可能。
   进而给出显示方案:**完整帧缓存 RGB888 = 1024×600×24 = 14.75 Mb > XC7Z020 全部 BRAM 4.9 Mb**
   ⇒ 必需 DDR + VDMA + PYNQ DRM;改为**曲线缓存 1024×10 bit = 10 Kb ≈ 1 块 BRAM**,
   PL 实时比较 `y == curve[x]` 描点,**省 1500 倍且不依赖 DDR**。
2. **参数三路交叉核定** —— 模块手册 DE 模式表 / 裸屏规格书 / 厂商 STM32 例程结构体
   `{45000000,1,1024,140,160,20,600,20,12,3}` 的**拆分逐项一致** ⇒
   H 20/140/1024/160 = 1344,V 3/20/600/12 = 635,PCLK 50 MHz ⇒ 刷新 58.6 Hz。
3. **例程落地** —— 修 GBK 编码 → 删冗余 → 例化 → 补 XDC → 综合 → 用户上板出彩条。

## 纠错轨迹

### 1. 🔴 **模型宣布「`.xpr` 残留引用 = 0」,这个结论是错的**（本次最重要的一条）

- **模型错在哪**:删掉 `rd_id.v` / `clk_div.v` / `lcd_rgb_colorbar.v` 后,模型用
  `grep -c <名> qrs.xpr` 查到 **0 处**,就宣布"没有悬挂引用"。
  实际上 `remove_files` 之后的 **`close_project` 并没有把改动落盘**,
  `.xpr` 里那三条 `<File Path="$PSRCDIR/sources_1/new/*.v">` **一直都在**。
- **怎么暴露的**:不是靠模型自查,而是**下一次会话里跑综合时 Vivado 自己报出来的** ——
  开工程即打 3 条 `CRITICAL WARNING: [Project 1-19] Could not find the file '…'`。
- **根因**:模型把**文本搜索**当成了**验证**。grep 只能证明"文件里没有这个字符串",
  证明不了"Vivado 加载工程后不引用这个文件"。**工具的语义边界没对齐**。
  与 `LLM-003` / `LLM-012` / `LLM-018` **同型:拿局部观察当完整结论**。
- **怎么改的**:重做一遍,并**用 md5 坐实落盘**(`4ea53826bf8c…` → `6d417373ae9c…`),
  再**重跑综合**确认那 3 条 CRITICAL WARNING 消失。
- **改完还有没有**:没有了。但教训是**这条纠错是工具替我发现的,不是我自己发现的** ——
  模型这一次没有在自己的结论上主动加"待 Vivado 回读确认"的限定词。

### 2. 🟡 **模型先过度保守、后有据自纠**（同一议题的两次表态）

- 起初模型说「厂商 FPGA 指南 V3.4 里只有 ATK-4342/4384/7084/**7016**/1018,
  **没有 MD0700R**,所以那张 ATK-7016 的时序表**不能假定适用**」。
- 随后用户把资料放进硬件资料文件夹,模型 `pdftotext` + 解压 STM32 例程后拿到 **`atk_rgblcd.c:47`**
  的结构体,发现**厂商就是复用的同一组参数**,于是**明确撤回自己上一句话**,
  并给出算术佐证(140+160+20 = 320;20+12+3 = 35,与模块手册 blanking 合计对得上)。
- **评价**:保守本身是对的(没有硬证据不硬套),但**结论停在"不能假定"就该同时给出取证路径**,
  而不是等用户把资料找来。**下次:拒绝下结论时,应一并说明"去哪里能取到证据"。**

### 3. 🟡 **模型拒绝为 MODE 脚下定论 —— 这次是对的,且事后被实测证实**

- 裸屏规格书写 `MODE` 脚 "H: DE mode; L: HSD/VSD mode",Default Status = **H**;
  模型在解压出的原理图文本层看到 `MODE` 附近有 `VCC3.3`,但**明确声明**:
  「这只是文本层的位置关系,**不是硬证据,我不下定论**」,要求用户去查 `ATK-MD0700R_V1.6.pdf`。
- **结果**:09-25 彩条上板成功 ⇒ **DE 模式判断被硬件坐实**。
  ⇒ 与第 1 条形成对照:**这次模型守住了"不下无据结论"的线,而且守对了。**

### 4. 🟡 **`get_files` 多模式语法写错**(小,记录以备考)

- 模型写 `get_files -quiet *rd_id.v *clk_div.v *lcd_rgb_colorbar.v`,
  Vivado 报 `ERROR: [Common 17-165] Too many positional options` ——
  `get_files` **只接受一个位置参数图案**。改用 `foreach` + `string match` 过滤后正常。

### 5. 🟢 **用户否决模型建议并给出理由（正面记录）**

- 模型把 `rd_id.v` / `clk_div.v` 标为「可砍」,并**额外提示** `lcd_rgb_colorbar.v` 是**竞争顶层**,
  删前两者会让它变成"缺模块"状态 ⇒ 三个文件必须一起决定,并就此**征询用户**。
- 用户选定「只留 `lcd_driver` + `lcd_display`」。
- **评价**:删除是不可逆动作,模型**先摆依赖关系再问**,没有直接动手 —— 这次流程是对的。

### 6. 🟢 **一次点亮坐实 5 个原本只是推论的决策**

彩条能出稳定图像,同时证明:① DE 模式正确(若屏实为 HV 模式,HS/VS 恒高不可能同步)
② PCLK 50 MHz 在屏窗口 40.8~67.2 MHz 内 ③ 时序 20/140/1024/160 + 3/20/600/12 正确
④ 30 根球号正确 ⑤ 硬编码 ID、砍掉 `rd_id`/`clk_div` 的方案成立。
⇒ 报告 §4.6 / **B06「设计判断依据」**的现成素材。
