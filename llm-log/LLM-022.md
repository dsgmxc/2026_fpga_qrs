# LLM-022:无网线跑通 PYNQ 2.7 —— 串口控制台路径打通;**模型给了一条粘不进串口的命令**

- **日期**: 2026-09-25
- **模型**: Claude (Claude Code)
- **任务**: 用户要在**没有千兆以太网线**的条件下开始 P2(PYNQ Overlay 骨架)。
  依次涉及:烧录 PYNQ 镜像到 SD 卡 → 找串口终端 → 板子起不来(`/dev/ttyUSB0` 不存在)
  → 板上启动 → 加载 Overlay 失败(`OSError: Root permissions required`)
  → `No Devices Found` 排障。
- **⚠️ 证据边界**:本次**所有上板操作由用户执行,模型未直接接触板子**。
  模型实际做的是:**诊断 / 给命令 / 提出根因假设 / 交叉核对资料**。
  串口输出由用户粘贴回对话,是本次唯一的实测证据来源。

## 模型回答

**先判可行性,再动手**:查正点原子《领航者 ZYNQ 之 PYNQ 开发指南 V3.2》(`pdftotext` 全文提取),
确认**网线只服务于 Jupyter 浏览器访问**,启动本身不依赖它 ⇒ **无网线走串口控制台是可行的**,
不必等网线。

随后四段排障:

1. **`/dev/ttyUSB0` 不存在** → 从 `lsusb` 有设备、但 `3-2:1.0` 接口**没有驱动绑定**、
   `ch341` refcount 为 0 这三条第一手观察出发,定位到 **`brltty` 盲文服务**:
   `/usr/lib/udev/rules.d/85-brltty.rules` 里有
   `ENV{PRODUCT}=="1a86/7523/*" … GOTO="brltty_usb_run"`,直接把 CH340 抢走。
   给出 `apt remove brltty`(先 `-s` 模拟确认无依赖级联)+ 重载 udev 规则,
   **并警告事后绝不能跑 `apt autoremove`**(brltty 挂在 `ubuntu-desktop-minimal` 的 Recommends 链上)。
2. **`OSError: Root permissions required.`** → 从调用链
   (`embedded_device.py:527` ← `MMIO(SLCR_BASE_ADDRESS)` ← `Clocks.set_pl_clk` ← `overlay.py:416 download`)
   判定这是 **`/dev/mem` 权限**问题,**不是 hwh 兼容问题**
   (整条 traceback 里没有任何 `hwh_parser` 帧)。
3. **`root的密码是多少`** → 全文检索 PYNQ 指南后如实回答:**没有任何关于 root 密码的记载**,
   不猜、不编。建议改用 `sudo`。
4. **`RuntimeError: No Devices Found`** → 提出假设:**`sudo` 会清掉环境变量,而 PYNQ 的设备探测依赖它**;
   让用户对比跑 `sudo` 与 `sudo -E`。**用户执行后证实**:`sudo -E` 成功。

## 纠错轨迹

### 1. 🔴 **模型给的多行 `python3 -c` 命令,粘进串口终端必然出错**（本次最实用的一条）

- **模型错在哪**:给了一条多行的
  `python3 -c "…\nfrom pynq import Overlay\n…"`。串口终端(minicom/tio)在**输入未闭合时进入续行模式**,
  提示符变成 `>`,而**该提示符后面的前导空格会被当成代码缩进**一起进入 Python。
  用户粘完得到 `IndentationError: unexpected indent`。
- **怎么暴露的**:用户直接粘贴了报错。
- **怎么改的**:改为**单行** `python3 -c "from pynq import Overlay; ol=Overlay('…'); print(ol.ip_dict)"`。
  模型明确说明**这不是板子的问题,是命令形式的问题**。
- **教训(可复用)**:面向**串口终端 / 交互式 shell / 无剪贴板完整性保证**的环境,
  命令必须是**单行、自闭合、不依赖续行**。这条与"多行 heredoc"同理,
  但串口的续行提示符会**静默注入缩进**,比普通终端更隐蔽。

### 2. 🟡 **一次"设备找不到"排障:模型的方向对了一半**

- 模型最初对 `Root permissions required` 的解释里,掺了一句"Jupyter 那边能跑通是因为它以 root 运行"。
- 用户改用 `sudo` 后**换成另一个错**(`No Devices Found`),才把真正的原因逼出来:
  **不是"谁在跑",而是"环境变量有没有传下去"**。
- **评价**:结论最后是对的(`sudo -E`),但中间的措辞是**未经证实的推测**,
  且**恰好把排查方向带偏了一层**。
- **正确姿态**应在第一次就区分:「确定的是 `/dev/mem` 需要权限;不确定的是 PYNQ 以何种方式取设备」,
  并把后者标成待验,而不是顺手给一个解释。

### 3. 🟢 **面对「root 的密码是多少」,模型没有编答案**（正面记录）

- 用户直接问 root 密码。全文检索官方指南后,模型回答:
  **文档里只有 xilinx 用户的密码,没有任何地方提到 root 密码** —— 如实说不确定,建议走 `sudo`。
- **为什么值得记**:这是一个**极易顺口编造**的问题(开发板默认密码有大量社区传言)。
  与 `LLM-003`(把推断说成规定)/ `LLM-012`(官方 XDC 里没有 ≠ 板上没有)形成对照:
  **这次守住了"没有出处就不给数字"的线。**

### 4. 🟡 **`brltty` 抢串口的诊断,证据链完整但未经"移除后复测"闭环**

- 诊断依据是**三条第一手观察**(udev 规则原文 / 接口无驱动绑定 / `ch341` refcount 0)
  + 官方规则文件里的匹配行,**不是猜测**。
- 但:模型**没有**在用户执行 `apt remove brltty` 之后回读一次
  `/dev/ttyUSB0` 是否出现、`dmesg` 是否出现 `ch341` 绑定 ——
  闭环是由"最终串口确实通了"**间接**完成的,**没有留下直接证据**。
