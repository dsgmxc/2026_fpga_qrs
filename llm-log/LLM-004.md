## 纠错轨迹

### 轨迹 A:模型第一轮指出的问题 —— 用户修对了 5 条

| 模型指出 | 用户修改 | 结果 |
|---|---|---|
| `cs` 多驱动 | 块1 不再赋 `cs`,只留块2 驱动 | ✅ 消除 |
| `delay_cnt` 多驱动 | 挪进块1 的 IDLE,块2 不再碰 | ✅ 消除 |
| `frame_cnt` 未在 IDLE 清零 | 块2 IDLE 加 `frame_cnt <= 0` | ✅ |
| `rx_data` 无赋值 | `DONE` 里加 `rx_data <= rx_shift` | ✅ |
| `done` 无赋值 | **删除该端口**(改用 `busy` 下降沿握手) | ✅ 合理的简化 |
| 块2 缺复位 / CPHA=0 第一位 / `DIVIDER` 死代码 / `start_r` 无边沿检测 等 | 未修 | 结转 |

前两条是**综合级错误**(同一 `reg` 两个驱动源),清除后工程才可能通过综合 —— 这是本轮最实的收益。

### 轨迹 B:用户的修改**改了表象,没动根因**

用户把 `TH` 从 `2*DATA_WIDTH` 改成 `2*DATA_WIDTH-1`,**但 `BIT_CNT_WIDTH` 没动(仍 4 bit)**。

**模型指出为什么这样改无效**,并给出完整推导:

> `bit_cnt` 是在 `DATA_R` 状态里被比较的,而 `DATA_R` **只会以偶数值进入**
> (它自身 `+1` 后经 `SCLK_TOG_T` 再 `+1`)。所以 `DATA_R` 观察到的序列是
> `0,2,4,6,8,10,12,14`,**永远看不到 15**。
> 而且在 `bit_cnt=14` 未命中后,`SCLK_TOG_T` 把它加到 16 → **4 bit 回绕成 0**,循环重新开始。
>
> **结论:改 `TH` 无效,根因是计数器位宽 —— `$clog2(2*DATA_WIDTH)` 永远够不到 `2*DATA_WIDTH`。**
> 最小修改是第 59 行改为 `$clog2(2*DATA_WIDTH + 1)`。

**观察**:这类"改了但没改对"很难自查 —— 因为改动**看似直指症状**(判据太严就放宽判据)。
真正的入口是**问"这个数在比较的那一刻,可能取到哪些值"**,而不是"判据该设多少"。

### 轨迹 C:用户的修改**新引入了一个更隐蔽的致命项**

`DONE` 状态中新增的 `if(start_r) next_state <= START;` 落进了 `if(CS_MODE)` 的 `else` 分支范围,
导致后续的 `else next_state <= IDLE;` **按"就近配对"规则绑定了 `if(start_r)` 而不是 `if(CS_MODE)`**:

```verilog
if(CS_MODE)                       // A
  if(frame_cnt >= FRAME_NUM-1)     // B
    next_state <= IDLE;
  else
    frame_cnt <= frame_cnt+1;     // ← B 的 else 只吃这一句
    if(start_r)                   // C ← 缩进骗了人
      next_state <= START;
else                              // ← 实际配的是 C
  next_state <= IDLE;
```

**后果:当 `CS_MODE=0`(默认值)时,A 分支整体被跳过 → `DONE` 里没有任何语句给 `next_state` 赋值
→ 状态机永久卡死在 `DONE`,只能发出第一帧。**

**这类 bug 的特点**:
- **缩进表达的意图是正确的** —— 用户想表达的结构没错,但 **Verilog 的 `else` 绑定不看缩进**
- 它比轨迹 B 更危险:**轨迹 B 是"没修好",轨迹 C 是"修坏了"** —— 且症状要到 1 号 bug 修好之后才暴露
  (当前状态机根本到不了 `DONE`,所以轨迹 C 暂时被掩盖了)
- 综合器不会报错,只会静默按错误方式解析

**模型的最小修改建议**:给 `if(CS_MODE)` 加 `begin/end`,并把 `if(start_r)` 移出该分支。

### 轨迹 D:模型自身的边界声明

模型在两轮审查中都明确划出**不替用户拍板的项**:

> `CPOL` / `CPHA` 具体取值必须对着 **AD9833 数据手册的时序图**确认,
> 模型拒绝对引脚时序作断言(项目中已有 LLM-003 的前车之鉴)。

## 观察与沉淀

**本轮最有价值的两条经验(都来自失败,不是成功)**

1. **"改了但没改对"**(轨迹 B):修改指向了症状而非根因。
   防线:改计数器/判据类的 bug 时,先问**"这个寄存器在比较那一刻可能取哪些值"**,
   再决定判据 —— 而不是调判据的数字。
2. **"改 A 引入 B"**(轨迹 C):修 bug 的改动本身制造了新 bug,且被上游 bug 掩盖。
   防线:**改动之后必须复核**,尤其是往已有 if/else 嵌套里插语句时 ——
   Verilog 的 `else` 就近配对是**语义与缩进背离**的经典陷阱。

**这轮也暴露了模型审查的一个固有局限**:静态阅读能找出逻辑错误,但**不能替代仿真**。
两条新结论至今未经波形验证 —— 记录里已如实标注。
