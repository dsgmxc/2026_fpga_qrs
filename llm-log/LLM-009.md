## 模型回答(要点)

### A. code ↔ 输出电压:两层关系,方向相反

用户问的是"设多少 code 对应多少伏"。模型**没有凭印象答**,而是回 TI 手册
`pdftotext -layout` 后 grep `VOUT` / `VREF` / `full.scale`,取到 Table 8 / Table 9 原表,
又翻了厂商例程 `DAC1220VolWrite()`:

| 层 | 关系 | `code=0` 对应 | 出处 |
|---|---|---|---|
| **芯片层**(DAC1220 本体) | 直通二进制 `VOUT = 2×VREF × code / 2^20` | **0 V** | Table 8 / Table 9,p14 |
| **模块层**(康威模块模拟级) | 双极性 `code = (V+10)/20 × 2^20` | **−10 V** | 例程 `mapfloat(v,-10,10,0,1048575)` |

Table 9 三行是关键判据(VREF=2.5 V 时):`0000h → 0V` / `8000h → 2.5V` / `FFFFh → 5V`。

→ **两层的 `code=0` 含义相反,按芯片式子算会整整差 10 V。**
→ 模块层是**代码级证据,不是原理图证据**(资料包内仍无模块原理图)→ 列为候选式,
   必须**三点标定**(`0x00000`/`0x80000`/`0xFFFFF` 各量一次,拟合 `V = a·code + b`)才能定稿。
→ 已写入 `docs/dac1220_interface.md` 新 **§八补**,并把原 U3 从「无法断言」改为「有候选式、待实测」。

### B. 测试台审查:6 条

| # | 级别 | 问题 |
|---|---|---|
| F1 | **编译阻断** | `reg sclk; reg mosi;` 接 DUT 的 `output wire` → `[VRFC 10-3236]` |
| F2 | 致命时序 | `CLK_PERIOD = 10`(100 MHz),而 DUT 全部常数按 50 MHz 标定 → **复位图案三个窗口破** |
| F3 | 致命逻辑 | `set_in` 上升沿被 `SETTLE_WAIT` 倒计时窗口整个吃掉 → 帧永远发不出去 |
| F4 | 测试无效 | `code` 恒为 `20'd524288`,拆出来 `40 08 00 00` —— **两个字节是 `0x00`**,等于 `cal_byte_f` 的 default,字节序错/接线漏全看不出来 |
| F5 | 验收无效 | 无 `$finish`,无任何 `$display` / 断言 |
| F6 | 会截断 | `#1000` = 1 µs,而一帧 430 µs |

F2 的判据是**算出来的手册窗口**(tXIN = 406.90 ns):

| 段 | 手册要求 | 50 MHz(20 ns/拍) | 100 MHz(10 ns/拍) |
|---|---|---|---|
| t16 | ≥ 512 tXIN = 208.3 µs | 260 µs ✓ | 130 µs ✗ |
| t17 | ≥ 10 tXIN = 4.07 µs | 10 µs ✓ | 5 µs ✓ |
| t18 | 1024–1800 tXIN = 416.7–732.4 µs | 570 µs ✓ | 285 µs ✗ |
| t19 | 2048–2400 tXIN = 833.3–976.6 µs | 900 µs ✓ | 450 µs ✗ |

**50 MHz 下四中四,100 MHz 下三破一过。**

### C. F3 的逐拍推演(改之前的原始 NORMAL_WAIT)

`init_done` 上升那一刻 `CAL_WAIT` 把 `delay_cnt <= 0` 并进 `NORMAL_WAIT`,
而 `NORMAL_WAIT` 的前 `SETTLE_WAIT` 拍**只倒计时、不看 `set_in`**:

```
拍0   init_done<=1, state<=NORMAL_WAIT, delay_cnt<=0  ← 触发脉冲在这里来
拍1   set_in_d<=1, set_in_d_d<=0  → 沿成立!  但 delay_cnt=0 < SETTLE_WAIT → 只加计数 ✗
拍2   set_in_d_d<=1               → 沿消失(单拍宽)
拍10  门开 → 查 set_in_d & !set_in_d_d = 1 & !1 = 0  ✗
拍11+ 永久如此
```

**沿在拍 1,门在拍 10 才开。** 换真实值 `SETTLE_WAIT = 1 500 000` 更糟(沿更早)。
语义上还自相矛盾:`init_done` 对外含义是"DAC 可用",上层一看到就会触发 —— 但 FSM 之后 30 ms 不理人。

## 验证方式

**这是本次的实质进展 —— 全部证据来自真实仿真,不是推演。**

工具:xsim 2025.2(用户机器 `/home/hyp/xilinx/2025.2/Vivado`),50 MHz(20 ns/拍),
**只覆写了三个毫秒级参数**(`PWR_WAIT=100` / `CAL_WAIT_T=200` / `SETTLE_WAIT=100000`),
`SPI_HALF_T` / 复位图案六段 / 字节间隔 1024 **全用真值**。

### 1. 语法与 elaboration
`xvlog` + `xelab` **零错误** —— 顺带坐实了此前"未验证"的 **`initial` → `function` 重构**
(把四张查表改为 `function` + `case`,用户转述老师意见"设计文件最好不要出现 `initial`")。

### 2. 复位图案四窗口 —— 首次由「按源码推」变成「量出来的」

| 项 | 实测 | 手册要求 |
|---|---|---|
| t16 | **260.02 µs** | ≥ 208.3 µs ✓ |
| t17 | **10.02 µs** | ≥ 4.07 µs ✓ |
| t18 | **570.02 µs** | 416.7–732.4 µs ✓ |
| t19 | **900.02 µs** | 833.3–976.6 µs ✓ |
| `dac_cs` | 复位后恒为 0 | 恒低 ✓ |

### 3. 9 个字节位序 — **NORMAL 的 4 个字节第一次被真的验了**

在 SCLK 下降沿采样 `dac_mosi`,实测:

```
实测: 24 20 A0 05 A1 40 01 23 50
期望: 24 20 A0 05 A1 40 01 23 50   ✅ 完全一致
```

`40 01 23 50` = DIR 命令 + `code=20'h12345` 的三字节;`init_done` 实测 **2349.93 µs**。

### 4. A/B —— 死锁复现 + 修复成立

同一激励:**触发脉冲打在 2400 µs**(`init_done` 后 50 µs,而门要到 4349.93 µs 才开),
**全程只有一个沿**。`init_done` 两版都在 2349.93 µs(差别只有触发处理)。

| | SCLK 上升沿总数 | 2400 µs 后 MOSI 跳变 | 结论 |
|---|---|---|---|
| **旧版** | 40 = **5 字节** | **0 次** | 校准发完就永久静默,**帧一帧没出去** |
| **新版** | 72 = **9 字节** | 13 次 | 帧在 **4350.03 µs** 准时发出(= `init_done` + `SETTLE_WAIT`) |

**F3 死锁复现,方案 A 修复成立。**

### 5. 局限(必须随结论一起引用)
- 验证用的是 **`/tmp` 下的 force 脚本**(`add_force` + `open_vcd`),**不是**用户的 `tb_dac_1220.v`
- 三个毫秒级参数被压缩 → **"等多久"没验**;验的是协议层与状态机转移
- **仍未综合、未做时序分析、未上板** → **M13 仍无证据**

## 纠错轨迹

### 1. 模型自己的第一跑没复现自己声称的死锁(自查发现)

第一轮 `dump.vcd` 跑完,帧**正常发出了**。但模型立刻意识到:**这不是反例** ——
那一跑的 `set_in` 脉冲打在 `init_done` 之后 **650 µs**,而门早在 2 µs 后就开了。
**脉冲压根没落进声称会失败的那个窗口里。**

> → **那一跑对 F3 这个结论的信息量为零。** 重做:把 `SETTLE_WAIT` 提到 100000 拍(2 ms),
>   脉冲改到 `init_done` 后 50 µs —— 这才真正落进窗口内部。
>
> **教训:验证脚本必须显式落在"你声称会失败"的那个条件下,否则"通过了"什么也证明不了。**
> 与 LLM-005 那条"不先证明测试会失败,测试通过就没有信息量"同源,但这次是**模型自己抓住的**。

### 2. 模型的 VCD 解码器错位(自查发现)

第一次解码得到 `02 42 0A 00 5A 14 00 12 35`,与期望 `24 20 A0 05 A1 40 01 23 50` 不符,
模型一度报"❌ 不一致"。复核后定位:**是解码器把复位图案的 3 个下降沿和 `$dumpvars` 的初值
也当成了采样点,多出 4 个前导 bit。**

去掉这 4 个样本后**逐 bit 完全一致**。**RTL 没问题,是量具错了。**

> → 与 LLM-005 那两条 `sed` 静默失配同类:**读数工具本身要先自证**。

### 3. 用户自纠两次(§6.0 分工如常)
模型指出 F1 后,用户**自己**改了 `mosi`,漏掉 `sclk` → 再报"仿真启动又失败了" → 补上后跑通。
全程模型只指出、未代改。

## 沉淀

→ **新候选 `skill/testbench-timebase-must-match-dut/`** ——
  测试台的时钟周期、参数覆写范围必须与被测时序常数的标定基准一致。
  本次 `CLK_PERIOD = 10`(100 MHz)把 50 MHz 标定的全部协议常数在真实时间上减半,
  且**仿真照样"跑通"** —— 属于"能跑但测的不是真东西"。

→ **新候选 `skill/verify-the-verifier/`** —— 本次两条自身教训合流:
  ① 验证条件没落在声称的失败窗口里 → 那一跑零信息量
  ② 解码器把非采样点也算进去 → 误报 RTL 错
  **共同点:在相信"通过/不通过"之前,先证明量具本身可信。**
  与 LLM-005 的 `sed` 静默失配是同一条,本次补上两个新样本。

→ **扩展候选 `skill/intent-vs-code-mismatch/`**(LLM-008 提出)—— 本次 F3 是新形态:
  **模型把"新建状态的首次进入"漏在了轮询设计之外**。
  用户明示意图是"饱和轮询、单拍宽的沿必被抓到"(LLM-008 §4),但
  **进 `NORMAL_WAIT` 时那个建立窗口不受这条保护** —— 意图与实现在**另一条路径上**又对不上了。

→ **扩展候选 `skill/one-signal-one-meaning/`**(LLM-007 提出)—— **第二次实证**:
  LLM-007 是 `init_done` 兼作 SCLK 选择,本次是 `init_done` 的"可用"语义
  与"能接受触发"的实际状态**差 30 ms**。同一个信号,第二次栽在同类问题上。

→ **`skill/datasheet-to-rtl-constants/` 补一条**:"设多少码对应多少伏"这类换算
  **必须回手册取传递函数表**,并且**先分清是哪一层的传递函数**(芯片本体 / 模块模拟级)。
  本次两层的 `code=0` 含义相反,差 10 V。
