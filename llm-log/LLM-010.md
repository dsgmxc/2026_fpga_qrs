## 模型回答

摘要:核对 TI SBAS082G 手册 + 两份厂商 STM32 例程(核心 `DAC1220.c` 完全相同)后逐条判定 ——

| 差异项 | 判定 |
|---|---|
| 校准 `04 00 05 A1` vs 本项目 `24 20 A0 05 A1` | ✅ 等价(多字节命令,决策 D19) |
| CMR 高字节 `0x20`(本项目)vs `0x00`(例程) | ✅ **本项目对** —— Table 13 bit13「Write '1' to this bit」;p17 明写早期版本该位可写、写 0 非最优 |
| 例程校准后多发一次 `05 A0` | ✅ 可以不发 —— MD 位说明「After the sequence is complete, the DAC1220 switches to Normal mode」 |
| **DIR 三字节切片** | 🔴 **错**:`code[19:16]/code[15:8]` 应为 `code[19:12]/code[11:4]` |

手册依据(p14 原文):「The DIR is 24 bits wide, and the code stored in it is **left justified**,
with the least significant bits ignored.」+ Table 9 算例(`code=80000h` → `DIR=80000xh`)
+ 例程 `dat<<4` 后取 `23:16 / 15:8 / 7:0`。三处互相印证。

影响:`code[11:4]` 这 8 位被整个丢弃 → 有效码值 = `code & ~20'h0FF0`,
最大偏差 4080 码 ≈ **0.39% 满量程**,有效分辨率从 20 位掉到 ~12 位。
输出仍然单调 → **光看电压表很难发现**。

## 纠错轨迹

1. **【最核心的一条】模型上一轮(LLM-009)把判据建在了被测物自己身上。**
   09-18 那轮的判据 ④ 写的是「NORMAL 发出去的 4 个字节是不是
   `0x40`/`code[19:16]`/`code[15:8]`/`{code[3:0],4'b0}`」——
   **这串期望值是从 RTL 里抄的,不是从手册推的**,所以「波形与表一致」是**恒真**的,
   仿真通过**不含任何信息**。这次一查手册,发现**判据本身就是错的**。
   与 LLM-005 的 `sed` 静默失配(制造出恒 PASS 的空转负测试)**同源**:
   **判据的来源必须独立于被测物。**
2. **用户直觉对、模型复查结论错。** 用户说「我感觉我发送的字节和别人的例程好像不太一样」,
   而模型上一轮刚宣布「9 字节位序逐字节一致」。**用户的怀疑是对的** ——
   一致的是"字节与 RTL 自洽",不是"字节与手册一致"。
   教训:**"和我的实现一致"永远不能作为"正确"的证据。**
3. **模型自查出的三处量具错(全部由"真的跑一遍"暴露,静态看代码看不出来)**:
   - ① **`t17` 测量错位**:第 1 个 SCLK 沿其实是「复位图案之前那段空闲低电平」的结束,
     被当成了 `t17`(实测 20.22 µs),真正的 t17 被挤到 `l_w[1]`;且第 3 个低段写到了
     **`l_w[2]` —— 数组只开到 `[0:1]`,越界写**。→ 改为「从第 2 个沿起记录」+ 加边界保护。
   - ② **SCLK 半周期期望值写错**:期望填了 512,实测 256。因为量的是「上一个沿到本沿」
     = **半个**周期(相邻下降沿之间才是整周期)→ **期望值错,不是 RTL 错**。
   - ③ **`t14` 在下降沿分支也记了一次**,把 256 拍的噪声混进最小值,
     真正的字节间隔 1791 拍(35.82 µs)被掩盖 → 挪到上升沿分支后才量出来。
   - ④ 附带:`chk()` 的**中文标签经 task 端口传给 xsim 后被打成 U+FFFD**
     (`PASS | DIR = code << ��������`),而同一批中文写在 `$display` 字面量里显示正常
     → 判据标签改纯英文,报告正文仍保留中文。
4. **模型一处影响量级算错并自查更正**:第一次推影响时把结果估成「1/16 满量程」,
   重算后确认正确值是「丢弃 `code[11:4]` → 最大偏差 0.39% FS」。**已按更正后的数字写进上表。**
5. **模型的第一次对照差点把"例程写 0"当成正确答案**:例程 CMR 高字节写 `0x00`,
   本项目写 `0x20`。若不查手册,很容易判成"用户写错了"。回手册 Table 13 才发现
   **bit13 明确要求写 '1',是例程写的 0 不合规**。→ 与 LLM-006「例程是"能跑"的证据,
   不是"合规"的证据」同向,本次是**同一结论的第二个实例**。
