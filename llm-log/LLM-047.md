## 模型回答

1. **上板验收**:新实例起起来后,「系统复位」页三行控件 + 状态行 + 复位按钮全部工作。
   寄存器侧逐位核对通过(见「验证方式」)。
2. **误判更正**:模型先前断言"触摸链路已死"(依据:盯 `0x68` 75 s 零变化),
   **该结论错误**。真实情况:`err` 粘滞位是上电首次 I2C 事务留下的历史标志,
   `seq` 不涨只是因为**没人碰屏**。日志显示 `seq` 已到 71、`按下/抬起` 成对出现、
   坐标合理、每次点击都正确写了 `0x80`。模型自行推翻并更正。
3. **缺陷一(字库吞字)**:LVGL 点阵字库是 `lv_font_conv` 用 `--symbols` **白名单**生成的
   (260 字)。新加的文案里「样 / 相 / 率 / 居 / 中」等 252 个字不在白名单里 ⇒
   屏上被**静默吞掉**,状态行渲染成「激励 0.100MHz **采** 10.00MSPS(DIV13) **位** -2」。
   经用户决策后**重建字库**(260 → 510 字),已复现性验证 + 上板确认。
4. **缺陷二(复位后高亮不同步)**:由**用户**发现。`DisplayProtocol_RequestReset()` 同步复位了
   参数并刷了状态行,但**没有重算按钮高亮** ⇒ 出现"状态行写 10.00MSPS、采样率那行却还亮着
   5MSPS"的自相矛盾。修复 = 在复位确认回调里补一次 `UI_UpdateInitConfigStyle()`(4 行)。

## 纠错轨迹

<!-- 这一节是评分重点 -->

1. **❌ 模型把"没人碰屏"判成了"触摸链路已死"**
   依据是盯 `0x68` 75 s 零变化 + 一个 `err=1` 的粘滞位。模型据此写了
   「🔴 全程零变化 —— 触摸链路不通」,并开始深挖 `gt911_ctrl.v` 的
   `S_ERR/S_RECOV` 状态与 I2C 时钟拉伸处理,**准备改 RTL**。

2. **怎么发现的**:取 `/var/log/qrs-ui.log` 时看到
   `seq` 已经涨到 71、`[touch] 按下 (751,443) 点数 1` 成对出现、
   每次点击都跟着一行 `[mc] 激励 → …`。**链路一直是好的。**

3. **错在哪(根因)**:
   - `err` 是**粘滞**位(`0x68[4]`,只有重配 PL 才清),日志里明确记着它是
     上电首次事务 `0x68=0x00000110` 时置起的 —— **历史累计,不代表当前状态**。
     探针自己的注释也写了这一点,模型读到了却没往这个方向想。
   - **"零变化"是个二值问法用错了场合**:它只能证明"这段时间没有新帧",
     不能区分"没人碰"和"碰了没反应"。正确做法是**先制造输入再观测**,
     或者直接看日志里有没有 `按下` 行 —— 而不是在无人操作的窗口里等。

4. **改完还有没有问题**:无。更正后 `gt911_ctrl.v` 一行未动,
   反而避免了一次基于错误前提的 RTL 改动。

5. **另一处自相矛盾(模型自己的文件里)**:
   `measure_config.c` 的文件头注释写着窗应为 `[−4,+1]`,而代码算的是 `[−6,+6]` ——
   注释与代码相反。模型按 `adc_capture.v:238` 的**寄存器合法范围**写了守卫,
   但真正的**数据稳定窗**是另一个更窄的区间。两者越界后果不同:
   - 超出合法范围 ⇒ 永不命中,**失败方向安全**
   - 在合法范围内但不稳 ⇒ **采到垃圾值且不报错**
   守卫必须用**窄**的那个。已在全部 254 个 DIV 值上自检,确认窗包含自身中心。

6. **一处只在实屏上才暴露的缺陷,靠"客观看屏"而非人眼发现**:
   模型先在代码层反复推理"文案应该没问题",直到写出 `fb_dump.py`
   —— 直接读 DDR 帧缓存的像素 —— 才**看见**字真的缺了。
   **代码层查不出来的,就不要继续在代码层查。**

## 沉淀

→ 新候选 `skill/fixed-glyph-font-is-a-whitelist/`
   点阵字库是**白名单**,不是"缺字自动回退"。给界面加文案前必须先查字表;
   被吞的字**不报错、不留日志**,只在屏上少一个字。查表的判定规则(实测坐实):
   `unicode_list[i]` 存的是 `码点 − cmap.range_start`(`SPARSE_TINY`),
   本文档记录的 20 px 字库 `range_start = 937`(U+03A9 Ω)。

→ 新候选 `skill/dump-the-framebuffer-to-see-the-screen/`
   帧缓存在 DDR ⇒ 拿 `/dev/mem` 按物理地址映射就能读到**正在显示的那一帧**。
   让"屏上到底是什么"变成可自动化比对的数据,而不是等人拍照。
   本会话据此断言了三个缺陷,每个都精确到像素。

→ 新候选 `skill/hot-swap-userspace-without-reloading-bitstream/`
   PL 有自由运行的 AXI 主设备时,一个上电周期只能加载一次位流。
   换用户态程序的做法:**`SIGSTOP` 持有 `Overlay()` 的父进程** → 停旧程序 →
   构建到临时名字 → 起新程序。父进程冻住就不会发现子进程已死、不会退出去
   释放帧缓存。旧二进制留一份,失败可回退。本会话据此完成了 3 轮
   "改 → 编 → 换 → 截屏验证" 循环,位流一次没重下。

→ 扩展 `skill/verify-claims-not-intuition/`
   **"窗口内零变化"不等于"功能故障"** —— 它只说明这段时间没有新事件。
   二值问法必须配对"先造输入再观测",否则会把"没人操作"读成"坏了"。

## 附:字库重建的完整可复现命令

> ⚠️ 现有仓库里这两张字库的生成命令**只存在于文件头的注释里**,没有脚本。
> 下面是把注释补成可执行步骤的版本。源字体不在仓库里(16 MB),
> 由系统 Noto 包现拆。

```bash
# 1) 从系统 Noto 字体集合里拆出 SC 面(第 2 面 = Noto Sans CJK SC)
python3 -c "
from fontTools.ttLib import TTCollection
c = TTCollection('/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc')
c.fonts[2].save('/tmp/NotoSansCJKsc-Regular.otf')"

# 2) 取符号集 = 原白名单 ∪ 源码里所有字符串字面量里的非 ASCII 字(去掉 OTF 没有的)
#    (脚本见本次交互;产出 /tmp/symbols_final.txt,588 字)

# 3) 生成(参数逐字复刻原文件头)
npm install --prefix /tmp/lvfc lv_font_conv@1.5.2
for S in 20 28; do
  /tmp/lvfc/node_modules/.bin/lv_font_conv \
    --font /tmp/NotoSansCJKsc-Regular.otf --size $S --bpp 4 --format lvgl \
    -r 0x20-0x7E --symbols "$(cat /tmp/symbols_final.txt)" \
    --no-compress --no-kerning --lv-include lvgl.h \
    -o ui/ui_font_cn_$S.c
done
```

**注意**:`-o` 的文件名会反推 `#ifndef UI_FONT_CN_xx` 这个守卫宏名,
输出到别的名字会让守卫名跟着变 ⇒ 必须直接输出成目标文件名。

**已知差异**:不同 FreeType 版本的光栅化舍入会有几处半字节差异(本次 5 处),
不影响字形几何。字库从 260 字涨到 510 字,二进制 +131 KB。
