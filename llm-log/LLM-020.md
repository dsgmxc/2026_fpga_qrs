## 一、回一手出处核出的 5 条(不采信二手转述)

模型**没有**照 `备赛要点.md`(二手提炼)转述,而是用
`pdftotext -layout Task_Requirement/AMD赛道选题指南.pdf` 取出原文后逐条核对:

| 条款 | 出处 | 原文要求 |
|---|---|---|
| **命名** | **3.3.5.4**(p21) | 「仓库内所有目录名与文件名须使用纯英文(小写字母、数字、下划线或连字符),不得出现中文、空格或特殊字符……中文只出现在文件的正文内容中」 |
| **目录结构** | **3.3.5.4**(p21) | 推荐 8 项;**「非强制」**,采用其他组织方式的队伍**须在 README.md 中给出目录对照说明** |
| **开源** | **3.3.3.3**(p20) | 「强烈要求在 GitHub 或 Gitee 上开源,采用允许再分发的开源协议,推荐 MIT 或 Apache-2.0」 |
| **工程包 5 项** | **3.3.5.1**(p21) | 源码 / 仿真验证结果 / 综合与实现报告 / 上板工程+运行脚本+实测输出与比对 / 可复现构建脚本 |
| **声明型号** | **3.3.3.2**(p20) | 「两组均须在提交物中**声明具体型号**」 |

⚠️ 二手 `备赛要点.md` 与原文**无实质冲突**,但有一处细节是模型读原文才注意到的:
3.3.5.4 明确写着**推荐结构「非强制」**,而"必须写目录对照说明"是**采用其他结构时**的附加义务。
这决定了本项目多一个 `docs/` **不需要改结构,只需要在 README 里说明**。

## 二、🔴 模型被否决并撤回的一处建议(本次最有价值的一段)

模型在审计完两个目录后,给出的建议是:

> 「**`.git` 并到有内容的那个目录**」——
> `mv qrs_fpga_2026/.git qrs_2026_fpga/.git`,理由是"内容在一个里、git 在另一个里,
> 这是改错目录的标准事故现场",并推荐"并掉空壳目录"。

**用户的纠正:**

> 「**这个文件夹是你工作的地方,那个文件夹才是仓库真正的位置**,但是那里的东西
> 我准备自己把关,**你不要写到那里除非我要求的**」

⇒ 模型**撤回了该建议**。真实布局是**有意的分工**:

| 目录 | 角色 | 归谁写 |
|---|---|---|
| `~/Desktop/qrs_2026_fpga/` | **模型的工作区**(状态文档 / LLM 记录 / 审查材料) | 模型 |
| `~/Desktop/qrs_fpga_2026/` | **交付仓库**(带 `.git`,推到 Gitee) | **用户**,模型须经点名才可写入 |

**错在哪**:模型把"两个名字很像的目录"直接判成了一次命名事故,
**只看了目录名与 `.git` 的位置,没有先问一句"这是不是有意分开的"**。
与 `LLM-003`(把推断说成规定)、`LLM-018`(把推断说成一手依据)**同型:
都是拿局部观察当成完整结论**。

**可写进报告的一点**:这次是**在造成任何破坏之前**被用户拦下的 ——
建议只停留在文字上,没有执行 `mv`。**教训是"跨目录的破坏性操作,给建议前先确认布局意图"。**

## 三、首次提交前的三条事前拦截

模型在用户执行 `git push` **之前**提出检查项,结果如下:

| # | 拦截项 | 结果 |
|---|---|---|
| ① | **空的 `.gitignore` + `git add -A` 会把 `xsim.dir/`、`.Xil/`、`*.jou` 一起收进首次提交**(而首次提交永久留档) | ✅ **生效** —— 用户在 commit 前填了 `.gitignore` |
| ② | **`git config user.name` / `user.email` 均未配置** ⇒ `git commit` 会失败或用脏身份 | ✅ **生效** —— 用户随即配置(`hyp` / 邮箱) |
| ③ | **Gitee 建仓若勾了「初始化仓库」,远端就非空**,`git push` 会被拒(non-fast-forward) | ⚠️ **多虑了** —— 实际 push 成功(`* [new branch] master -> master`),说明远端是真空 |

⇒ ① ② 是**真拦截**(省掉一次重做历史 / 一次提交失败);
③ **零成本但事后看不需要** —— **如实记下,不包装成"三次命中"**。

## 四、`docs/` 与命名:一处**被用户决策自动消解**的问题

模型在审计工作区时发现**两个中文文件名**:
`Task_Requirement/自主选题赛道-初级组-备赛要点.md`、`Task_Requirement/AMD赛道选题指南.pdf`,
并按 3.3.5.4 判为**硬性违规**。

⚠️ **但这两个文件在**工作区**,不在交付仓库。** 用户随后拍板
「**task_requirement/(赛题资料)不要**进交付仓库」⇒ **该违规自动消解**,
交付仓库从未包含过任何非 ASCII 文件名(最终核验:**0 个**)。

📌 **但仍留一条前置条件**:若将来要随仓库提交赛题资料,**必须先改英文名再拷**,
不能直接拷进去 —— 一旦提交,中文名会**永久留在 git 历史里**,改工作区文件名也删不掉。

用户另外拍板:**`CLAUDE.md` 不进交付仓库**。

模型未写入。

### 🔑 `.gitignore` 的一处**有意改动**(可提炼的技术判断)

工作区那版用 **`*.log` 全局忽略 + `!sim/logs/*.log` 补例外**。
交付仓库这版**改成逐个文件名列出,不做全局 `*.log`**:

> 理由:全局通配符 + 补例外的模式**会静默吞证据**。
> 工作区已经因此丢过一次(`sim/logs/` 下 M02 的 8 份原始日志);
> 交付仓库里 log 会出现在**更多地方**(`sim/logs/`、`build/` 下 Vivado 的 `runme.log`),
> **补一次漏一次**。多写几行换"证据不会被安静吞掉"。

⚠️ **本条是设计判断,不是实测结论** —— 模型**没有真的跑过 `git add` 去验证两种写法**,
依据是工作区那次已记录的踩坑。

## 纠错轨迹

1. **出错**:模型把「两个目录名近似 + `.git` 在空目录里」判成命名事故,建议 `mv .git` 合并。
2. **怎么发现的**:用户直接说明这是**有意分工** —— 一个是模型工作区,一个是交付仓库。
3. **怎么改的**:模型**撤回建议**,并确认新的写入纪律:
   **交付仓库里一律不写,除非用户点名**。
4. **改完还有没有问题**:有 —— **分工边界目前只在对话里,没进 `CLAUDE.md`**,
   下次会话如果不记得,可能又往交付仓库里写。**已列入待办**。

## 沉淀

→ 候选 `skill/repo-first-commit-audit/`
   —— 首次提交前的固定审计动作:① 文件名非 ASCII 扫描 ② `git add -An` dry-run 看清单
   ③ 确认 `.gitignore` 非空 ④ 确认 `user.name/email` 已配。
   **依据是一条不可逆性**:首次提交永久留档,文件名/大文件进历史后**改工作区也删不掉**。

→ 候选 `skill/glob-ignore-swallows-evidence/`
   —— `*.log` 这类全局忽略 + 补例外的写法,在仓库长大后会**静默吞掉证据**;
   宁可逐个文件名列出。与 `skill/verify-the-verifier/`(量具也会错)同源。

→ **扩展 `skill/zero-cost-elimination-first/`** —— 本次新增一个反面样本:
   模型对局部的观察(目录名像 / `.git` 位置)**直接升级成结论**,而没有先确认意图。
