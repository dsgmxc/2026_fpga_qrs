# LLM-013:AD9833 上板前接口规格核定 + **模型低估了「改共享模块」的耦合面**

- **日期**: 2026-09-20
- **模型**: Claude (Claude Code)
- **任务**: 承接上一轮(解除「AD9833 手册待核」阻塞项),本次要定下 AD9833 的
  **SPI 例化参数、初始化帧序列、复位流程与上电顺序**,并评估一处拟改的 `spi_master.v` 改动。
  **本会话用户未写任何代码**,产出全部是规格与审查意见。

## 提示词

```
① SPI_HALF_T和CS_SETUP填多少
② 那我干脆例化两个spi一个把80位发完一个正常发数据
③ 你不是说分五帧要修改模块吗,但是我这个模块还要给dac用不好改啊      ← 关键
④ 方案A的参数设置是什么
⑤ 现在告诉我大流程,就是复位完就可以正常工作了吗还是要校准什么的
⑥ 现在向我简述复位流程
⑦ 我是说ad9833的复位流程
```

## 模型回答

1. **②③ 的作答(核心)**:一次 `start` = 一帧 16 位,`cs` 自动分帧 ⇒ **分帧零改动**;
   手册 p13 原文「**或者**,FSYNC 可以在 16 倍数个 SCLK 脉冲期间保持低电平」⇒
   80 位连续流只是**可选项**,不是必需;两个实例驱动同一组推挽输出会**打架**(需 3 个 mux)。
2. **④ 的作答**:`CPOL=1 / CPHA=0 / DATA_WIDTH=16 / MSB_FIRST=1 / SPI_HALF_T=256 /
   CS_SETUP=1000`;4 帧初始化 `0x2100 → 0x570A → 0x428F → 0x2000`(64 位,非 80 位)。
3. **⑤⑦ 的作答**:三种「校准」分层(AD9833 无需 / DAC1220 内部自校准 600 ms /
   系统 OPEN-SHORT-LOAD);AD9833 复位 = 写 D8,无最短保持时间,释放后 7~8 个 MCLK 出波形。
4. **给出一条建议**:AD9833 的 init 应复用在 DAC1220 的 `PWR_WAIT`(200 ms)之后 ——
   依据 p13「mode 位之外的所有控制位均在 **MCLK 的内部下降沿**采样」⇒ 板载 25 MHz 晶振未起振时写了不生效。

## 纠错轨迹

### ① 模型说改动「零风险」——只看了一侧(用户戳破)

1. **模型错在哪**:提出 t8 收尾时序偏离后,模型写道「**反过来说,这个改动本身零风险**」。
   这个判断**只考察了 AD9833 那一侧**——ROI 上"早收尾 25 ns"确实无害。
2. **用户怎么发现的**:用户没有接受这个前提,而是直接指出
   「**我这个模块还要给 dac 用不好改啊**」—— 一句话点出该模块是**被多处例化的共享模块**。
3. **怎么改的**:模型回去追 `dac_1220.v`,逐项列耦合面:
   - `cs` → **无影响**(`dac_1220.v:66` 是 `.cs ()`,DAC1220 那份**根本没接**)
   - SCLK 边沿 → **无影响**(早退发生在第 32 个沿**之后**,边沿一个不少)
   - `done` / `busy` → ✅ **有影响**:`dac_1220.v:288` 的 `DELAY` 状态是**从 `done` 起算 1024 拍**,
     早退会使 `done` 提前 256 拍 ⇒ 字间间隔 **35.8 µs → 30.7 µs**
4. **改完还有没有问题**:结论从「零风险」改判为「**你的顾虑成立,直接改不合适**」,
   建议从「改」改为「**先别改**」(方案 A)。**用户采纳方案 A。**
   → 这条是本次会话最有价值的记录:**模型的"零风险"结论在用户一句反问后就被推翻**。

### ② 模型上一轮把「连续流」说死了 —— 本次自我更正

上一轮(未成文)模型说「**用这份 `spi_master` 就必须分帧**…没法把 FSYNC 连续压低 80 拍」。
这话只对 `DATA_WIDTH=16` 成立。本次查证后发现:**把 `DATA_WIDTH` 设为 80 时,
`cs` 从 START 一直低到 DONE,恰好就是手册说的连续流模式**,不需要第二个模块。
已在 ② 的作答里主动更正,并补了位宽核算(`BIT_CNT_WIDTH = $clog2(161) = 8`,`TH = 160` 装得下)。

### ③ 模型照抄的厂商序列是错的 —— 本次读源码改正

上一轮记录里模型把厂商初始化序列写成 **5 个字** `0x2100 → 0x570A → 0x428F → 0xC000 → 0x2000`。
本次实际读 `AD9833_Init()` / `AD9833_SetFrequency()` 源码,发现厂商真实顺序是
**4 个字** `0x0100 → 0x2000 → 0x570A → 0x428F`,且 **`SetFrequencyQuick()` 从不调用 `ClearReset()`** ——
RESET 位是被帧 2 写 `0x2000` 时**顺带清掉**的。由此看出厂商代码真正的坑:
**频率寄存器是在 RESET 已释放之后才装的**,中间有一段输出垃圾频率的窗口。
→ 这是本记录里唯一一处**"模型引用二手结论、回头读一手源码才发现抄错"**的样本。

### ④ 用户未采纳 / 未决的部分

- 模型建议「把 AD9833 的 init 挂在 DAC1220 的 `PWR_WAIT` 之后」—— **用户尚未表态**。
- 模型建议「定一条上电顺序决策(AD9833 一出波形就在加激励,DAC 还要 ~800 ms 才可用)」
  —— **用户尚未表态**,拟进决策表(接 D21)。
