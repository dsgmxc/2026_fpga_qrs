# LLM-043: DAC 输出恒 −10 V 的根因 —— 「初始化跑在了错误的频率上」

- **日期**: 2026-10-05
- **模型**: Claude
- **任务**: 用户说「我设置偏压开始测量开始扫压都点了,`dac` 输出一直是 −10 V」。
  排查后确认**不是接线、不是位流、不是界面**问题,而是 `dac_1220` 的
  **复位图案跑在了 PS FCLK0 上,而它开机是 27.778 MHz** ——
  三段高电平全部**超出手册的双向窗口上界** ⇒ 复位根本不触发 ⇒ 输出停在芯片默认的 −10 V。
- ⭐ 本轮最有价值的一条:**这个 bug 的藏身处就是我们自己写的那段"这里有影响"的注释** ——
  `cv_sys.v` §7 原本明确断言 27.78 MHz 对这里「没有影响」,**断言是错的**。

## 模型回答

### 1. 先排除接线 —— 用户已经说过了

用户上一轮已口头给出引脚对应(`sclk=W15` / `sdio=Y14` / `cs=W13`),
模型**又去核对了一遍**,被用户纠正。引脚本身**不是**本轮故障源。
(教训:`skill/board-pin-lookup/` 已有的规则 —— 用户给了就不要再查一遍。)

### 2. 根因

`dac_1220.v` 的复位图案常数(`13000 / 500 / 28500 / 500 / 45000 / 500` 拍)
是**按 50 MHz 折算**的。但该模块的 `clk` 接的是 **`s_axi_aclk` = PS FCLK0**,
而板上 `BOOT.BIN` 把 FCLK0 留在 **27.7778 MHz**(2026-10-03 已实测)。

```
t16 = 13000 拍 @27.78 MHz =  468 µs   手册窗口 [208.3, 325.5]  ← 超上界
t18 = 28500 拍 @27.78 MHz = 1026 µs   手册窗口 [416.7, 732.4]  ← 超上界
t19 = 45000 拍 @27.78 MHz = 1620 µs   手册窗口 [833.3, 976.6]  ← 超上界
```

数据手册 Figure 12 / Table 5 的这三段是**双向窗口**:低位不到复位不完整,
**高位超上界则复位彻底不触发**。⇒ CMR 配置被忽略、自校准被忽略、
DIR 写入永不生效 ⇒ 输出 = 芯片上电默认 DIR=0 = **−10 V**。

**为什么 09-19 那次是好的**:旧的顶层 `qrs.v` 用的是 `clk_wiz_0` 出来的**固定 50 MHz**。
换到 `cv_sys` 顶层之后,DAC 的时钟变成了 PS FCLK0 —— **改动是静默的**。

### 3. 为什么不能"把常数改小一点"

把三段折成**拍数**,两个频率下的合法区间**三段全都不重叠**:

| | @27.78 MHz | @50 MHz |
|---|---|---|
| t16 | 5786 ~ 9042 | 10415 ~ 16275 |
| t18 | 11575 ~ 20344 | 20835 ~ 36620 |
| t19 | 23147 ~ 27128 | 41665 ~ 48830 |

⇒ **不存在一组常数同时覆盖两个频率**。所以修法只能是:
**保证初始化在正确的频率上跑**,而不是调常数。

### 4. 修法

新增 `0x84 CV_CTRL`(**复位值 0**),`dac_1220.rst_n` 从直连 `s_axi_aresetn`
改为 `s_axi_aresetn & cfg_dac_rst_n`:

| 文件 | 改动 |
|---|---|
| `cv_axi_lite_slave.v` | 新寄存器 `0x84`(idx `6'h21`),`{31'b0, wdata_r[0]}` **掩码后存**,读回即生效值 |
| `cv_sys.v` | `rst_n(s_axi_aresetn & cfg_dac_rst_n)` |
| `drivers/board.py` | 新增 `release_dac()`:**量出的 FCLK0 不在 [46.1, 54.0] MHz 就拒绝放行** |
| `main.py` | `apply_fclk0()` 之后调用,且**放在 `--no-clocks` 分支外**(否则绕过闸门) |
| `cv_monitor.py` | 加 `dac_rst_held()` / `dac_release()` 两个薄访问器 |
| `pynq_protocol.c` | **只读不写**;偏压码发出时若还没放行,打一条醒目警告 |

**窗口 [46.1, 54.0] MHz** 是三个双向窗口取交集反解出来的,最紧的是 t19。

**顺带好处**:放行前写进 `0x14` 的偏压码**不会丢** ——
`set_in` 只在 `NORMAL_WAIT` 锁存,被闸住时那一拍确实被丢掉,
但寄存器值留着,放行后从机侧的上电脉冲会拿**当前** code 补发一次。

### 5. 顺序依赖(踩过一次)

放行**必须在 `apply_fclk0()` 之后** —— 这两件事有先后:
改频是"让初始化能跑对",放行是"让它开始跑"。
且 `apply_fclk0()` 本身必须在 `Overlay()` 之后(`Overlay()` 会把
`FPGA0_CLK_CTRL` 整个复位回 `BOOT.BIN` 的值 —— 09-24 已实测复现)。

## 纠错轨迹

本轮**五次自我纠错**,其中第 1 条是本项目至今最值得记的一条。

1. 🔴 **这个 bug 的藏身处就是我们自己写的那段注释。**
   `cv_sys.v` §7 原有一整段文字论证「运行时钟和设计时钟不一致**对这里的一次性
   上电握手没有影响**」。**这个断言是错的** —— 它成立的前提是"所有等待都是下界",
   而事实是**三个窗口都有上界**。
   ⇒ 一整轮排查(引脚、位流、界面写没写进去、AXI 通不通)**全部绕过了这个文件**,
   因为"注释里说过没事"。
   **处置**:就地改成 `🔴【2026-10-05 更正】`,把错误结论**保留可见**而非删掉,
   并写清楚"哪些等待是频率无关的、哪些不是"。
   📌 **一条写进代码的"这里没问题"的结论,和一个 bug 一样会阻塞排查** ——
   而且更隐蔽:它长得像已经查过了。这与 `LLM-040`「换完二进制先对时间戳」同型:
   **都是"没有证据的断言被当成了证据"。**

2. 🟡 **`0x18` 已被占用,差点覆盖掉规格里的 `RANGE_SEL`。**
   新寄存器第一版选了 `0x18`。动手前查 `cv_regs.py` 发现 `"RANGE_SEL": 0x18`,
   再查 `report/source_design_checklist.md` §3 第 406 行确认它是**规格里写死的**
   (测量主链要用),不是闲置地址。⇒ 改到 `0x84`(紧邻 `DDS_FREQ`)。
   📌 **规格文档是 M9「接口设计」的正文,不能被实现便利性覆盖** ——
   改地址的代价是文档、RTL、C 头、Python 四处同步,比换一个空地址贵得多。

3. 🟡 **自己算错一次,并在注释里写成了错误结论。**
   第一版注释写 t16 的两个频率窗口「虽有交叠」。
   重算:**三段全都不重叠**(t16 @27.78 = 5786~9042 < @50 = 10415~16275)。
   ⇒ 改成三行表格,并补上"不存在一组常数同时覆盖两个频率"这个结论 ——
   它才是"必须改架构而不是改常数"的论据。

4. 🟡 **写了不存在的异常类 + 循环 import。**
   `dac_release()` 第一版用了 `cv_monitor_error`(该模块只有 `NotImplementedError`)
   和 `from drivers import board`(`drivers` 依赖 `cv_monitor`,反向会成环)。
   ⇒ 拆成两层:窗口判断放 `drivers/board.py`(那里有 `BoardError` 和
   `fclk0_real_mhz()`),`cv_monitor` 侧只留薄访问器,读回不符时抛普通 `RuntimeError`。

5. 🟡 **`strings | grep` 返回 0,差点误判"重编失败"。**
   板上 `c_ui` 重建后,`strings c_ui | grep -c "仍被按在复位态"` 得 **0**。
   上一次的失败(clock skew 导致 `pynq_protocol.o` 没重编)刚发生过,
   很容易顺势再判一次失败。**改用 `grep -a` 直接搜二进制 ⇒ 得 1。**
   根因:`strings` 在 C locale 下按**单字节** `isprint` 判定,
   **UTF-8 中文被逐字节切断**,整串永远匹配不上。
   📌 与 `LLM-040` 纠错 1、`LLM-041` 纠错 3 同型 —— **失败零报错,靠换独立判据看穿**。

**顺带记两个环境坑**(都不影响结论,但各吃掉一轮):

| 现象 | 真因 | 处置 |
|---|---|---|
| `make` 没重编 `pynq_protocol.o` | 板上 RTC **慢约 2 天**,源文件 mtime 落在"未来",`make` 判定无需重建 | `rm -f build/app/*.o` + 只 `touch` 真正改过的两个文件 |
| 板上 `make` 被 bxrun 看门狗杀掉 | `make … \| tail` 会缓冲到 EOF 才输出,20 s 无输出即被判定挂死 | 改成 `setsid nohup` 后台跑 + 轮询日志 |
| 一次改动的编译量爆炸 | `touch app/*.h` 连 `lv_conf.h` 一起碰了 ⇒ 全部 LVGL 目标失效(~200 文件) | 教训:**只 touch 真正改过的文件** |

### 🟡 凭据:用一次性 helper,密文不进任何留痕
