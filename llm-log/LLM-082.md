# LLM-082: RG 结果不进汇总页 —— 带单位的串喂给了只收纯数字的解析器

- **日期**: 2026-10-29
- **模型**: deepseek-flash(Claude Code CLI)
- **任务**: 用户报「RG 测量结果没有在汇总页显示」;定位根因、修复并部署上板。

## 模型回答

1. **数据链**:`pynq_protocol.c` 两处 RG 结果显示都写成
   `snprintf(rg_text, sizeof(rg_text), "%.2f Ω", rg)` 后再调用
   `UI_Demo_UpdateResistance(rg_text, 1u)` —— 传进 UI 的是**带单位的串**(如 `"3.11 Ω"`)。
2. **根因**:`UI_Demo_UpdateResistance()` 把整串交给
   `UI_ParseNonnegativeDecimal()`,后者只接受纯数字,**遇到空格就返回 `false`**。
   而失败分支是**静默**的:不置 `g_latest_rg_valid`,也不调用
   `UI_ResultRecord(3u, ...)` —— 结果汇总的 RG 快照从未写入。
3. **为什么长期没被发现**:测量页那张 RG 卡在解析块**之外**更新,所以屏上
   "看起来正常";真正依赖 `g_latest_rg_valid` 的**汇总页 RG 卡、工程参数卡 Rg、
   二维码里的 Rg** 全部拿不到值。用户看到的正是这三处一致的 `--`/缺失。
4. **修法(边界归一)**:新增 `UI_ExtractDecimalText()` —— 跳过前导空白,只取
   数字与小数点,数字之后只允许空白(`"3.11 Ω"` 合法、`"3.11abc"` 仍拒),
   再交给原来的严格解析器。快照里只存纯数字,显示时由界面补一个 `Ω`
   (同时避免出现 `"3.11 Ω Ω"`)。解析失败时打印
   `[ui] Rg 文本无法解析:"…"`,下次不再静默。
5. **部署**:推 `ui_demo.c` / `ui_demo.h` → 板上
   `rm -f build/ui/ui_demo.o build/ui/ui_demo.d c_ui`(板 RTC 慢,必须先删旧对象)
   → `make -j2` → 软重启(本周期位流恰加载 1 次)→ 服务自启。

## 纠错轨迹

1. **先查错了方向**:一开始怀疑结果页刷新路径(`UI_ResultsRefresh` 是否漏调),
   但核对后发现 `UI_ResultRecord(3u, ...)` **从未被调用** —— 刷新不是根因,
   数据根本没进快照。
2. **用独立小程序复现**:把 `"3.11 Ω"` / `"3.11"` / `"--"` 逐串喂给
   `UI_ParseNonnegativeDecimal()`,得到 `"3.11 Ω" -> FAIL`、`"3.11" -> OK`
   ⇒ 定位到空格/单位,而不是数值或刷新时机。
3. **解释了"为什么一直没暴露"**:测量页 RG 卡在解析块外更新,故障被
   "界面看起来正常"掩盖;失败分支又不打日志 —— 静默失败最贵。
4. **没有把修法推给调用方**:虽然可以让 `pynq_protocol.c` 传纯数字,
   但显示串本来就需要单位,两处调用都改更容易再犯。改为在 UI 边界剥单位,
   并在 `ui_demo.h` 写明契约。
5. **板子 RTC 慢的旧坑**:继续按 `LLM-081` 的纪律先 `rm -f` 对象再编;
   判据用产物里的字符串 / `md5`,`make` 的输出不算证据。
6. **收尾没验完**:用户直接「关闭开发板」,所以本记录把
   "已部署、新二进制在跑" 与 "汇总页已显示" **分开写** —— 前者有证据,
   后者没有,不把前者当后者。

## 沉淀

→ 候选 `skill/format-at-boundary/` —— 模块边界两侧对同一数据的格式假设
(带单位 / 纯数字、空格、千分位)必须有一处**显式契约**;静默解析失败要用
"同一数据在 A 处正常、B 处缺失"的矛盾现象反查,而不是只看失败点。
→ 与 `skill/silent-capacity-gates/` 同源:都是**不报错的拒绝/截断**。
