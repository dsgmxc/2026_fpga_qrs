# LLM-050: 「100 kHz + 10 MSPS」单点测量 100% 失败 —— 解调参考表上限 64 点/周期被击穿;**报错文案的排查指引方向反了**

- **日期**: 2026-10-06(第 46 次会话,收尾——板子环境整理过程中读全量日志发现)
- **模型**: DeepSeek-V4-Flash
- **任务**: 用户要求「整理一下板子环境和文档,更新交付仓库并推送,关闭系统」。
  在把板上 `/var/log/qrs-ui.log` 全量取回做收尾对账时,**发现一条谁都没注意到的真缺陷**:
  停服务时 `dump_stats()` 报 `ADC 采集 成功=332 失败=5`,而这 5 次失败**在日志里只打了一行**。

## 提示词

```
整理一下板子环境和文档，更新交付仓库并推送，关闭系统，整理完板子就关闭系统
```

> ⚠️ 这条缺陷**不是用户报的**,是我在按上面这条指令做**日志对账**时查出来的。
> 记在这里是因为它满足记录的实质要件:**真实发生、有板上原始数据、有可复现步骤**。

## 模型回答(发现与判断)

**先对账,再看症状。** 日志切片取本上电周期(第 1033 行「PS 侧启动」起至 EOF):

| 项 | 实测 | 对账 |
|---|---|---|
| `[adc] 扫压` 行 | 326 | 5 轮完整扫压 × 60 = 300 + 被停止的 `27/60` 那轮 26 点 ✓ |
| `[adc] 单点` 行 | 6 | — |
| 合计 | **332** | **= `dump_stats` 的 `成功=332`** ✓ |
| `[adc] 🔴` 失败行 | **1** | 只打印一次(见下) |
| `100 kHz 窗口内的点测请求` | **5** | **= `失败=5`** ✓ |
| 本周期点测请求总数 | 11(2 单路 + 9 三路) | **11 = 6 成功 + 5 失败** ✓ |

**⇒ 5 次失败全部落在同一个设置窗口内:用户把激励切到 100 kHz 之后。这一窗口内 5 次尝试 5 次失败(100%)。**

**机理**:

```
N = f_s / f_e = 10 MSPS / 0.100 MHz = 100 点/周期
ADC_DEMOD_MAX_N = 64                       ← adc_sample.c 的静态表上限
⇒ build_table(100) 返回 false ⇒ AdcSample_Demodulate() 拒绝解调
⇒ 单点测量整体失败,电压/电流两个波形都不画
```

`adc_sample.c` 里那张 `s_tab_cos[64]/s_tab_sin[64]` 的余量是**按 DIV 从 1 MHz 反推**的
(DIV=2 → 65 点/周期,注释里写"取 64 不够,但那一档本来就采不出可用波形"),
**没有考虑"用户把激励频率调低"这条路径** —— 调低激励和调高采样率对 `N` 是**同一个方向**。

## 🔴 两个加重情节(比缺陷本身更值得记)

**① 报错文案的排查指引 ③ 方向反了。** 日志原话:

```
[adc] 🔴 单点测量:采集或解调失败 —— 解调不可用:每周期 100 点,超出参考表上限 64
      ⇒ 依次查:
         …
         ③ 采样率档位是不是太低 —— 每周期点数 < 4 时本层拒绝解调 …
```

真实原因是**采样率相对激励频率太高**(100 点 > 上限 64),文案写的是"是不是太**低**"。
⇒ 该文案只覆盖了 `N < 4` 那一支,**漏了 `N > 表上限` 这一支**;
**照它排查会往反方向走**(去调高采样率,而那样 `N` 只会更大)。

**② `adc_report_failure()` 只打印一次 ⇒ 后 4 次失败静默。** 这是为了防扫压时刷 60 行
(日志里明写「此后不再重复打印这一条」)。代价:
**本次 5 次失败里只有第 1 次留在证据上**,其余 4 次屏上无反馈、日志里没有。
若不是收尾时停了服务、把 `dump_stats()` 打出来,**这次失败在证据上就是不可见的**。

**③ 隐患:同一设置下扫压会"看起来跑完了,曲线是空的"。**
扫压的 60 点全部走同一条 `AdcSample_Demodulate()` 路径,所以 100 kHz 下 60 点会全部失败
且**只打 1 行**;而 `[proto] 扫压结束:60 点已下发到 DAC` **照常打印**。
(本次 6 轮扫压都在 1 MHz 下跑,**未命中**这一支。)

## 结果

☑ ✅ 直接可用   ☐ ⚠️ 部分可用   ☐ ❌ 不可用

**理由**:结论由**板上原始日志 + `dump_stats()` 计数器双向对账**坐实,11 = 6 + 5 与 326+6 = 332
两条链都能闭合,**不是推断**。给出的是"**不要动哪段代码**"和"**文案该往哪边改**"两条可执行判断。

## 验证方式

**(A) 板上真实日志**,`report/measurements/artifacts/20261006_qrs_ui_full_log.log`(1802 行,含停服务后的 `dump_stats()` 段)。
原始片段:

```
[mc] 激励 → 0.100 MHz(0x80 = 0x10624E)
[proto] 点测 CISS+COSS+CRSS @ 5.00 V:偏压已下发,300 ms 后采一次
[adc] 🔴 单点测量:采集或解调失败 —— 解调不可用:每周期 100 点,超出参考表上限 64
      ⚠️ 此后不再重复打印这一条。
```

**(B) 对账两条链**(§二那张表):`100 kHz 窗口内点测请求 = 5` = `失败=5`;
`扫压 326 + 单点 6 = 332` = `成功=332`;`333 − 326 − 6 = 1` = 那条 🔴 行。
⇒ **每一个 `[adc]` 行都有归属,没有余数。**

**(C) 常量出处**:`app/adc_sample.c` 的 `#define ADC_DEMOD_MAX_N 64u`、
`static float s_tab_cos[ADC_DEMOD_MAX_N];`、`build_table()` 的 `n > ADC_DEMOD_MAX_N` 返回 false。

**(D) 交叉证据 —— 位流本身没问题**:同一周期内 6 轮**1 MHz** 扫压共 326 点**全部成功**,
`偏压写=342 / 回读核对失败=0`,`axierr=0` ⇒ 失败**只跟设置组合相关**,不是硬件/位流故障。

**(E) ⏸ 未做(如实标注)**:没有做**独立复现**——只有本次会话的 1 组数据。
复现步骤明确、代价极低:**上电 → 激励切 100 kHz → 点单点测量 → 看两个波形页签是否为空**。
本轮服务已停,再起服务就是本上电周期的第 2 次 `Overlay()`(已知会锁死 HP 口),**做不了**。

## 纠错轨迹

1. **我原本是去"对账"的,不是去"找 bug"的。** 起因只有一句话:`成功=332 失败=5`,
   而日志切片里 `grep -c '^\[adc\]'` 得 **333**。**我第一反应是"对数不上,可能是计数器漏计"**
   —— 这是错的:`333 − 326(扫压) − 6(单点) = 1`,那 1 行正是 🔴 失败行。
   ⇒ 📌 **两个数字对不上时,先问"它们的定义一样吗",再问"哪个错了"。**
   这里"日志行数"与"成功计数"**本来就不是同一个量**(日志还含失败行)。
2. **差点把 5 次失败当成"5 个不同的偶发失败"。** 只有在按时间轴切片、
   发现 5 次**全部**落在 `[mc] 激励 → 0.100 MHz` 之后才成立"100% 失败率"这个判断。
   ⇒ **同一个计数,按"总数"读是噪声,按"时间窗"读才是信号。**
3. **差点漏掉"只有第一行有日志"这件事。** 如果只 grep 到那 1 行 🔴 就下结论,
   会把它当成"1 次偶发失败",而真值是 **5 次**、且**后 4 次不可见**。
   这条是本次最该沉淀的部分:**"打过一次就不再打"的日志策略,会让复现次数丢失。**
4. **报错文案的方向错误不是本次引入的**,是 `adc_sample.c` 里 `adc_report_failure()` 的既有文案。
   我没有去"顺手改"它 —— §6.0 的分工是用户写代码。**本轮零代码改动**,
   只把判断依据写进 `report/measurements/20261006_board_ui_log_analysis.md` 和 `docs/project_state.md`。

## 沉淀

→ 候选 `skill/error-text-can-point-the-wrong-way/`

- **适用范围**:任何"错误信息里带排查指引"的诊断代码(不限本工程)。
- **判据**:**报错文案与判定条件必须同源**。本工程的判定是 `n > MAX` 或 `n < 4`(**双侧**),
  文案却只写了 `n < 4` 那一侧 ⇒ 用户按文案走会**朝错误方向调参**。
  检查方法:把判定条件的所有分支列出来,逐条问"文案里有没有对应这一支"。
- **失效条件**:若判定只有单侧,则不适用。
- **来源失败**:本次 `每周期 100 点,超出参考表上限 64` 却让用户去查"采样率是不是太低"。

→ 候选 `skill/report-failure-once-loses-the-count/`(扩展既有 `count-is-not-inclusion`)

- **适用范围**:**所有"失败了就不停重试、但日志只打一次"的循环**(扫压 60 点、轮询、重连)。
- **判据**:这类代码必须**配一个收尾计数**(本工程的 `dump_stats()` 就是)—— 否则失败次数**不可知**。
  更稳的做法:**首次打全文,后续每次打一行摘要**(或每 N 次汇总一行)。
- **失效条件**:若失败一次即中止整个流程,则丢失的风险小。
- **来源失败**:本次 5 次失败里**只有 1 次可追溯到日志**;
  若非收尾时停服务并打印了 `dump_stats()`,这次缺陷**永远不会被发现**。

→ 与既有 `skill/measurement-instrument-can-be-wrong/` 同族,但**方向相反**:
那条讲"量具不可信",这条讲"**量具可信、但它的报错把你指错了路**"。
