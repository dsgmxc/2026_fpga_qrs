# LLM-037: 「画面向右平移、按键要往左点」的排障 —— 模型两次拿噪声当结论,被用户叫停

- **日期**: 2026-10-03
- **模型**: Claude(DeepSeek-V4-Flash 底座)
- **任务**: 定位用户报的「画面整体向右平移,但按键位置是对的,点按键左边才触发跳转」;收尾做开机自启动 + 环境整理

## 提示词

```
我按完了，另外显示有点小问题，画面整体稍微向右平移了，但是按键的位置却是对的，我点按键左边才触发跳转
```

```
这完全没达到之前我看到的那种画面漂移的程度，感觉只是手指误差而已，这样测没什么意义，
你不如再把ui界面调出来我看一下
```

```
两张都不变，之前那个应该是个例外，先不管了，开机初始化做好，然后把没用的暂时性文件清除，
整理环境，下午先这样了
```

## 模型回答

摘要:先把现象拆成两个可能来源 —— ①显示扫描输出偏移 δ_display,②触摸坐标过报 δ_touch。
两者产生**完全相同的症状**,必须用绝对参考(屏的物理边缘)才能分开。
随后画了 5 根已知位置的竖条 + 两端 8 px 白条,让用户逐条点中心,用 `/dev/mem` 旁路读回触摸寄存器反推 δ。
最后放弃"点位测量",改用 **UI 自己的布局当尺子**(两张大卡之间的 22 px 缝隙),一次按压得出 |δ| ≤ 11 px。

## 结果

☐ ✅ 直接可用   ☑ ⚠️ 部分可用   ☐ ❌ 不可用

> 结论本身**可用**(|δ| ≤ 11 px,触摸无标定问题);但**得出这个结论的过程里我错了两次**,
> 第一次和第二次给出的数都**不足以支撑任何结论**,是用户叫停后才换的量具。

## 验证方式

| 判据 | 方法 | 结果 |
|---|---|---|
| 触摸 X 偏移 | 首页两张大卡(各 **453×156**,左卡 x∈[48,501]、右卡 x∈[523,976])之间的 **22 px 缝隙**,按缝正中 x≈512 看哪张卡进按下态 | **两张都不进按下态** ⇒ \|δ\| ≤ 11 px |
| 显示不可能右移 | 读 `lcd_timing.v` + `cv_sys.v` 输出级 | `assign lcd_hs = 1'b1;`(HSYNC 恒高)+ DE 模式 ⇒ 屏没有行同步可数,唯一列参考是 DE 上升沿 ⇒ **画面横向平移无物理通路** |
| 触摸链路无缩放 | 读 `gt911_ctrl.v` / `pynq_touch.c` / `pynq_indev.c` / `lv_indev.c` | GT911 模块**不下载配置表**(只轮询 `0x814E`/`0x814F`);RTL 取 `{rbuf[3][3:0],rbuf[2]}` 原样 12 位;`lcd_panel_config.h` 三个变换宏全 0;`lv_indev.c:332` 只在 `rotated!=0` 时变换,当前 `rotated=0` ⇒ **全链路纯直通** |

## 纠错轨迹

### 1. 模型差点把 ±10 px 的噪声当成 1.4% 的标定误差发表出去

我让用户依次点 5 根竖条的中心,读回触摸坐标,得到:

| 竖条 | 帧缓存中心 | 点到 | δ |
|---|---|---|---|
| 红 | 131.5 | 140 | +8.5 |
| 绿 | 323.5 | 339 | +15.5 |
| 白 | 515.5 | 523 | +7.5 |
| 黄 | 707.5 | 711 | +3.5 |
| 蓝 | 899.5 | 900 | +0.5 |

δ **单调递减**,看着像"负的比例误差"(触摸可用范围 ≈ [10, 1020] 而不是 [0, 1023]),
我几乎就要据此写"GT911 存在约 1.4% 欠标定"。

**自己把这条推翻的证据**:同一个蓝条,上一轮量到 **+10.5**,这一轮 **+0.5** ——
同一条、同一位置、同一个人,**两次差 10 px**。而绿色那条的 y=285,其余四条都在 294~304,
**它是瞄歪的**,不能进拟合。

⇒ **手指瞄准的重复性就是 ±10 px 量级,和要测的效应同量级。这套量具没有分辨力,我不该继续解读它。**

### 2. 我做的"边缘判定"没有声明分辨力,却当成了证明

我画了 x=0..7 和 x=1016..1023 各 8 px 白条,用户回「两个白线都能看见,没看到黑缝」,
我就记成"δ_display ≈ 0"。

**问题**:8 px 的白条只能排除 **δ≥8**,排不掉 3 px 的偏移;而且我从来没告诉用户
"这个测试的分辨力是多少"。用户后来说「之前画面上的偏移严重多了不可能只是个黑缝几个像素的」——
**用户的量级感和我这个测试的量级根本对不上,而我拿我的测试去否掉了用户的现象。**

### 3. 用户叫停,换量具才拿到答案

用户原话:「**这完全没达到之前我看到的那种画面漂移的程度，感觉只是手指误差而已，
这样测没什么意义**」。

被叫停之后换的思路:不问"偏移多少 px",改问"**偏移有没有超过某个界**"——
用 UI **自己的布局**当尺子:

> 两张大卡各宽 453 px、中间**只有 22 px 缝隙**。
> 按缝正中(x≈512),按住不松,看哪张卡变按下色。
> 右卡亮 ⇒ δ > +11;都不亮 ⇒ |δ| ≤ 11;左卡亮 ⇒ δ < −11。

**这一次不要精度**:缝隙边界是 LVGL 自己算的,手指偏 10 px 也还在缝里。
用户回复「**两张都不变**」⇒ |δ| ≤ 11 px,收工。
**同一个问题,换一个不需要人眼量尺寸的问法,一次按压就解决。**

### 4. 附带:模型归因一次,自己撤回一次

本轮更早,我一度判断"板子挂死是因为在活跃 PL 上重载位流",随后读本项目的
`never-poke-fpga-rst-ctrl-live.md` 发现**那条记录写的恰恰相反**(重载位流是安全路径),
当场撤回,改列为三个未验证候选。这条纪律本轮保留:**归因先查自己已存的结论,别抢着下判断。**

## 沉淀

**候选 skill ①:`用被测对象的布局当量具,而不是用人的手当量具`**
人的瞄准重复性(~±10 px)常常和要测的效应同量级。换成"判定是否越过某个已知边界"的
**二值问法**,可以把分辨力从"手感"转移到"被测系统自己的几何"上。
判据要从被测对象里**算出来**(这里是 453×2+22 的布局),而不是量出来。

**候选 skill ②:`测量前先声明分辨力`**
给用户做任何"测一下"的测试之前,先算清楚**它能分辨多小的量**。
分辨力不够就说不够,别把测出来的数当结论 —— 本轮两次错误都出在这里。
反例判据:如果一个数字要写进结论,它必须**先有已知分辨力**。
