# LLM-068: 扫压末端尖峰的根因(不是算术,**是整次采集混进了坏样本**)+ 用户口径「多测几次取合理值」的正确形态(自洽闸 + 重采,不是中位数)

- **日期**: 2026-10-15
- **模型**: Claude(DeepSeek-V4-Flash 会话)
- **任务**: 用户看到 CRSS 高压端 Cs 冒出 519 pF(基线 ~13 pF)的尖峰,问
  「**什么原因,或者扫压的时候就是多测几次取合理值让结果更稳定行不行**」,
  随后指令「**按照最合理的方式进行修复**」。
  产出:`adc_sample.{c,h}` 新增 `AdcSample_PpConsistent()` 自洽判据;
  `pynq_protocol.c` 新增 `adc_capture_pair()` 重采外壳 + 账本 + 两处日志证据。

## 提示词

## 模型回答

**根因(先答"为什么",这是用户真正问的那半句)**:不是算术算错。
**同一个缓冲里有两个数互相矛盾** —— `B/INB 幅值 0.0067 V`(1 MHz 单点相干解调、
8190 点平均)隐含峰峰 `2×0.0067/2.0×4096 = 27 码`,而同一次采集打出的 `峰峰` 是
**2588 码**,差 **94 倍**。正常点这两个数一致到 ~2%。
指纹还多一条:某次扫压出现 `A码 = B码 = 3205`(两路读到**同一个字**)。
机制:A 与 B 是**同一条 12 位总线上的两个时分字**,采样刻度错一拍就会让 A 读到 B 的字
⇒ `VH ≈ VL` ⇒ `Z ≈ 0` ⇒ Cs 爆掉。只在 **CRSS 高压端**放大,因为 `Cs ∝ 1/VL²`,
那里 `VL = 23 码`(0.56% 满量程);同样的毛刺落在 CISS(`VL ≈ 1000 码`)上动不了 1%。
⇒ 指向采样刻度距 ADC 总线边沿只有 **1 tick = 7.69 ns** —— 与 **2026-10-15 的
`P=2→4` 改动**(Cs 离散度 3.86% → 0.42%)记的是同一个机制。
⚠️ **明说这是推断不是证明**:决定性实验(扫 `P=4` 的四个刻度 `{−2,−1,0,+1}` 看跑间稳定性)
在界面活着时做不了 —— 界面每次采集开头都会经 `MeasureConfig_PushPhase` 重写 `0x88`。

**回答"多测几次取合理值行不行"**:方向对,但**中位数不行**。
坏点不是"读数有噪声",是**整次采集里混进了坏样本** —— 同一个缓冲里两个数差 94 倍。
这种点整次都错,N 次取中位数会让**错的多数赢**。
有效的形态是先问"**这一次算不算数**"(由一条物理不变式定义),不算数就**换一次重采**。
即:**「合理」由不变式定义,不由投票定义。**

**重采真的有用吗(实测,不是想当然)**:日志里同一偏压连测 ≥4 次的 **63 组,
全部是"有时标、有时不标",次次都标的一组都没有** ⇒ 毛刺在同一点上不恒定,重采能救。

**判据**(`码 ≤ K × 2×幅值 + FLOOR`,单边 —— 只拦"码比物理上可能的大得多")。
阈值**从 2039–4462 个真实样本里选**,不是拍的:

| 判据 | 抓住"坏"(`码/期望 > 5`) | 误伤"好" |
|---|---|---|
| 只看 `OTR ≠ 0` | 128/347(36.9%) | 24/1692(1.4%) |
| K=2.5, FLOOR=32 | 347/347(100%) | 155/1692(9.2%) |
| **K=3.0, FLOOR=64** ← **选定** | **342/347(98.6%)** | **31/1692(1.8%)** |
| K=4.0, FLOOR=128 | 341/347(98.3%) | 31/1692(1.8%) |

分布:中位比值 A 1.021 / B 1.084;p90 B 37.0;max B 193.5;
坏点 `码` 一律钉在 3800–4095(与期望值无关),其中 92–96% 带 `OTR ≠ 0`(正常点只有 4–5%)。
误伤集中在"较小那一路只有 50–200 码"的点(6.1%),200 码以上只有 1.2% —— FLOOR 就是为此而设。

## 纠错轨迹

<!-- 这一节是评分重点。只记成功案例拿不到分。 -->

1. **★ 差点把阈值按理论定死,而不是按数据定。**
   我第一反应是"K=3 太松" —— A 路幅值下 `3×1352+32 ≈ 4088` 几乎等于满量程,
   看着像"满量程毛刺都拦不住"。**若照这个直觉把 K 调小,会把大量好点判掉。**
   改法:先把日志里真实分布量出来。结果 A 路最大比值只有 **3.71** ⇒ K=3.0 在 A 路完全安全;
   真正需要收紧的是 B 路,而 B 路靠 FLOOR 才收得住。**先测分布,再选阈值。**

2. **★ 第一版方案过大,自己砍掉了。**
   我最初设计的是"N 次采集取中位数",配**第二对 64 KB 暂存缓冲 + memcpy 拿胜者**。
   写之前意识到:自洽闸已经把**整次坏掉的采集**挡在门外了,活下来的点之间只差 ~0.4%,
   而"重采到第一次自洽为止"**不需要任何额外交互缓冲**。
   ⇒ 换成现在的形态。**更简单,论证强度不减。**

3. **★ 把估计值写成了实测值的口气,自查后改回。**
   `ADC_SAMPLE_TRIES_MAX` 的注释里原写「量级 ~6 ms」,读起来像量过。
   **实际上没有。** 改成显式标注"**估计,未实测**",并附上测量方法(A/B 两轮总时长差 ÷ 重采次数)。
   —— 这正是 `skill/` 里 `measurement-instrument-can-be-wrong` 那条的同型错误。

4. **★ 一个假设被自己证伪,如实告诉用户,没有悄悄丢掉。**
   我怀疑 `sweep_autoscale()` / `MeasureConfig_PushPhase` 会在采集途中重写 `0x88`,
   那会产生一模一样的"两种字混在一个缓冲里"的签名。查下来:`PushPhase` 只在
   `AdcSample_CapturePair` 里调,**且被 `wait_until(ADC_STS_BUSY_MASK, 0, ...)` 挡住** ——
   正是 `adc_capture.v` 自己规定的规则。**这条路径排除,已明说。**

5. **★ 板卡目录结构又猜错一次(这是同一类错误的第 5 次)。**
   我按 `/home/xilinx/cv/src/c_ui/app/` 去 md5,两个路径都不存在。
   实为:C 源在 **`/home/xilinx/c_ui_src/app/`**,而 **`/home/xilinx/cv/` 是纯 Python 树**
   (`qrs-ui.service` 的 `WorkingDirectory`)。教训照旧:**先列目录,再下结论。**

6. **★ 交付仓库同步时,`rsync` 报的两处"差异"方向恰好相反,照它同步会把仓库打回旧版。**
   - `src/rtl/`:工作区那份是 **9 月残本 5 个文件**,仓库那份才是当前真本 **18 个文件**
   - `board/qrs.bit`:工作区 `232c649d…`(**10-14 那版**)vs 仓库 `c92c7ed5…`(**10-15 第 61 次,现行**)
   - `report/measurements/20261005_*.md`:两边**只差 `report/` vs `board/` 路径前缀**,仓库那版才是对的
   ⇒ 三个方向都由**时间戳/md5/内容**逐个核过才动手,`--dry-run` 的"有差异"三个字不足以定方向。
   另:仓库把 LLM 记录放在**顶层 `llm-log/`**,工作区放在 `report/llm-log/` —— 直接 rsync 会造出一棵重复的树。
