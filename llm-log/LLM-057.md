## 纠错轨迹

### A. ★ 我自己的 bug:一条**永不执行**的 `if` —— 靠板上实测翻出来

`relay_view.c` 我原本写成 `if (fault) { 硬件出错 } else { switch(err) { 三条具体文案 } }`。
板上实测:写 `0x1C=0x7F` 时真因是 `err=0x03`(BUSY),**界面却弹「硬件出错,状态未确认」**。

回查 `cv_sys.v:793`:

```verilog
assign sts_status = {16'h0, io_err_code, 5'h0, (io_err_code != 8'h0), io_done, io_busy};
```

**`STATUS[2] fault` 是 `(err_code != 0)` 的派生冗余位,不是独立故障** ⇒
`if (fault)` 恒等于 `if (err != 0)`,恒真,把三条具体文案全吞了。
**修法**:删掉 fault 分支,只按 `err_code` 映射(去重 key 也从 `(err<<1)|fault` 简化成 `err`)。
**复测**:写非法档位 ⇒ 界面正确显示「档位编码非法 / 档位编码非法,硬件已保持原值」✅

> 这条正是 `CLAUDE.md` §6.2 要的那种记录:不是我读代码读出来的,是**用户要的「说明失败原因」
> 在屏上没出现**才暴露的。**如果不真上板看一眼,纯静态检查抓不到** —— 两个分支各自都「看起来对」。

### B. ★★ 未解决:每次写 `0x1C`,PL 表现为**两次** `cfg_relay_set` 脉冲

**四组对照实测**(全部 `settle` 与写入值两个变量,其余不变):

| # | settle | 写 `0x1C` | 合法? | 读回 `0x1C` | STATUS | **源 RTL 预测** |
|---|---|---|---|---|---|---|
| 1 | 0 ms | `0x3C` | ✓ | `0x3C` ✓ | err=0x00 | relay=0x3C, err=0x00 ✓ |
| 2 | 0 ms | `0x80` | ✗ | **`0x00`** ✗ | err=0x01 | relay **不变 0x3C**, err=0x01 |
| 3 | 2000 ms | `0x51` | ✓ | **`0x00`** ✗ | err=0x03 | relay=0x51, err=**0x00** |
| 4 | 40 ms | `0x1E` | ✓ | **`0x00`** ✗ | err=0x03 | relay=0x1E, err=0x00 |

**唯一自洽的解释**:两个脉冲 —— **第一个携带 `0x00`**,第二个携带真值。
`0x00` 在白名单里(合法组合 `COSS_DISCHARGE`)⇒ 第一个脉冲**总被受理** ⇒ `relay_reg ← 0x00`;
第二个脉冲再按状态被受理或被拒。

**对照组 2 单独就能把「两次脉冲」钉死**:一次写不可能同时是 `0x00` 和 `0x80`。
`0x1C` 掉到 `0x00` 要求有一次**被受理**的写(`relay_reg` 只在受理分支被写;
复位分支写的是 `RELAY_RESET=8'h10`,不是 0),而 `err=0x01` 要求有一个**非法值**进 FSM。

**但我把源 RTL 的每一处相关逻辑都核过了,一次写只可能出一拍脉冲:**
`do_write = aw_hs & w_hs & ~bvalid_r`,而 `bvalid_r` 在 `do_write` 下一拍即置 1
⇒ `do_write` 高不过一拍 ⇒ `relay_set_r` 高不过一拍。

**⇒ 板上行为无法由当前源文件推出。根因未定位,不下结论。**

**已逐条排除(均实测,非推断)**:

| 假设 | 排除方式 |
|---|---|
| 源 / 位流不一致 | 全盘 `find` 同名文件只有 1 份 `relay_ctrl.v`;`.xpr` 引用的就是它;DCP(synth 15:42:19 / routed 15:43:10)**晚于**源(15:31) |
| PS 侧有第二个写入方 | `systemctl stop qrs-ui` 后复测 —— **现象完全复现** |
| C 界面偷偷写 | 全量 grep `app/` —— 只有 `cv_reg_read`,无 `cv_reg_write` |
| `IDX_*` 常量重复 / 读分支 case 重复 | 全量 dump 读分支 + grep,无重复 |
| `wdata_r` 落后一笔写 | 前一笔故意留低位 `0x61`,复测读回 **`0x00` 不是 `0x61`** ⇒ 不是简单的陈旧数据 |

**为什么没有继续用「推理」往下推**:`CLAUDE.md` §6.2 的红线是「不要编造」。
源 RTL 推不出的东西,再推理就是猜。**下一步应走仿真或网表核对,不该靠脑补。**

### C. ⚠️ 顺带查出的安全项(比 B 更该先处理)

`0x00`(COSS_DISCHARGE)与 `0x10`(ALL_OFF)是**两个不同的物理组合**。
既然第一个脉冲总携带 `0x00` 且总被受理,则:

> **一个「被拒收」的写(例如非法值 `0x80`)仍会把继电器组合实际拨到 `0x00`。**

而 `relay_ctrl.v` 的设计备忘明确承诺相反的契约:「★ 拒收:`relay_reg` 一位都不动」。

⚠️ **但继电器的物理触点从头到尾没量过** —— 以上全是**寄存器侧**读数。
「`relay_reg` 变了」和「继电器真动了」是两件事。**需要万用表实测触点才能下这个结论。**

### D. 方法层:一次「不用危险手段」的主动选择

`relay_hold.py` / `relay_rw.py` 都调 `Overlay(..., download=True)`。
而此刻 `lcd_fb_reader` 正在 HP 口上读 DDR —— 第二次 `Overlay()` 会让 AXI 事务中途消失,
**锁死 HP 口连带 CPU,只能断电**(`tools/adc_probe.py:11` 有记载)。
⇒ 本次全部诊断改用 `/tmp/poke_relay.py`:只 `mmap /dev/mem`,**不碰位流**。

## 沉淀

1. **`fault` 这类「派生冗余位」是死代码的温床。** 一个恒真的 `if` 会让它后面所有分支静默失效,
   而两个分支**各自看起来都对** —— 静态检查抓不到,只有拿真硬件跑一遍才暴露。
   ⇒ 读状态寄存器前,先回去看**它是怎么被赋值的**,别只看名字。
2. **「只读接入」的验收判据不是「界面显示了」,而是「界面显示的值 == 直接读寄存器的值」。**
   少了这条交叉核对,写死一个看起来合理的字符串也能蒙混过去 —— 那正是本次要消掉的那个谎。
3. **`settle=0` 会把「两次脉冲」这类缺陷完全掩盖掉**:两次都被受理,后一次(真值)覆盖前一次,
   读回恰好正确。凡是「有的路径对、有的路径错」,先找**让错误路径不触发的那个参数**。
