## 纠错轨迹

### 1. 状态文档与现实不符(模型通读时发现)

`docs/project_state.md` §十一 写「交付仓库是 **git 仓库**,而工程在仓库之外 → 一次误删就是全丢」。
模型核对后发现:

```
$ git rev-parse --is-inside-work-tree   →  fatal: 不是 git 仓库
$ find ~/Desktop -maxdepth 4 -name .git -type d  →  空
```

**两边都没有版本控制** —— `.gitignore` 在,`.git` 从未存在过。实际风险比文档写的更大
(M15 开源要求也依赖它)。用户答复:仓库过两天建。

→ **教训:状态文档是模型自己维护的,同样会失真。通读项目时要拿文件系统核对,不要只读文档。**

### 2. 「简化回答」—— 用户对模型输出方式的纠正

模型给了一份很长的时序说明(带推导、出处、附加建议、结尾追问),用户回复:

> 「简化回答,太长了,就告诉我时序就行」

→ 用户要的是**当下能用的数字**,不是完整论证;冗长回答把关键数字埋起来了。
→ 已改为默认:表格 + 极简要点,出处/推导/发散一律不主动展开(被追问时能立刻出示)。

### 3. 第一轮审查:3 条致命

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| ① | `set_in_d <= start;` | 名字是 `set_in`,喂的却是 `start`。**`set_in` 端口全文从未被读** | NORMAL_WAIT 里 `set_in_d` 恒 0 → **发完第一帧永远卡死** |
| ② | `NORMAL` 状态 | **没给 `tx_data` 赋值**。`code_in_d[0:3]` 声明并填充了,但**全文从未被读** | 发出去的是 `CAL` 留下的残值 **`0xA1`**,不是 DIR 字节 |
| ③ | NORMAL_WAIT → NORMAL | **`work_cnt` 没复位** | 第二帧起只发 1 个字节,DIR 写不进去 |

其中 ② 的迷惑性最强:数组**建对了、填对了**,只是没人读它 ——
波形上会看到"有 4 个字节在发",但内容是错的。属「**结构齐全、接线漏了**」类缺陷。

### 4. 用户纠正模型,但双方各对一半(**本次最有价值的一条**)

模型第二轮指出:

> 「`set_in_d & !set_in_d_d` 只在上升沿后**一个周期**为真,而 NORMAL_WAIT 每 1,500,000 拍才采一次
> → 必然错过」

用户反驳:

> 「每 1,500,000 拍才采一次并非吧,**他计数完我特意没有清空**一直到检测到边沿,
> 也就是说直到除了第一次会等待以外后面都没有等待啊」

模型**没有直接让步,也没有坚持**,而是重新 `sed` 出该段原文核对 —— 结果:

```verilog
else
    begin
        state <= NORMAL_WAIT;
        delay_cnt <= 0;      // ← 这一句在
    end
```

**用户的意图是对的**(计数到顶后不清空 → 逐拍轮询 → 单拍宽的沿必被抓到),
**代码和他的描述不一致** —— `else` 分支里多了一句把计数打回 0 的赋值,
把"饱和轮询"变成了"每 1.5M 拍采一次"。

→ 用户删掉那一句后,设计成立。
→ **教训:用户描述的是意图,代码描述的是行为。两者冲突时不能盲信任何一方 ——
去读原文,然后指出是哪一边有问题。** 本次若直接认错,那句 `delay_cnt <= 0` 会被留下;
若直接坚持,则会误解用户的正确设计。

### 5. 附带确认:`dac_cs` 从复位到结束恒为 0(**又一次 `cs-is-optional` 实证**)

用户追问「那从复位开始 cs 从始至终就没变过啊」,模型确认这是**设计意图**,并给出三条依据:

- 手册 p11:"If CS is not used, it should be tied low." → 恒低是**正式路径**
- **复位图案本身就要求 CS 低**("can only be triggered when CS is low")→ 在这里 CS 低是**必须的**
- 复位图案靠**三段极长高电平**(512~2400 tXIN)与普通 SCLK(5 tXIN)自行区分,
  命令之间靠 `MB` 字节数 + SCLK 静默 ≥ `t14` —— **CS 不承担分帧职责**

→ 只有一种情况要改:**总线上加第二个从机**(如 AD9833 复用 `spi_master`)。与 D20 一致。

### 6. 后两轮:小问题的修正

| 轮次 | 模型指出 | 用户处理 |
|---|---|---|
| 第 3 轮 | `delay_cnt <= 0;`(见 §4)、`delay_cnt < 1024` 实得 1025 拍(与全文 `xxx-1` 体例不符) | ✅ 两句都改 |
| 第 4 轮 | `code` 在帧中途变化会**撕裂**(4 字节分别取 `code_in_d[work_cnt]`,而它每拍跟着 `code` 更新) | ✅ **改为帧起始时锁存** `code_in_d`(NORMAL_WAIT 检测到沿那一拍);顺带把 `code_in_d` 的复位并进主复位分支 |

**模型同时主动标注的一处行为变化**:`CAL_WAIT` 的出口由 `NORMAL` 改成了 `NORMAL_WAIT`
→ **上电后不会再自动发第一帧**,校准完 600 ms 后板子静默,直到 `set_in` 出现一个 0→1。
设计上更统一(所有帧都由 `set_in` 触发),但**上板时若把 `set_in` 接常量 1 就会一直静默**。
