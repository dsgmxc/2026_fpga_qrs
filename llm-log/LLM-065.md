## 模型回答

### 一、回退用**文件开关**,不用环境变量(为了避开红线)

理由:环境变量要重启服务才生效,而**重启 `qrs-ui.service` = 第二次 `Overlay()` = 红线**;
文件在 `sweep_start()` 时**现读、不缓存** ⇒ 「改文件 → 下一场扫压」即生效,代价为零。

| 位置 | 改动 |
|---|---|
| `pynq_protocol.c:126` | `#include <unistd.h>`(为 `access()`) |
| `pynq_protocol.c:168` | `#define SWEEP_AUTO_GEAR_FLAG "/home/xilinx/sweep_auto_gear"` + 完整理由注释 |
| `pynq_protocol.c:200` | `sweep_auto_gear_enabled()` |
| `pynq_protocol.c:1007` | `sweep_autoscale()` 开头早退 |
| `pynq_protocol.c:918` | 扫压起手日志**明说**当前模式,事后对日志不会有歧义 |

```bash
sudo touch /home/xilinx/sweep_auto_gear   # 回到自动换挡
sudo rm    /home/xilinx/sweep_auto_gear   # 固定挡位(默认)
```

### 四、★ 用户跑了一场扫压 —— **「数据很奇怪」的根因坐实**

日志 `/var/log/qrs-ui.log` 第 **5384–6103** 行(该文件跨上下电**追加不截断**)。
存档:`report/measurements/20261015_uilog_fixed_gear_sweep.txt`,md5 `8c17256b861ed0e099d2b007d86c10c8`。

**① 固定挡位真的生效了**(用户①②的直接验收):

```
[proto] 扫压开始:CISS+COSS+CRSS,0.10 V → 100.00 V,60 点/腿,每点 300 ms
        挡位 0x2(100 Ω):🔒 **扫压期间固定不变**(自动换挡默认关闭,要开见 SWEEP_AUTO_GEAR_FLAG)
```
60 点**每一点**都印 `挡位 0x2`,`sweep_autoscale()` 一次都没触发。

**② 三腿继电器真的逐腿切了**(`LLM-062` §一④ 的验收):

```
[relay] 回路 → CISS(0x7F)  →  RG(0x3C)  →  CISS(0x7F)
[relay] 回路 → COSS(0x61)
[relay] 回路 → CRSS(0x51)
[proto] 扫压结束:CRSS,共 60 点已下发到 DAC
```
⇒ 三条曲线**不再共用一份数据**(`LLM-062` 结清的「四处假装」之一,上板确证)。

**③ 🔴🔴 核心发现:CRSS 腿的两路 ADC 都顶到满量程。**

| 腿 | A 峰峰(码) | B 峰峰(码) | OTR 非零 | `VL/VH` | 判定 |
|---|---|---|---|---|---|
| CISS | 1199–3516 | 943–3516 | **1 / 72** | 74 % 稳 | ✅ 正常 |
| COSS | 1636–2876 | 133–3569 | **1 / 60** | 7.3 % 稳 | ✅ 正常 |
| **CRSS** | **2815–4095** | **3213–4095** | **58 / 60** | 0.09 %–3.3 % | 🔴 **饱和** |

`4095` = **12 bit 满量程**(`VFS_PP = 2.0 V / 4096 码`)。CRSS 腿最大 OTR = **43 / 次采集**;
**B 通道基波塌到 0.002–0.008 V,而原始峰峰是满量程** ⇒ **信号没了,只剩削顶。**
`Z` 因此飞出 2955 Ω → **127 kΩ**,`Cs` 出 **−210.7 pF / 507.5 pF / 2.56 pF** 这类非物理值。

**对照下来 CISS / COSS 两条腿是干净的** —— `|Z|` 稳(`VL/VH` 74 % / 7.3 %),
`Cs` 平(2055 pF / 118 pF),`OTR` 各只有 1 次非零。

**④ 顺带坐实:前一轮的「变好了」是虚的(见 `LLM-064` 更正)。**

## 纠错轨迹

1. ★ **我把「四个挡位读数终于一致」当成了接线修好的证据,它是虚的。**
   用户整理接线后测四挡得 CISS 3504.8 / COSS 4750.2 pF,看着比之前"整齐"。
   我回头比对才发现:**那场的偏压是关的** —— 偏压关的扫压给 3505.4 / 4743.8 pF(吻合),
   偏压**开**的给 2055.4 / 118 pF,而整理接线**之前**(偏压开)给 2055.5 / 114 pF。
   ⇒ **接线整理没有改变任何东西**;「变好」只是偏压没开。
   📌 **两个变量一起动时,"看起来更好"什么都证明不了** —— 同 `LLM-063` 纠错① 的同一类错。
2. **我把日志里的一次「挡位 10000 Ω → 1000 Ω → 100 Ω」误读成"迟滞失效、挡位来回跳"。**
   回原始行才发现那是 **CISS 腿第一个点继承了上一条腿的 D 挡、再用两步收敛下来** 🔴
   —— 这恰恰是 `|Z| ≈ R0` 判据**该有的行为**,不是故障。**是我读日志的模式错了,不是硬件错了。**
3. **自写的日志解析器把腿归属算错**:分组表显示 `VL/VH ≈ 90 %`,而同一份日志里
   自动换挡那行写的是 7.4 %。**我没信自己的解析器**,退到 `sed` 逐行原文才确认。
   根因:解析器把 `cur_leg` 跨场带了过去。
4. **正被运行的执行文件不能被 `make` 覆盖(Linux `ETXTBSY`)。**
   做法改成先 `mv c_ui c_ui.prev` 再 `make` —— rename 不动已运行的 inode。
   📌 **顺带白得一份回滚件**,比直接覆盖更安全。
5. **`echo xilinx | sudo -S -p '' wc -l < /var/log/qrs-ui.log` 读口令失败。**
   重定向 `<` 由**远端 shell 先于 `sudo`** 执行 ⇒ `sudo -S` 的 stdin 被换成了那个文件,
   它拿日志的头几行当口令,报两次 `Sorry, try again.`。
   改成把文件名当**参数**(`wc -l /var/log/...`)即可。

## 沉淀

→ 待建 `skill/two-variables-one-move/`(**两个变量一起动时,任何"看起来更好"都不构成证据**;
判据 = **一次只动一个,并且把"没动"的那一次也记下来**)—— `LLM-063` 纠错① 与本次纠错 1 **同型复发**,
说明它不是一次疏忽而是**我的默认推理方式有漏**。

→ `skill/`:本轮还产生一条可复用的**运维**形态:
**「用文件开关代替环境变量 / 服务重启」** —— 当重启进程本身是红线时(此处 = 第二次加载位流),
把"编译期决定"改成"运行时现读"能让代价从「一个上电周期」降到「零」。
⚠️ 判据:开关的读取点必须是**每次进入该功能时**,而不是进程启动时缓存。
