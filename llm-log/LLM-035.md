## 模型回答

**一句话**:把厂商那份**已验证**的位流烧进同一块板读同一组寄存器,加上 PS7 参数**全量**
比对,得出一条与上轮相反的推论 ——
**根因不在 PS7 的配置里,只可能在 PL 侧**(或板子本身)。上轮的四条方向砍到两条。

四步,全部有实测支撑:

1. **AFI 假设作废**(→ 存档 §10.1)。`AFI0_RDCHAN_CTRL / ISSUINGCAP / RDDATAFIFO_LEVEL /
   WRCHAN_CTRL / FPGA_RST_CTRL` **五个读数逐条相同**(我方位流 vs 官方位流)。
   「位流改了 AFI 状态」不成立。

2. **🔴 推论:AFI 不可能是根因**(→ §10.3)。`ps7_init.c` 7450 行里
   **对 `0xF8008xxx` 一次写都没有**;而**位流无法写 PS 侧寄存器**
   ⇒ **任何位流烧进来 AFI 都停在同一默认值** ⇒ 厂商那份能工作则默认值可工作
   ⇒ **DECERR 不可能是 AFI 配错**。这条把上轮的方向表砍掉一半。

3. **PS7 参数全量比对:HP0 一处不差**(→ §10.4)。上轮只比了 6 个键,本轮把两份 hwh
   的 PS7 段全量比(979 vs 979),**不同 37 个,全部是 DDR PHY 训练参数 / `FCLK_CLK0_BUF` /
   `GP0` 使用 / `FTM_CTI`**。`S_AXI_HP0` 相关键 **0 处不同**。

4. **🆕 唯一找到的拓扑差异**(→ §10.5):官方 `axi4_rw_test/M_AXI → axi_smc → S_AXI_HP0`
   **过了 SmartConnect**;我方 `cv_sys_0/M_AXI → S_AXI_HP0` 是**直连**。

## 纠错轨迹

### ① 🔴 上轮的「十条已排除」里,有两条其实**没有排除力** —— 本轮自己把它撤了

上轮 §五 第 8、9 条:

```
8. AFI 读通道配成了 32 位 → afi0_rdchan_ctrl = 0x00000000 ⇒ 32BitEn = 0 ⇒ 64 位  ❌ 排除
9. AFI 发不出事务         → afi0_rdchan_issuingcap = 0x00000007(最大值)        ❌ 排除
```

本轮复测同一条 `qrs.bit`,**同两个地址读出的是 `0x00000000` 和 `0x00000007`** ——
可是存档里记的 `0xF8008024` 是 `0x00000F00`,`0xF8008010` 是 `0x0000001A`。
**同一块板、同一条位流、两个会话,读数不同。**

⇒ 这两个寄存器**读的是当时的活动状态,不是配置**。上轮把它们当"配置读回来核对"
**是错的**,连带的「解读」列(`0xF00` → "64 位读通道"、`26` → "队列里有 26 项")
也是**过度解读**。

**已在存档 §10.2 显式作废**,并说明第 8 条的**结论恰好仍成立**、但**理由要换**
(换成"官方位流也是 0"这个对照,而不是"读到 0 即 64 位")。

> **教训**:一个寄存器"读回来符合预期"**不等于**你知道它是什么。
> 先确认**读数是否稳定**(同条件复读一次),再拿它当判据。
> —— 这与 memory `verify-claims-not-intuition` 是同一条,但这次的形态是
> **「把活动状态寄存器当配置寄存器用」**。

### ② 🔴 上一轮的结论方向**是反的**,而推翻它靠的是"再找一个对照物"

上轮 §九 写:「问题被收敛到了一个点上:**PS7 的 `S_AXI_HP0` 端口本身**」。
本轮的 10.3 把这条推翻了 —— 根因**不可能在 PS7 配置里**。

推翻的方式不是重新推理,而是**多找一个对照物**:厂商那份位流。
上轮手上有它(`/tmp/lcd_ref/`)但**只用了它的 hwh 比 6 个键**,没有烧进去读寄存器。

> **教训**:手里有一个"已知能工作"的参照物时,
> **把它的每一个可读点都读一遍并与自己逐条对比**,比对着参数表逐个推理有效得多。
> 上轮比了 6 个键就停了 —— 而真正的差异(拓扑)不在参数表里,在**连接关系**里。

### ③ 🟡 上轮的一次「比参数」止步太早

上轮 §五 第 5 条的判据是「hwh 里 6 个 HP0 键逐条核过」。
本轮把 PS7 段**全量**比(979 键)才发现:参数表**确实一处不差** ——
**也就是说,答案不在参数表里**。

**这个"没有差异"本身是有价值的结论**(它把整张参数表排除掉),
但**只有全量比过才敢这么说**;比 6 个键说"配得一样",证据强度不够。

### ④ 🟢 本轮唯一"正面"的方法:拿**自描述数据**当判读指纹,而不是拿 LED 当判读

已知按一下 `PL_KEY0` 能让厂商例程跑一次。但**我不看 LED** —— 人眼看 LED 再转述,
是一层不可靠的转述。改用人可复核的物理量:

厂商 RTL 写的是**自增数**(`axi4_rw_test_v1_0_M_AXI.v:457-461`:`axi_wdata <= 1, 2, 3 … 16`),
落到 `0x10000000` 起 64 B。**先实测该处基线**(是 Linux 的 DTB:`0xEDFE0DD0 …`),
按完键再读一次 —— 变成 `1…16` 就是通,仍是 DTB 就是不通。

> **设计这个判据时问的是**:「这个观测量能区分我要区分的那两种情况吗,
> 而且**换一个观测者**(PS 读 DDR)能独立复核吗?」
> —— 与上轮沉淀的 `skill/counter-cannot-separate-content-from-count` 同源。
