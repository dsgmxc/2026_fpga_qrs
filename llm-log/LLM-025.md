## 模型回答

1. **分工**:源码写在**电脑上**的交付仓库 `qrs_fpga_2026/src/{rtl,hls,python}/`,**跑在板子上**。
   Jupyter 是**探索工具,不是交付物** —— notebook 住在板子的 `/home/xilinx/jupyter_notebooks/`,**不在 git 里**,
   调通后必须落成 `src/python/*.py`。
2. **不用从板子拷库** —— 板上 `pynq` 依赖 Xilinx runtime / `/dev/mem` / Zynq PS 硬件,
   拷到 x86 装不上也用不了;而 `baseline.py` 的立意就是**纯 Python 锁相**,本就不该依赖 PYNQ。
   电脑上装 `numpy/scipy/matplotlib` 即可。
3. **反对装 Python 3.8、反对升级板子的 Python**(见纠错轨迹第 1 条)。
4. **VS Code 插件清单**:Python / Pylance / Jupyter / Ruff / Verilog-HDL / C-C++ / Markdown / TCL;
   并**实测**报告了板子端口状态(`22` 不通 ⇒ Remote-SSH 不可用;`445` 通 ⇒ Samba 可用)。
   多根工作区 = 一窗口多挂载,价值在**跨目录全局搜索**(规格在 `qrs_2026_fpga/`,实现在 `qrs_fpga_2026/`)。
5. **继电器架构:PS → PL**(**已定,非新选择**),三条出处见下表。

## 纠错轨迹

### 1. 🟢 模型**否定用户的提议**(反向建议,本次最有价值的一条)

- 用户提议:「**那要不在装个 3.8 版本或者板子上的 python 能升级吗,这样不是很方便吗**」。
- 模型**两条都否**:
  - **升级板子** —— PYNQ 2.7 是**预构建镜像**,`pynq` 包 / Jupyter / 驱动都是对着
    **Ubuntu 20.04 + Python 3.8** 编译的;PYNQ 走**自己的 venv**
    (09-25 那条成功的 `sudo -E <venv>/python3` 就是它),动系统 Python 会**打断绑定**;
    而 Ubuntu 20.04 源里根本没有 3.9+,要升就得加第三方源在 ARM 上编译。
    **P2 刚跑通,风险与收益不成比例。**
  - **电脑装 3.8** —— 买到的只是「防止误用 3.9+ 语法」**这一件事**,
    而违反代价极低(板子上报个 `SyntaxError`,10 秒改完);换来的是**持续的环境维护成本**。
- **替代方案(更省)**:同一份源码两个解释器都能跑,约束只是**写作纪律**
  (避开 `dict | dict` / `list[int]` 注解 / `match`);
  且 **B03 的性能数据本来就必须在板子上出**,"推上板跑一次"是绕不开的步骤 ——
  **板子天然就是那个 3.8 裁判**,不需要在电脑上再养一个。
- **评价**:用户想用"统一环境"消除风险,模型指出**真正的风险很小、而统一环境的代价是持续的**。
  ⇒ **拒绝过度工程**的一个样本。

### 2. 🟡 模型主动暴露「文档与实际不符」

- 用户说「我在**工作区**写了继电器矩阵的 pl 端」。**「工作区」在本项目有特指**
  (`qrs_2026_fpga/` = 模型工作区;`qrs_fpga_2026/` = 交付仓库)。
- 模型**没有猜**,实测找到:`qrs_2026_fpga/src/rtl/swm.v`,今天 **17:11**。
- 顺带实测到一个**文档读起来比实际乐观**的缺口:
  **交付仓库 `qrs_fpga_2026/src/rtl/` 仍然是空的**(只有 `.gitkeep`)
  ⇒ 3 个已完成的 RTL + `swm.v` **全部只在工作区与 Vivado 工程里**,**M01 的缺口比状态文档写的大**。
- ⚠️ **模型自己的第三次同类失误**:第一次 `find` 用了 `-maxdepth 3`,
  把第 4 层的文件**全截掉了**,差点据此得出「仓库里没有文件」的否定结论;
  改用 `ls -la` 复核才发现。
  ⇒ **浅搜索得出的否定结论,在本项目已出现第三次**(前两次见 `LLM-012`/`LLM-021`)。
  本次新增一条具体形式:**`find -maxdepth N` 会静默截断**。
