## 模型回答

本轮产出**两份实测存档 + 一轮板上实验**,回答分三块:

1. **时钟口径被推翻**(→ `report/measurements/20261003_fclk0_real_measured.md`):
   2026-10-01 存档里的「FCLK0 实测 41.6667 MHz / IO PLL = 1500 MHz」**两条都是错的**。
   41.6667 是 PYNQ 按**假定的** IO PLL 1500 做除法得到的**计算值**,从来不是任何仪表的读数。
   本轮**首次用帧率法(独立时基)**实测:真值 **1000 MHz IO PLL**,开机默认 **27.78 MHz**,
   `apply_fclk0()` 后 **50.000 MHz**(帧率法复测 50.0594,偏差 −0.12%);
   并顺带结案遗留决策 **F2**:改频**必须在 `Overlay()` 之后**(`Overlay()` 会把
   `FPGA0_CLK_CTRL` 整个复位回 `BOOT.BIN` 的值)。

2. **全黑根因收敛**(→ `report/measurements/20261003_ddr_hp0_decerr.md`):
   把 `0x74` 从"纯拍数"改成"**低 18 位拍数 + 高 14 位内容证据**"后,**一次实测就把两个假设分开**:
   ```
   rresp_lat  = 11 (DECERR)    ← 每个响应都被拒
   axi_or_nz  = 0             ← 回来的数据全零
   px_or_nz   = 0             ← 行缓冲里什么都没有
   beats_cnt  = 153088~153600 ← 可是握手**满帧完成**
   ```
   **地址扫描 9 点无一例外**:含 `0x00000000`(OCM,必然可读)与 `0x40000000`(必然越界)
   ⇒ **拒绝在端口层面,与地址译码无关。** 十条假设被逐条钉死排除(§五),PL 侧全部洗清。

3. **板子整理**:按收尾提示词清理板上临时文件(26 项 → 16 项,`~` 58M → 46M),
   删除 4 份过期位流/无关 hwh、10 个根目录一次性判决脚本、5 个 `~/cv` 下一次性脚本、
   全部 `__pycache__`、0 字节 XRT 残留;两个明天要用的调试工具从 `/tmp`
   **收进工作区并改名**(`t_dbg.py` → `tools/lcd_ddr_debug.py`,
   `t_sweep.py` → `tools/lcd_fb_sweep.py`),避免 `/tmp` 被清后无处可取。

## 纠错轨迹

### ① 🔴 最有价值的一条:模型把「三条同源事实」写成了「三条相互独立证据」

2026-10-01 的存档断言「FCLK0 实测 41.6667 MHz / IO PLL = 1500 MHz」,并列了**三条证据**:

1. `1500/6/6 = 41.6667` 与 `Clocks.fclk0_mhz` 读数分毫不差 ⇒「41.6667 是真时钟」
2. 改频后寄存器**确实变了** ⇒「PYNQ 操作的是真硬件」
3. `1500/30/1 = 50.0` 与请求值吻合 ⇒「PYNQ 的请求是精确的」

**本轮复核发现第 1、3 条根本是同一个东西**:它们都是 `IO_PLL / DIV0 / DIV1`,`IO_PLL = 1500`
是 **PYNQ 内部的一个假定**(PYNQ 按 `PS_CLK = 50 MHz` 建模,而本板实为 33.333);
第 2 条只证明"寄存器被写了",**与 IO PLL 是多少无关**。

⇒ **三条证据实际上是"一个假定 + 一次写操作",一条独立证据都没有。**
**推翻方式**:帧率法 —— 帧几何是常量(`1344 × 635`),数出来的帧就是数出来的帧。
若 FCLK0 真是 41.6667,帧率应为 `41.6667e6/853440 = 48.82 Hz`;**实测 32.50 Hz**,差 50%。

> **教训**:「证据条数」不是强度指标,**独立性才是**。
> 三条都从同一个数出发,等于一条。

### ② 🔴 「拍数满帧」被当成了「通路正常」—— 握手 ≠ 数据

第 33 次位流测到 `DBG_BEATS = 153600`(**满帧**),当时的判读是"Axi 读通路没问题,
问题在读侧(乒乓/相位)"。**这个判读是错的。**

**DECERR 时 AXI 从设备会回全零数据,而握手照常完成** ⇒ 拍数一样是满帧。
只看拍数,「收到 153600 拍零」与「收到 153600 拍真图像」**读数完全一样**。

**改法**:把 `0x74` 拆位,加两个"内容证据"位(`axi_or_nz` / `px_or_nz`)与响应码锁存(`rresp_lat`)。
改完**一次实测**就把假设分开 —— 这是本轮唯一一次"改 RTL → 综合 → 上板"的循环,
而且是**先想清楚"哪个观测能把两种假设分开"再动手**,不是盲目加探针。

> **教训**:加观测前先问「这个计数器能区分我要区分的那两种情况吗」。
> **数个数量的探针,分不开"数量对、内容错"的故障。**

### ③ 🔴 模型把板子写挂死过 —— 教训已进 memory,但当时**没进记录**

排障过程中模型写了一个只读探测脚本 `t_rst.py`,其中**写了 SLCR 的 `FPGA_RST_CTRL`
(`0xF8000240`)**。在 **PL 侧有活跃 AXI 主机**的情况下拉 PL 复位,
**锁死了 HP 口并连带把 CPU 拖死** —— 板子当场失联。

**用户没有因此中断工作**,模型随后把这条教训写成 memory
(`never-poke-fpga-rst-ctrl-live`),并在 `drivers/board.py` 里落地为硬护栏:
`_SLCR_FORBIDDEN = (0xF8000240,)` 命中即抛 `BoardError`。
本轮后续所有 SLCR/AFI 探测**一律只读**(`t_slcr.py` / `t_afi.py` 的文档字符串里写死了这一条)。

> ⚠️ **本轮未做、明天要做的**:这次事故是否**遗留**了后果 —— 见下条。

### ④ 🟡 根因未找到,但模型**没有**编一个自洽的故事

`S_AXI_HP0` 为什么拒,本轮**没有答案**。模型的处理是:
把 §五 十条已排除项**逐条连证据一起列出**(包括"排除依据本身可能不成立"的那条),
把剩下的怀疑方向**排序成明天可执行的清单**,并明确指出
**「下一动作是断电重启,不是改代码」**。

**特别标注了一条自己的证据可能不可靠**:

> §五 第 6 条用「`FPGA_RST_CTRL` 读回 `0x00000000`」排除了"③ 的事故留下残留复位"。
> 但**读回值干净 ≠ 该寄存器控制的硬件已复原** —— 这条"排除"**保留**,直到断电重启验证过。

> **教训**:`DECERR` 是"从设备拒绝",不是"主设备算错"。
> **一个端口对所有地址返回同一种错误,答案通常不在地址上。**

### ⑤ 🟡 两次低级失误:`KeyError: 'source'`,因为假设了返回类型

`t_dbg.py` 里写 `lcd.clear_sticky()["source"]`,报 `KeyError`。
根因:`clear_sticky()` 返回的是 `self._mon.lcd_status()` 的**原始 dict**,
而 `LcdPanel.status()` 返回的是**合并后的增强 dict**(多一个 `source` 键)。
**两者名字像、都叫 status,返回形状不同。**

改法:拆成两条语句(`clear_sticky()` 然后 `status()`),**没有**去改驱动的返回值
—— 因为驱动侧那个选择是对的(清粘滞不需要解析)。

> **教训**:调用链上"看起来一样"的两个方法,返回值形状可能不同;
> **读一眼被调方的 `return`,比猜快。**

### ⑥ 🟡 一次自伤:拿板子上的路径去本地 `md5sum`

想核对位流一致性,写的是 `brd.run('md5sum .../impl_1/system_wrapper.bit')`
—— 那条命令**在板子上执行**,而该路径只存在于 PC。
报 `No such file`,一度被读成"位流不一致"。
改法:本地文件本地算,板上文件板上算,**再比 md5**。

### ⑦ 🟢 本轮唯一"正面"的设计判断:用**必然可读**的地址做对照

9 点地址扫描里特意放了 `0x00000000`(OCM,**必然可读**)。
若扫描只放 DDR 地址而全部 DECERR,仍可辩称"地址映射配错了";
**加了 OCM 这一行之后,这个辩解被当场封死**。
同样,越界的 `0x40000000` 也在里面,它的作用是证明"**界内界外读数一样**"
(⇒ 这一行**不能**用来证明"越界会 DECERR",已在存档里自我标注)。
