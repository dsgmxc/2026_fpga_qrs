## 模型回答

**推荐的方案(HP0 直连)** —— 理由三条:
1. **位宽**:HP0 可配 64 bit;GP0 经 `axi_smc` 只有 32 bit。一行 1024 像素 × RGB565 = 2 KB,
   64 bit 一拍 4 像素 ⇒ 256 拍/行;32 bit ⇒ 512 拍/行。行周期只有 1344 clk,**取一行要花 256/512 拍**,
   余量本来就紧 ⇒ 位宽直接决定余量。
2. **路径**:HP 是 PS 的**高带宽从口**,直连 DDR 控制器;GP 要过 `axi_smc` 互连。
   HP 少一级、时序可预期。
3. **代价**:HP 口**本来是给 DMA 用的**,占用后 PS 侧 DMA 不可用 —— 但本项目 PS 侧不走 DMA,
   **零代价**。

**本轮实际改动(四块)**:

| # | 文件 | 改动 |
|---|---|---|
| 1 | `lcd_fb_reader.v` | 新写(~250 行):行取数状态机 + 乒乓行缓冲 + 预取 + AXI 读主机 |
| 2 | `cv_sys.v` | 新增 `M_AXI` 端口组(41 根),接 `lcd_fb_reader`;补 `lcd_clk` 的 `X_INTERFACE_PARAMETER` |
| 3 | `system.bd` | `PCW_USE_S_AXI_HP0=1` / `PCW_S_AXI_HP0_DATA_WIDTH=64`;`cv_sys_0/M_AXI ↔ S_AXI_HP0`;地址映射 |
| 4 | 位流 | 综合 → 实现 → 生成 `.bit` + `.hwh` |

## 纠错轨迹

> 本轮两处都不是"看一眼就知道"的错 —— 都满足「**报错文本指向别处,真因在别处**」这个模式,故价值更高。

### 轨迹 A:`update_module_reference` **静默失败**,真因是模块引用缓存过期

1. **模型错在哪**:给 `cv_sys.v` 加完 `M_AXI` 端口后,模型在 BD 里 `delete_bd_objs` + `create_bd_cell` 重建 `cv_sys_0`,
   预期新端口自动出现。**结果:一个 `m_axi` 引脚都查不到,而且没有任何报错**。
2. **怎么发现的**:`get_bd_pins /cv_sys_0/*` 的输出里没有 `m_axi`,但 `cv_sys.v` 文件里的端口明明写着。
   **"文件里有、BD 里没有、且不报错"** —— 这个组合本身就说明中间夹着一层缓存。
3. **怎么查的**:模型先试的是 `update_module_reference`(Vivado 官方用来刷新模块引用的命令),
   发现它**存在但不可用**:不带参数、`-quiet`、绝对路径、`current_bd_design` 四种写法**全部返回 rc=1 且错误信息为空**。
   ⇒ 转去查缓存目录,找到 `qrs.gen/sources_1/bd/mref/cv_sys/component.xml`,
   **时间戳 `10月 1 17:04`** —— 正是上一次打开 BD 的快照,**早于本次 RTL 改动**。
4. **怎么改的**:
   ```
   rm -rf qrs.gen/sources_1/bd/mref/cv_sys qrs.runs/synth_1/.gen/sources_1/bd/mref/cv_sys
   ```
   然后再 `delete_bd_objs` + `create_bd_cell` ⇒ `/cv_sys_0/M_AXI` 出现,**41 根引脚**。
5. **改完还有没有问题**:有。这一条**只在下次改端口时才暴露**,而且**症状是"没有症状"** ——
   缓存过期不会报错,只会让 BD 拿旧端口表干活。已写进 `docs/display_subsystem.md §6.2b` 作为固定动作。

### 轨迹 B:AXI4 / AXI3 协议不匹配 —— **从"能连上"退到"必须改 RTL"**

1. **模型错在哪**:模型把 `M_AXI` 声明成 `PROTOCOL AXI4`、`m_axi_arlen` 写成 **8 位**、
   `MAX_BURST_LENGTH 256` —— 按 AXI4 的规格写的(更宽、更省事)。BD **直接拒绝连线**:
   ```
   ERROR: [BD 41-1285] The protocols of the interfaces '/cv_sys_0/M_AXI'(AXI4)
          and '/processing_system7_0/S_AXI_HP0'(AXI3) are incompatible.
   ```
2. **怎么发现的**:BD validate 直接报错。**这一条是工具主动拦下的,不是模型自查发现的。**
3. **怎么改的** —— 关键在于**改哪一边**。摆在面前两条路:
   - **路 A**:插一个 `axi_protocol_converter`(AXI4→AXI3),BD 里两行 Tcl 搞定,**RTL 一行不动**
   - **路 B**:把 `lcd_fb_reader` **改成原生 AXI3** —— `arlen` 收成 4 位、一行 256 拍拆成 **16 次 × 16 拍**、加突发序号计数器

   **模型选路 B**,理由:**HP 是实时通路,每行有硬截止期**(消隐只有 320 clk ≈ 6.14 µs @50 MHz,
   而取一行要 256 拍,余量本来就按拍算)。`axi_protocol_converter` 是**变延迟 IP**,
   把它插在一条按拍数算余量的通路上,等于**用一个不可预测的延迟换十几个 LUT 的计数器** ——
   这笔交易在别处划算,在这里不划算。**这条判断写进了 RTL 头注释和 `display_subsystem.md §6.2`**,
   属于 B04「资源取舍论证」/ B06「设计判断依据」的正文素材。
4. **改完还有没有问题**:有,且模型**主动标了出来**:16 次突发是**串行**发起的
   (不叠多笔 out-standing),估算 16 ×(AR 握手 + 16 拍 + 尾巴)≈ **300–900 cycle**,
   行周期 1344 clk ⇒ **估算是够,但没有实测**。已在代码内写死一句:
   **若板上 `LCD_FB_STATUS[19]`(underrun)** 真的置起来,**这里就是第一个该改的地方**。

### 轨迹 C:测试台的**编译期错误 + 陈旧结果回放**(差点骗过自己)

1. `ERROR: [VRFC 10-3236] concurrent assignment to a non-net 'm_arready'` —— 声明成 `reg` 却用了 `assign`,改 `wire`。
2. `ERROR: [VRFC 10-3380] identifier 'm_arlen_r' is used before its declaration` ——
   声明挪到引用之前。**这是本项目反复踩的同一个坑**(`cv_sys.v` 早先也栽过)。
3. 🔴 **最有价值的一步**:第 2 个错误修完重跑,`xelab -R` **打印出了上一轮的 PASS 输出** ——
   因为编译根本没成功,跑的是**旧的可执行文件**。之所以没被糊弄过去,是因为模型注意到
   **新加的那行「ARLEN 越界」没出现在输出里** ⇒ `rm -rf xsim.dir` 重来。
   ⇒ 「**输出比预期少一行**」和「**输出报错**」一样是信号,而且更隐蔽。
