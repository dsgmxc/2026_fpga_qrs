# LLM-059: Q31 结案 —— `0x1C` 写入异常的根因不在 PL,在 PS 的一行 Python 写法

- **日期**: 2026-10-10(接 LLM-058 之后,同一天;第 54 次会话)
- **模型**: DeepSeek-V4-Flash
- **任务**: 用户上电后,定位 Q31(`写 `0x1C` 继电器寄存器表现为两次 set 脉冲、硬件停在 `0x00`)的根因,
  并修掉它

## 提示词

```
上电了
```

**前提**(同一天早先授权,`CLAUDE.md` §6.0 显式例外):

```
后面代码都归你写,先关系统我断电,你写完再叫我上电测试
```

本轮全部排查均由模型在板上自动执行(SSH + paramiko 脚本),**用户只做了「上电」这一个物理动作** ——
与授权边界一致:代码归模型,物理动作归用户。

## 模型回答

**根因:PS 侧的 `struct.pack_into(fmt, mmap, off, v)` 对一个 Python `mmap` 会发出两笔 AXI 事务,
第一笔是常数 `0x00000000`。** PL 完全无辜。

完整机制:

| 步 | 事件 |
|---|---|
| ① | `struct.pack_into` 发出第一笔写,数据 = `0x00000000` |
| ② | 从机忽略 `WSTRB`、照单全收整字;`0x00` 恰好在继电器白名单里(`COSS_DISCHARGE`) |
| ③ | 该写被**受理** ⇒ `relay_reg ← 0x00`,并锁 **40 ms** busy(settle 互锁) |
| ④ | 第二笔(真值 `0x61`)撞 `ERR_BUSY`(`0x03`),被拒 |
| ⑤ | 硬件停在 `0x00` —— 与写入值无关、与寄存器原值无关 |

⇒ **修法一行**:`relay.py::_DevMemRegs.write` 从 `struct.pack_into` 改成切片赋值
`self._map[off:off+4] = value.to_bytes(4, "little")`。

> **为什么只有 `0x1C` 出问题**:它是唯一带 settle 互锁的命令寄存器。其余寄存器
> (`0x18`/`0x24`/`0x60`/`0x84`…)同样会吃到那笔 `0x00`,但没有互锁 ⇒ **后写覆盖前写** ⇒ 看不出来。
> 另:`0x00` 若不合法,第一笔会被直接拒 ⇒ **这个缺陷根本不会存在**。症状落在哪个寄存器上,
> 有时是白名单与互锁的巧合。

## 结果

☑ ✅ 直接可用

## 验证方式

**全部为板上实测**,位流 md5 `9613c2928a01f832b71aef7c45c4c0b9`,同一份位流、同一次上电。

1. **公平四路对照**(写 `0x1C = 0x61`,每例前先清 busy 并核对基线 `relay=0x10 / err=0x00`):

   | 写法 | 结果 |
   |---|---|
   | `pynq.MMIO` 整字写 | `0x61` / err `0x00` ✅ |
   | 裸 mmap 单字节 `m[0x1C]` | `0x61` / err `0x00` ✅ |
   | 裸 mmap 切片赋值 | `0x61` / err `0x00` ✅ |
   | **`struct.pack_into`** | **`0x00`** / err **`0x03`** ❌ |

2. **把 settle 置 0(拆掉互锁)后四种写法全部得到 `0x61`** ⇒ 最后一笔是对的,
   问题是**笔数**,不是"值送错"。
3. **六组遍历**(基线 `0x10`/`0x61`/`0x7F` × 载荷 `0x61`/`0x7F`/`0x00`)⇒ **全部 `0x00` / err `0x03`**
   ⇒ 与基线无关、与载荷无关 ⇒ 第一笔是**常数零**,不是"读-改-写"。
4. **证人寄存器**:`wr(0x4C, 0x11223344); mm[0x4F] = 0xAA` → 读回 **`0xAA223344`**
   ⇒ 窄写被模拟成读-改-写(实测,非推测)。
5. **修后回归**:`tools/relay_rw.py --diagnose`,**两个后端各跑一遍**,均 **`结果:全部通过`**
   (★0 触发条件 2/2 · A 11/11 · B 3/3 · C 6/6 · D1 5/5 · D2 6/6 · E 实测 40.2 ms / 100.4 ms)。
6. **同进程修前/修后对照**(最干净的归因):同一个类、同一次上电,只把 `write` 换成
   `struct.pack_into`,7/7 通过立刻翻转成 3/3 失败 —— **一行代码切换两种结果**。

证据存档:`report/measurements/20261010_relay_cfg_write_anomaly.md` §10(§9 是那处矛盾)。

## 纠错轨迹

> 本轮**模型自身的错误至少 7 处**,其中 2 处直接把排查方向带偏、1 处浪费了一整个上电轮次。
> 这是本项目迄今**单位时间纠错密度最高的一次**。

1. **★ 最大的一处:把 `0x48` 当 SCRATCH 用。** 第一个机制探针脚本(`mech.py`)拿 `0x48`
   当证人寄存器,结果**无论写什么,读回来永远是 `0x48`**。当时的第一反应是"写不进去",
   差点又去查 PL。
   **发现方式**:去读 `src/python/cv_regs.py` 的寄存器表 —— 它**一直是对的**(`:125-126`),
   `0x48` 是 **VERSION(RO,恒 `0x00010000`)**,`0x4C` 才是 SCRATCH。**是我看错了表。**
   **改法**:全部改用 `0x4C`,并把"证人寄存器必须先自证是 RW 的"写进 `skill/`。
   **后果**:浪费一轮上电;但它顺带产出了那条 RMW 实测(`0xAA223344`)。
2. **★★ 第二处带偏方向的:断言"两条后端的映射属性不同,不能互相代表"。**
   LLM-058 里我据此把范围划成"PS 写通路",并**计划挂 ILA(要重建位流)**。
   **发现方式**:去读了 PYNQ 源码 —— `pynq/pl_server/embedded_device.py:523`,
   两条路**都是** `open("/dev/mem", O_RDWR|O_SYNC)` + `mmap(MAP_SHARED, PROT_READ|PROT_WRITE)`。
   **映射属性完全相同,差别在写下去的位宽/笔数。**
   **这条错判是本轮最贵的**:它让我在 ILA 方案上停留了一段时间。已在
   `20261010_bd_smartconnect_inspection.md` §4 就地标注为**错的**。
3. **假设"从机 honors WSTRB"。** 由 A 节现象(`m[0x1F]=0x00` 能让 busy 位起来、
   但 `relay_reg` 不变)反推。**被 grep RTL 证伪**:`s_axi_wstrb` 只出现在端口声明 `:157`,
   全文再无使用 —— 从机**忽略** WSTRB。正确解释是那个 RMW 模拟(读回的是寄存器现值 `0x10`,
   再整字写回,于是 `relay_reg` 看起来"没变")。
   📌 **教训**:我是先有解释、再去验证的,顺序反了;若先 grep 一行就没有这条。
4. **第一版 `struct.pack_into` 对照不公平。** settle = 40 ms,而两次写法之间只隔几十毫秒
   ⇒ 可能是**上一轮的 busy 残留**在起作用,不一定是写法本身。**重做**:写 `mech3.py`,
   每例前显式清基线并核对。**缺陷在公平协议下依然复现** ⇒ 结论是真的,但**第一版数据不可用**。
5. **`tools/relay_rw.py` D 节出现 5 个假失败。** `set_gear()` 在 Python 侧就校验并抛异常,
   **根本走不到硬件** ⇒ `err` 永远是 `0x00`,不可能等于期望的 `0x02`。
   **顺带查出一个真问题**:RTL 的 `ERR_GEAR` 分支**从来没有被任何测试走过**。
   **改法**:拆成 **D1**(Python 护栏:必须抛且硬件不受影响)与 **D2**(新增 `gear_write_raw()`
   绕过 Python 校验,逼 RTL 拒收)⇒ D2 **6/6 通过,这是该分支第一次被验证**。
6. **`section_trigger` 结束时硬写 `r.workaround = True`** —— 会把调用方的 `--workaround`
   选择覆盖掉(A 节因此一度在绕法下跑过)。**改法**:存-还。
7. **`--no-fix` 语义在默认值翻转后反转。** 默认从 `True` 改成 `False` 后,
   `workaround=not args.no_fix` 会**强制打开**绕法。**改法**:换成 `--workaround`,
   `workaround=args.workaround`。
8. **两处我自己写的"绕过"其实一直无效。** `_write_relay` 的绕法掩码写的是
   `orig & 0xFFFF_0000`,**与它的注释恰好相反**(注释说保留高 16 位,实际保留低 16 位获得高)。
   **它"看起来能用"是因为只被 `pynq.MMIO` 后端用过,而那个后端本来就不需要绕法。**
   ⇒ 已随根因一并删除,并把 `WORKAROUND_0x1C` 置 `False`。

**这轮还顺带推翻了 LLM-058 的一处自我怀疑**:LLM-058 里我读过 `cv_axi_lite_slave.v` 的
写桩并说"四种情形逐拍推演都得一笔一个脉冲,推不出结论" —— **那个推演本来就是对的**。
PL 确实是一笔一个脉冲,与它推演的一致。
