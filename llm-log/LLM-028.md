## 模型回答

**① `cv_sys` v2 设计(用户授权后动手,CLAUDE.md §6.0 例外)**

- `cv_axi_lite_slave.v` 加 `0x50 LCD_CTRL`(`[0]src_sel`)与 `0x54 LCD_FILL`(`[23:0]` RGB888),
  写通道由 if-else 链改为 `case`(与读通道写法一致,便于续扩);
- 关键设计选择:**`LCD_CTRL` 复位值 = 0 = 厂商彩条**。这样"搬进 `cv_sys` 后 LCD 没坏"那次回归
  **变成免费保留的**,不必专门停一步看彩条 —— 直接回应了用户"能不能跳过彩条验证"的诉求;
- `cv_sys.v` 只做一级像素源 mux,**`lcd_display` / `lcd_driver` 一行未改**。

**② 用户写 `main.py`,模型只做最小 diff**

用户自己写完了链路自检部分。模型**实测**(不是目测)发现 `main.py:16-17` 的 f-string 跨行折断:

```
$ python3 -c "import ast; ast.parse(open('main.py').read())"
SyntaxError -> unterminated string literal (detected at line 16)
```

改为一行,并追加第 3 段(三色切换 + 切回彩条)。

**③ FCLK0 实测**

`Clocks.fclk0_mhz` 读出 **41.666667**,而 BD 里写的是 **50.000000**。
经三轮寄存器实测,确认 **41.6667 是真时钟**,且 PYNQ 可在运行时改到精确的 50 MHz。

## 纠错轨迹

> 本轮共 **7 处错误**,其中 **6 处是模型自己的**。这是目前单次会话里错误密度最高的一次。

### 1. `cv_sys.v` 隐式声明 bug —— **由工具抓到,不是模型发现**

把 `cfg_lcd_ctrl` / `cfg_lcd_fill` 的 `wire [31:0]` 声明写在了从机例化**之后**。
Verilog 对未声明标识符做隐式声明 ⇒ 它们被当成 **1 位 wire**,与例化端口位宽冲突:

```
ERROR: [VRFC 10-2938] 'cfg_lcd_ctrl' is already implicitly declared on line 132
ERROR: [VRFC 10-8530] module 'cv_sys' is ignored due to previous errors
```

**怎么发现的**:模型跑 `xvlog` 做语法检查时**顺手抓到**的 —— **不是靠读代码发现的**。
如果跳过这步直接综合,Vivado 也会报,但会在更晚、更难定位的地方。

**怎么改**:把声明移到例化之前,并加注释块写明"未声明的标识符会被隐式声明成 1 位"。
改后 `xvlog` 4 模块 0 错 0 警,`xelab` 快照干净。

**沉淀**:这条是 **Verilog 声明顺序**的通用坑,与 `skill/verilog-integer-defaults-to-x/` 同族。

### 2. 误判 `io.xdc` 的约束是启用的

模型 `grep` 到 `io.xdc` 里有 LCD 行,断言"这些约束生效了"。
**用户纠正:「io我设置禁用了啊,现在生效的应该只有led才对」**。

**根因**:模型只 dump 了 `<File>` 元素的 `attrib`(只有 `Path`),
**没看子节点 `FileInfo/Attr`** —— `UserDisabled = 1` 就在那里。
"没看到"被当成了"不存在"。

**改法**:把 XML 原样打印出来重看,确认状态其实很干净。

> ⚠️ 这是本项目**同一类错误的第 N 次**(`skill/no-all-negative-from-shallow-search/`):
> **浅搜索得出的否定结论**。本次新增一种具体形式:**只查元素属性、不查子节点**。

### 3. 把工作区 README 当成交付仓库 README,编出两条不存在的"漂移"

模型对用户说:"`README.md` 的目录结构已经对不上了 —— 里面写着 `CLAUDE.md` 和 `Task_Requirement/`……"

**实际**:那条 `cat README.md` 是在 **cwd 被 Bash 工具重置到工作区之后**跑的,
读到的是 `qrs_2026_fpga/README.md`(工作区),不是 `qrs_fpga_2026/README.md`(交付仓库)。
工作区里**确实有** `CLAUDE.md` 和 `Task_Requirement/`,所以那份 README **没写错**。

**交付仓库的 README 是干净的那份**,两条"漂移"里的一条**整个是虚构的**。

**怎么发现的**:用户说"去更新文档吧",模型准备动手前重读文件,发现 Read 出来的内容和之前 `cat` 的不一样。

**教训**:Bash 工具每次调用后 cwd 会重置,**相对路径的 `cat` 读到的可能不是以为的那个文件**。
跨目录操作**必须用绝对路径**。

### 4. 按错了寄存器的位定义去解码

模型对 `FPGA0_CLK_CTRL = 0x00600600` 解码,得出 `ACT=0`(时钟关闭),
并据此说"这和屏幕在亮矛盾"。

**实际**:`FPGA0_CLK_CTRL` **没有 `CLKACT` 字段** —— 那是 `UART_CLK_CTRL` 一类的寄存器才有的。
模型**按记忆套了别的寄存器的布局**,并且把 `[3:0]` 这些**保留位**当成了有效字段。

**怎么发现的**:解码结果与实际现象矛盾 → 模型**没有强行解释,而是去搜 TRM 的准确位定义**,
搜到后发现自己的解码根本不成立,主动作废(`ACT=0` 那条结论已声明作废)。

### 5. "41.667 是复位默认值" —— 基于一个没验证的常数

模型算:`复位值 0x00101800 → DIV0=24, DIV1=1 → 1000/24 = 41.6667`,于是宣称
"41.667 恰好是出厂默认,说明 `ps7_init` 从没碰过 FCLK0"。

**实际**:这个推导**默认了 IO PLL = 1000 MHz** —— 而这个常数**模型从来没有验证过**。
实际 IO PLL = **1500 MHz**(由三个独立数据点反推一致)。复位值对应的是 **62.5 MHz**,不是 41.667。

**怎么发现的**:用户改频后寄存器从 `0x00600600` 变成 `0x00101e00`,
模型解出新值 `DIV0=30/DIV1=1`,用 1000 去算得 33.33(与请求的 50 不符),
**两个数据点对不上同一个 PLL 值** ⇒ 回头发现前提错了。

**正确的推导**(三条相互独立的事实):
| 时刻 | 寄存器 | `DIV0` | `DIV1` | 反算 PLL |
|---|---|---|---|---|
| 改前 | `0x00600600` | 6 | 6 | 41.6667 × 36 = **1500** |
| 改后 | `0x00101e00` | 30 | 1 | 50.0 × 30 = **1500** |
| 且 | PYNQ 请求 50 MHz 时**自己写入 `DIV0=30`** | | | 50 × 30 = **1500** |

### 6. 编造板上 Python 版本

模型修 f-string 时说:"板上 PYNQ 镜像(PYNQ 3.0 / Ubuntu 22.04)也是 **Python 3.10**,上板必挂"。

**实际**:`docs/project_state.md` 里白纸黑字记着 **PYNQ 2.7.0 / Python 3.8.2**(2026-09-25 实测)。
模型**没有去查已经记录过的实测值,而是凭印象说了个版本号**,并且用了"已核实"的语气。

**结论方向没变**(3.8 比 3.10 更不支持跨行 f-string,那个 `SyntaxError` 照样必挂),
**但引用的版本是错的** —— 在报告里会变成一处硬伤。

**怎么发现的**:模型自己在写 `docs/dev_workflow.md` §3.1 时去核对板上版本,发现对不上。
