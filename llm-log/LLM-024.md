# LLM-024:串口控制台登录 + 电脑↔板子直连网线打通(Jupyter 可达)

- **日期**: 2026-09-26
- **模型**: Claude(Claude Code)
- **任务**: ① 给出串口工具登录板子的方法;② 用户插上网线后,把电脑与板子之间的直连链路配通使 Jupyter 可访问;
  ③ 排查过程中出现的「ping 不通」与「`_xsrf` 报错」。

> **⚠️ 证据边界**:上板操作**全部由用户执行**,模型未接触板子。
> 但**电脑侧的全部诊断由模型实测**(`ip` / `nmcli` / `/dev/tcp` 探针),这部分是第一手证据。

## 提示词

```
怎么使用串口工具登陆来着

现在我有网线连接开发版了
（粘贴 ifconfig：eth0 无 IPv4，eth0:1 = 192.168.2.99/24）
fixfox显示网络激活失败

（粘贴，实际在板子上执行了电脑侧的命令）
sudo nmcli con add … → 成功
ping -c 3 192.168.2.99 → 全通

（粘贴）警告：存在其他 1 条带有名称 "pynq-direct" 的连接 / ^C

（粘贴）错误：ipv4.addresses: "method=manual" 不允许这个属性为空

（粘贴）连接已成功激活 / enp2s0 UP 192.168.2.100/24 / ping 通

登陆进去了

怎么突然又ping不通了，是ip变了吗

运行历程显示'_xsrf' argument missing from POST
```

## 模型回答

1. **串口工具**:`picocom -b 115200 /dev/ttyUSB0`(本机已装 picocom,minicom/screen/tio 均无;
   用户在 `dialout` 组故无需 sudo)。参数与凭据全部出**指南 p22 原文**:115200 / 8 / 1 / No Parity /
   No Flow Control,用户名 `xilinx`、密码 `xilinx`。并核对了 P5 跳帽、SD CARD 启动模式两项前置。
2. **链路诊断**:板子侧 `eth0` **无 IPv4**(DHCP 拿不到)、`eth0:1` = **192.168.2.99/24** 静态;
   电脑侧 `enp2s0` **carrier=1** 但 NM 报 `disconnected`、**无 IP** ⇒ 定位为**电脑端缺地址**,
   并解释了「网络激活失败」的来源(旧配置 `有线连接 1` 以 DHCP 模式占着 `enp2s0`,链路上无 DHCP 服务器)。
3. **给配置**:新建 `pynq-direct` = 静态 `192.168.2.100/24` + **`ipv4.never-default yes`**(保住 WiFi 默认路由)
   + 关掉旧配置的 autoconnect(避免两条配置抢同一张卡)。
4. **硬验证**:不满足于 ping 通 —— 追加 `ip r get` 与 `ip neigh`,用
   **ARP 里 `lladdr 00:0a:35:00:22:01` 与板子 `ifconfig` 的 `ether` 逐位一致**坐实「包真的到了板子」。
5. **`_xsrf` 报错**:判定为**浏览器标签页在断网期间持有过期令牌**(与板子、与项目代码均无关),
   修法是 `Ctrl+Shift+R` 硬刷新;并提醒别跨断网/跨板子重启长时间开着标签页、别用两个地址访问同一台 Jupyter。

## 纠错轨迹

### 1. 🔴 指令没写执行位置 ⇒ 用户在**板子**上跑了电脑侧的命令

- 模型给出 `nmcli con add … ifname enp2s0 …`,**没写明在哪台机器执行**。
  用户当时正停在板子的串口控制台(`xilinx@pynq:~$`),直接敲了进去。
- **后果**:板子上根本没有 `enp2s0` 这张网卡 ⇒ 建了个绑不到设备的废配置;
  紧接着的 `ping 192.168.2.99` **是板子在 ping 自己** —— `0.104 ms` 的**环回速度**被当成了"通了"。
- **怎么暴露的**:模型核对提示符发现是 `xilinx@pynq`,而非电脑的 `hyp@hyp-GTR`,拆穿了假象。
- **教训(两条)**:
  ① 跨机器协作时,**每条命令必须自带执行位置**;
  ② **ping 通不等于链路通** —— 要验"包到没到对面",看 ARP / 路由,不看 ping。

### 2. 🔴 两台机器用了**同名**连接 ⇒ 一条"在板子上执行"的指令落到电脑上,把配置删了

- 链路打通后,模型让用户"顺手清掉板子上那条废配置",命令是 `nmcli con delete pynq-direct`。
- 用户**在电脑上执行了** —— 因为**两台机器的连接同名**,
  一条"板子侧"的清理指令在电脑上**语义完全成立**,于是把刚配好的 `pynq-direct` 整个删掉了。
- **症状**:用户报「怎么突然又ping不通了」。**模型实测**:`enp2s0` 无 IP、NM 连接名为空、
  路由里 `192.168.2.0/24` 消失、ARP 表空 ⇒ 确认是**配置被删**,不是 IP 变了。
- **修复**:按已跑通的顺序重建(6 条短命令),重建后 `enp2s0 UP 192.168.2.100/24`,ping 通。
- **根治**:① **停发板子侧的非必要命令**;② **跨机器不复用连接名**。
- **教训(可复用)**:「无害的清理动作」**在另一台同名机器上可能是有害的** ——
  命名冲突会让**正确的指令执行在错误的机器上**。

### 3. 🔴 `ipv4.method manual` 与 `ipv4.addresses` 拆成两行 ⇒ nmcli 校验不过

- 模型给的是两条独立命令:`con mod … ipv4.method manual`,然后 `con mod … ipv4.addresses …`。
- **实测报错**:`ipv4.addresses: "method=manual" 不允许这个属性为空`。
- **根因**:**nmcli 是「设一次校验一次」** —— 切到 manual 的那一刻地址必须已有值,
  拆开写**在顺序上注定失败**,不是操作失误。
- **改法**:先用 `+ipv4.addresses` 把地址**追加**进去(此时仍是 auto 模式,合法),**再**切 `ipv4.method manual`。
- **附带发现的环境因素**:**用户终端/粘贴在约 65 字符处折断长行**,
  把一条长命令劈成两半(后半截被当成独立命令执行,报「未找到命令」)。
  ⇒ 后续所有命令改为**短行**,整块粘贴时每行独立成命令。
