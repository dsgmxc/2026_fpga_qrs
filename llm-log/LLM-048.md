`0x8C/0x90/0x94/0x98` 在**全工程零行读取代码**,只有宏定义与注释。

**改动清单**(新增 2 文件 / 改 5 文件,`Makefile` 未动 —— `$(wildcard app/*.c)` 自动收新文件):

| 文件 | 改什么 |
|---|---|

| `app/main.c` | `dump_stats()` 补一行 `ADC 采集 成功/失败` |

**数据流**:

```
DisplayProtocol_Process()
  └─ 单点:等偏压稳定 s_dwell_ms → adc_capture_pair() → 250 点喂 kind 0 → 填卡片 → 刷新
  └─ 扫压:sweep_step() ①先收尾**上一个**点(它的偏压已稳定整一个驻留)
                             ②再写下一个点的偏压
          → 每点 UI_Demo_UpdateSweepPoint(…, cs, 0, 0, model_valid=0, …, valid)
          → 每点 UI_Demo_UpdateWaveformPoint(kind 1, index, total, volts, cur_ma, txt)
```

**「两路」是怎么来的 —— 本轮最关键的实现决定**:
`adc_capture.v` 里 `adc_clk = (cnt < P/2)`、`tick = cnt − P/2` ⇒ **上升沿 = tick −P/2**、
**下降沿 = tick 0**。用户口径定为「上升沿=通道 A、下降沿=通道 B」。但
**一次 GO 只锁存一个 tick** ⇒ "两路"只能用**两次采集**拿到(先 `PushPhase(−P/2)` 采 A,
再 `PushPhase(0)` 采 B)。**不需要改 RTL、不需要重下位流。**

⇒ 代价必须如实写进代码与文档:**A、B 是两次独立采集,GO 时刻任意,两路之间的相位差是随机的**
⇒ 只能比**幅值**,`Cs` 按"被测件是纯电容"由幅值比算出(且 `R_tia` 未标定),
**`Cp` 与 `D` 一律显示 `--`**(填上去等于编数据)。要真正同时采,须给 `adc_capture` 加第二组缓冲
+ 重综合 + 重下位流 —— **本轮不做**,记为后续项。

> 本轮四次自我纠错,**其中两次是"差点把对的改成错的"**。

5. ★★ **照抄用户口径的刻度,而我们自己的实测早就写了不是那回事 —— 两路认反了。**
   用户口径是「**上升沿是通道 a 数据下降沿是通道 b 数据**」。我把它直译成了刻度:
   `AdcSample_RisingTick(div) = −(P/2)`、`AdcSample_FallingTick() = 0`,代码全写完、构建通过。
   **收尾复核时去翻本工程自己的实测记录**(`LLM-045` §G),
   发现 §G 早就坐实那 12 位总线是**双端口时分复用**、两路各占半个周期:

   | 端口 | 窗口(tick) | 中心 |
   |---|---|---|
   | A = INA | `[2 − P/2, +1]` | `1.5 − P/4` |
   | B = INB | `[+2, P/2 + 1]` | `1.5 + P/4` |

   ⇒ **tick = −P/2 落在 B 窗、tick = 0 落在 A 窗 —— 两路正反了**;
   而且两者都**贴窗沿**,不是中心(P=13 时 A 窗 `[−4.5,+1]`、B 窗 `[+2,+7.5]`,
   `−6` 是 B 窗最外沿、`0` 是 A 窗右沿)。
   更要命的是**它不会报错**:两个刻度都在合法范围内、都能采到稳定的数,
   **只是把 INA 的数当成"电压"、INB 的数当成"电流"画了出去** —— 数据是真的,
   归属是错的,屏上看不出任何异常。

   **修法**:新增 `AdcSample_PortATick(div)` = `cv_adc_phase_center(div)`(与既有 `PH_OFF`
   默认值**同源**,不另算一份)、`AdcSample_PortBTick(div)` = `cv_adc_phase_center_b(div)`
   (新增在 `pynq_regs.h`,`1.5 + P/4` 同一条半远离零舍入规则,并**折回**寄存器合法范围),
   另加 `AdcSample_TickLegal()` 在推刻度前先查 —— 越界刻度的现象是 `done` **不置位**,
   不查的话很容易被误判成"位流不对"。
   **验证**:五个可选档位(P = 130/65/26/13/10)逐个核对**两个中心都落在各自窗口内**,
   且 A 的三个中心与已实测的 `−2 / −5 / −31` **逐位吻合**;`P=2` 那档确实越界,
   由 `TickLegal()` 挡住并给出"换档位"的可执行提示。
   ⇒ 📌 **"用户这么说"是需求,不是参数。** 需求照做(就要两个真实输入、就要两张图),
   **但把需求翻译成寄存器刻度时,必须回到本工程自己的实测结论去核**,尤其是那条结论
   就是上一场自己写的。

   且 `cv_regs.py::C_UI_BINARY` 默认就指向它 ⇒ **服务直接 `start` 即可,不用传 `--ui-bin`**)
4. `systemctl start qrs-ui.service` → 一次加载位流,屏上出界面
5. 用户点屏驱动:单点一次 → 扫压一轮(60 点);我每步抓 `[adc]` 日志 + `fb_dump.py` 抓帧缓存
6. 裸 `/dev/mem` 探针核 `0x88`(结论见验证表第 13 条)

**⚠️ 踩到的一条边界(下次别慌)**:`/var/log/qrs-ui.log` 是 **append 的、跨上电周期不清**,
里面有**好几轮历史的启动横幅**;`grep "PS 侧启动"` 会看到多次、`grep "收到退出信号"` 也有多次
—— 看起来像"main.py 反复重启"。**判据不是数日志横幅,是 `dmesg`**:
`dmesg | grep -i fpga` 里 `writing qrs.bin` 的**条数**才是这个上电周期真正的位流加载次数。
本次 = **1 条**,所以安全。

## 附:G. 板上发现的两处「看屏会误会」(不影响功能,记待改)

### G.1 `扫压波形` 的电流包络是 0 线,而 `单点波形` 的电流是 ~1990 μA

**两个页面画的不是同一个量**:

| 页面 | 电流含义 | 悬空输入下的表现 |
|---|---|---|
| `单点波形`(kind 0) | **缓冲里的原始采样** ÷ `R_TIA` | ~1.99 V / 1 kΩ ≈ **1990 μA**(直流电平) |
| `扫压波形`(kind 1) | **1 MHz 解调幅值** ÷ `R_TIA` | **≈ 0**(无激励分量) |

判据:单点喂的是 `AdcSample_CodesToVolts(s_code_b[i])`(逐点原始码),
扫压喂的是 `s_pair.cur_ma` = `mag_b_v / R_TIA × 1000`(解调**幅值**)。
⇒ **不是 bug** —— 对 C-V 测量,解调幅值才是物理上有意义的量;
但同一套界面里"电流"有两种含义,应当**在图上标清**(改法:标题写成
「回路电流包络 / 10 μA @1 MHz」之类),否则第一眼会读成"采样坏了"。

### G.2 日志打「幅值 0.0000 V」而 `Cs` 非零 —— `%7.4f` 把 1e-5 V 抹成 0

`adc_log_pair()` 用 `%7.4f` 打 `mag_a_v` / `mag_b_v`,而 `AdcSample_CsPf()` 用的是
**没舍入的浮点**。悬空输入下幅值在 1e-5 V 量级 ⇒ 打出来是 `0.0000`,而 `Cs` 是 64 pF
—— **同一行字看起来自相矛盾**。
⇒ 改成打 **mV**(`%9.4f` 配 `×1000`)或直接打**原始码**,一行就自洽。

两条都**只影响可读性,不影响任何功能或数值**。本轮**未改**(避免在"刚验完"的版本上再动刀,
留出干净的复现基线);改法与理由已写死在这里,下一轮直接动手。
