# LLM-023:P2 头号风险解除 —— Vivado **2025.2** 的 `.hwh` 能被 PYNQ 2.7 完整解析

- **日期**: 2026-09-25
- **模型**: Claude (Claude Code)
- **任务**: 用户批准做此前悬置的一项验证 ——
  「本项目用 **Vivado 2025.2**,而 PYNQ 2.7.0 镜像里**全部示例 hwh 都是 2020.2 产物**;
  2025.2 导出的 `.hwh` 能否被 PYNQ 的 `hwh_parser.py` 解析?」
  这是**在写 `cv_axi_lite_slave.v` 之前必须先去掉的风险** —— 否则等 overlay 导出来才发现加载不了,返工成本高。
- **⚠️ 证据边界**:本次**未上板、未烧任何 bitstream**。
  全部在开发机上完成(Vivado 2025.2 batch + 从 SD 镜像里取出的真解析器)。
  证据见 `report/measurements/20260925_hwh_compat.md`。

## 提示词

```
进行验证吧，我没有在跑ivado工程
```

（承前一轮模型主动提议:"用你的 Vivado 2025.2 从 `system.bd` 导一次 hwh,
拿卡里那份 `hwh_parser.py` 逐字段比结构。要开 Vivado 的话你说一声 —— 你要是正开着 GUI 我就不抢。"）

## 模型回答

**方法上没有停在"逐字段人眼比对",而是直接拿真解析器跑真文件。** 三步:

1. **造真文件**:在 `/tmp` 建**一次性探针工程**(⚠️ **不触碰用户的 `qrs` 工程**),
   搭出与目标 overlay 同形的 BD(PS7 + AXI 互联 + 带寄存器的 AXI 从机),`generate_target hw_handoff` 导出 hwh。
   选 `axi_gpio` 作从机,是因为它在**结构上正好对标将来的 `cv_axi_lite_slave`**。
2. **取真解析器**:用户 `qrs.srcs` 里的 `system.bd` 只有 PS7 + 一个已弃用的 `axi_quad_spi`,
   **没有带寄存器的 AXI 从机**,导它测不到 REGISTERS 那一段 —— 所以另建探针。
   板上真在跑的 `hwh_parser.py` 则用 `debugfs` 从 `ZYNQ-7020-2.7.0.img` 的 ext4 分区里取出(**免 root、免挂载**)。
3. **跑起来**:补一个 4 行的 `pynq.ps` 桩(只提供 `CPU_ARCH` 等四个常量),
   在 Python 3.10 里把**真解析器**跑到**真 hwh** 上,对比 `ip_dict`。

**对照组**:厂商 `ZYNQ_7020_PYNQ.zip` 里的 `2_axi_gpio` 示例 ——
其 BD 内容与探针 1 几乎一致(PS7 + AXI GPIO),但由 **2020.2** 生成。
**同内容、异版本,是最干净的 A/B。**

**结果:完全兼容。** 根节点 `EDKSYSTEM`、`EDWVERSION="1.2"`、
根子节点、`SYSTEMINFO` 属性、`MODULE` 属性集、`PARAMETERS`/`REGISTERS`/`ADDRESSBLOCKS`/`MEMRANGE` 层级 ——
**2020.2 与 2025.2 逐字段一致**,`ip_dict` 解析出正确地址(`axi_gpio_0` → `0x41200000`)。

### 🔴 本次**没有**验到的(不得当成已验)

1. **module_ref 带 AXI 接口**的情况**没跑到** —— 手上没有带 AXI 从机接口的 RTL 模块可挂。
   解析器里**有专门分支**处理它(`hwh_parser.py:282`,
   `vlnv.split(':')[:2] == ['xilinx.com','module_ref']`),说明是 PYNQ 官方支持的路径,
   但**未经实测**。⇒ 等 `cv_axi_lite_slave.v` 写出来即可闭环。
2. 解析器在**本机 Python 3.10.12** 上跑;板上是 **3.8.2**。用到的 ElementTree API 两边一致,
   风险低,但**板上跑一遍才算数**。
3. 厂商示例中**没有任何一个用了 module_ref**,所以「2020.2 对 module_ref 写不写 `BDTYPE`」
   **无法对照** —— 2025.2 的实测是 `BDTYPE` 缺失,而解析器对它 `.get()` 后解包丢弃(`:258` 的 `_, _`),**缺失无害**。

## 纠错轨迹

### 1. 🔴 **探针 2 的 `ip_dict` 是空的 —— 模型没有把它读成"不兼容"**（本次最关键的一步)

- **过程**:探针 2(把一个 RTL 模块引用挂进 BD)跑完,`ip_dict` **是空的**。
  在"验证 2025.2 兼容性"这个上下文里,空结果**很容易被读成"不支持"** —— 那会得出完全相反的结论。
- **模型怎么处理的**:没有下结论,而是**回头查这个空是怎么来的** ——
  解析 `spi_0` 那个 `MODULE` 节点,发现它的
  `ADDRESSBLOCK` / `MEMRANGE` / `BUSINTERFACES` **计数全是 0**。
- **根因**:**问题不在版本上,在探针设计上** —— `spi_master` 没有 AXI 接口,
  没接口就没地址,没地址就不进 `ip_dict`。这是语义正确的行为,与 Vivado 版本无关。
- **怎么补的**:加了**探针 3 作负对照**(PS7 + 互联 + 同一个无 AXI 的 module_ref),
  证明「即使 PS7 在场,module_ref 照样不进 `ip_dict`」,从而**排除掉"是因为探针 2 没放 PS7"这个解释**,
  两个候选解释都被明确排除后才下结论。
- **评价**:这是本项目此前反复栽跟头的地方(见 `LLM-003` / `LLM-012` / `LLM-018` / `LLM-021`,
  **同型:拿局部观察当完整结论**)。**这次模型主动做了对照,没有让空结果替自己说话。**

### 2. 🟢 **顺带查实一条对 P2 设计有直接影响的事实**

- 由纠错轨迹 1 的追查**副产品**:**没有 AXI 从机接口的裸 RTL 模块,在 PYNQ 里根本没有对象可访问。**
  `spi_master` 被挂进 BD 后确实出现在 hwh 的 `MODULE` 列表里(2025.2 正常导出),
  但 `ol.<name>` 取不到 —— 它没有地址。
- **对项目的意义**:寄存器文件**必须包在 AXI4-Lite 从机里**,PS 侧才有 MMIO 入口。
  这与 `report/source_design_checklist.md` §3 的方向一致,但**此前只是设计意图,现在是实测确认**。
  ⇒ 直接影响 `cv_axi_lite_slave.v` 的接口设计。

### 3. 🟢 **工具链验证的方法本身升级了一次**

- 模型**没有**停在"把 2020.2 和 2025.2 的 hwh 用肉眼/脚本比字段"(那是间接证据),
  而是**把板上真正在跑的那个解析器取出来,喂真文件给它跑**。
  `debugfs` 免 root 直读 ext4 镜像这一步,是这次能拿到"真件"的关键。
- 对照 `LLM-021` 的教训(`grep` 配置文件和"改动已生效"是两回事):
  **能跑真件就别比结构。** 这次是那条教训的正面应用。
