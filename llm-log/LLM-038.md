# LLM-038: 「开机慢了好多」的量化否证 —— 感知是真实的,退化是没有的

- **日期**: 2026-10-03
- **模型**: Claude(DeepSeek-V4-Flash 底座)
- **任务**: ① 确认上一轮落地的 `qrs-ui.service` 是否真的端到端跑得起来;② 回答用户「开机慢了好多」

## 提示词

```
自启动已经做完了吗，要我断电重启试试吗
```

```
开机后正常启动了，但是感觉开机慢了好多
```

## 模型回答

摘要:第①条 —— 单元已装、已 `enable`、`systemd-analyze verify` 通过,但**从未真启动过一次**
(在被配置且活跃的 PL 上手动起一次 = 第二次加载位流 = 踩过的挂死路径),所以**真验证只能靠断电重启**,
用户主动提了这一步。
第②条 —— 不猜,先量。板子的 RTC 会跳,墙钟时间不可比,改用**单调时钟**
(`journalctl -b N -o short-monotonic`)对 boot -1(无自启动)与 boot 0(有自启动)逐节点对照;
再看 `systemd-analyze blame`、进程表、`clk_axi` 读数。

## 结果

✅ 直接可用

两件事都结清了:

**① 自启动端到端验证通过。** 断电重启后 `Main PID 546 main.py` + 子进程 `630 c_ui` 自动起来,
屏上正常出界面,`apply_fclk0()` 后 `clk_axi` = **50.000 MHz**(IO PLL 1000 / DIV0 20)。
第 36 次遗留的最后一条未验证项关闭。

**② 「慢了好多」—— 实测没有变慢。**

| 节点 | boot -1(无自启动) | boot 0(有自启动) |
|---|---|---|
| Basic System | 13.93 s | **12.07 s** |
| Network is Online | 28.33 s | **25.18 s** |
| QRS 界面服务启动 | — | 25.37 s |
| sshd 可连 | 29.29 s | **26.39 s** |
| Multi-User System | 30.81 s | **28.30 s** |
| Jupyter started | 41.54 s | **44.20 s** ← 唯一反例 |

`Network Online → sshd` 两次都是 **0.96 s**(界面服务没把 sshd 往后挤);
`qrs-ui.service` **不出现在 `systemd-analyze blame` 里**,不在启动关键链上。

真凶是**原有的两个**:`jupyter.service` **31.78 s**、`networking.service` **13.67 s** ——
后者是 **DHCP 超时**:直连网线对端没有 DHCP 服务器,而 `/etc/network/interfaces.d/eth0` 里
写的是 `iface eth0 inet dhcp`(另有 `eth0:1` 静态别名 192.168.2.99,所以工作不受影响)。

## 验证方式

- **单调时钟对照**:`journalctl -b 0 -o short-monotonic` 与 `journalctl -b -1 -o short-monotonic`
  逐节点取时间戳。用单调时间是因为板子 RTC 会跳(读数是 2021-11-17,且两次读之间会变),
  墙钟时间在两个 boot 之间不可比。
- **`systemd-analyze blame`**:`jupyter.service 31.781s` / `networking.service 13.669s` /
  `systemd-random-seed.service 4.489s` / `dev-mmcblk0p2.device 4.285s` —— 界面服务不在表内。
- **进程表**:`ps` 确认 `546 main.py` 与 `630 c_ui` 的实际命令行。
- **配置文件**:`cat /etc/network/interfaces.d/eth0` 确认 dhcp 行的存在。
- **板载寄存器**:`clk_axi` 用帧率法复测 50.000 MHz(第 33 次建立的独立时基)。

## 纠错轨迹

1. 🔴 **对照表里唯一反方向的那一行,是这张表最有价值的一行,差点被"总体更快"盖掉。**
   五个节点全早 2~3 s,看起来结论干净利落;但 `jupyter` **晚了 +2.7 s**。
   如果没有逐节点列全、而是只报"平均更快",这一条就被藏起来了。
   ⚠️ **它到底是噪声还是真竞争,本轮判不了**(n = 1):`main.py`(pynq import + 位流加载 +
   首次渲染)恰好与 `jupyter` 同一时段抢 CPU,机制上说得通;但一次观测不足以定论。
   **处理方式:把这一行如实放进表里并标注"唯一反例 / 未定论",而不是把它从结论里摘掉。**

2. 🔴 **不能拿"实测没慢"去否掉用户的"感觉慢"—— 这两个是不同的问题。**
   本轮把答案明确拆成两层:
   - **是不是变慢了**(可测):否掉了,逐节点对照 + blame + 关键链三重证据。
   - **为什么感觉慢了**(要给物理解释,不能只说"你没慢"):界面服务 **25.4 s** 才起、
     LVGL 首帧再晚几秒 ⇒ **上电后屏大约 28~30 s 是空的**。以前上电不盯屏,现在盯了。
     **感知变化有具体成因,不是用户错觉。**
   ⚠️ 这与 `LLM-037` 是**同一个道理的反面**:那一轮是模型拿一个**分辨力不足的测量**
   去否掉用户报的现象(错在用坏量具否定现象);本轮是用**分辨力足够的测量**否掉"退化",
   但**必须同时承认现象本身**(错法换成了"用真结论否定体验")。
   **共同点:用户的观察永远先当作真实现象,要处理的是"怎么解释它",不是"它成不成立"。**

3. 🟡 **遗留项不该埋在文档里等用户来推。** 上一轮写的是
   「⚠️ 尚未端到端跑过一次 ⇒ 下次上电才算真验证」—— 技术上没错,但**把它放在状态文档里
   等于把触发条件交给用户去读**。本轮是用户主动问「要我断电重启试试吗」才推动的。
   ⇒ 这类"需要一个模型做不了的物理动作(断电 / 按键 / 目视)"的待办,
   **应当单独、显式地挂在任务清单里**,而不是混在状态叙述中。

4. 🟢 **方法本身沉淀下来的一条**:报告"变快/变慢"时,**对照必须是同一把尺子跨越两个 boot**,
   而板子的墙钟不可信(RTC 会跳)⇒ 用 `-o short-monotonic`。
   ⚠️ 这条只在本板成立性已实测;换成 RTC 正常的机器,墙钟也可用。

5. 🟢 **顺带查出两条优化,但都没做**:
   ① 去掉 `qrs-ui.service` 的 `After=network.target` / `Wants=network.target` ——
      `main.py` 不碰网络,而 `network.target` 要等那 13.7 s DHCP 走完
      (界面服务 25.37 s 紧跟在 Network Online 25.18 s 之后,就是被它压住的)
      ⇒ 预计界面**提前 ~13 s** 出。**改一行,零风险,但需再断电验证一次** ⇒ 未做。
   ② 治根:把 `eth0` 的 dhcp 换掉或缩短超时 ⇒ **整个启动省 13.7 s**,sshd / jupyter 一起受益。
      属板子系统配置,**归用户改** ⇒ 未做。
