## 纠错轨迹

### ① ★ 本次核心:**模型自己写的取数窗边界是错的,靠仿真抓出来**

`lcd_timing.v` 第一版里:

```verilog
localparam integer H_REQ_END = H_ACT_END - 2;   // ← 定义了(1182)
...
wire x_win = (h_cnt >= H_REQ_BEG_V) && (h_cnt < H_ACT_END_V);   // ← 却用了 1184
```

**定义了正确的量,却在判断里用错了一个别的量。** 后果:取数窗 158..1183 共 **1026** 拍,
`px_x` 跑到 **0..1025** —— 每行多发 2 个像素。

- **发现方式**:**写了临时 testbench 实跑**(`/tmp`,不进 `sim/` —— 按 §6.0 那是用户的地盘)。
  第一轮跑出 `坐标序列错误 1230176`,日志里第一行就是
  `[XY ERR] got (1024,0) expected (0,1)` —— **px_x = 1024 直接暴露了窗宽**。
- **改法**:`x_win` 上界改用 `H_REQ_END_V`,并在代码里留注释钉住
  (`🔴 上界是 H_REQ_END_V(1182),【不是】H_ACT_END_V(1184)`),
  连同实测数字 `1231200 = 1026×1200` 一起写在旁边 —— **让下一个读到这行的人知道为什么**。
- 🔑 **为什么这条最有价值**:这个 bug **不会让屏幕坏**。1026 拍一行,多发的 2 个像素落在
  DE 之外被丢掉,上板看**彩条完全正常**。
  它会一直到 Chunk B 才发作:帧缓存取行时 `px_x` 越过 1023 **去读下一行的头两个像素**,
  表现为"图像右边缘有 2 列串到下一行"。**那时候再查,已经隔了好几步。**
- 📌 **教训**:—— **"定义了正确的常量"不等于"用对了那个常量"。**
  同一文件里 `H_ACT_END` 与 `H_REQ_END` 只差 2,肉眼扫过去几乎一样。
  ⇒ 凡是"差一个常量"的边界,必须**跑数**,不能靠读代码确认。

### ② 临时 TB 的第一版断言本身也是错的(模型自查)

第一轮 TB 断言「2 帧内 `de_req` 应恰好 = 2×614400」,实测 **1231200** 判 FAIL。
**但这是 TB 的错,不是 DUT 的错**:

- 复位在 `#100`(帧中间)释放 ⇒ 观测窗覆盖的是 **2.003 帧**,不是 2 帧整。
- 且期望游标从 `(0,0)` 起算,而首个采样点是 `(0,0)` 只是**碰巧**(那次对齐上了)。

**改法**:① 游标改为**首个 `de_req` 到来时对齐**,不再假设初值;
② 删掉"绝对帧数"断言,改判**比值**(`de_req` 必须 == `de_act`,且每行恰 1024)。
- 🔑 教训:**测试台报 FAIL 时,先怀疑测试台。**
  若当时直接去改 DUT,会为了迁就一个错误的期望值引入真 bug。

### ③ 三处「有意留 warning」的取舍(用户未反对)

本批刻意让 `de_req` / `vblank` / `line_start` / `frame_start` / `cfg_lcd_swap_req`
**悬空无消费者** ⇒ 综合会报 "signal has no load"。

- **不消除的理由**:消除它只有两条路 ——
  ① 现在照抄一段"看起来在用"的假逻辑;② Chunk B 真接上。
  **选后者。** 假逻辑会掩盖"功能其实没实现",还会给 B04 添一笔说不清的资源开销。
- 📌 与 `skill/zero-cost-elimination-first/` 是**同一条原则的反面**:
  那条说"能零成本消除的先消除",这条说"**不能零成本消除的,不要用假逻辑凑**"。

### ④ 用户点破"你不是说 pl 部分要修改吗" —— 模型的过程问题

LLM-029 一整轮**只产出文档、零代码**,且**当场没有说清"代码按约定该由用户写"**,
导致用户以为模型漏做了。用户追问后才补上说明并拿到授权。

- 🔑 **不是踩了 §6.0 的线**(模型确实等了),而是**没把"我在等什么"讲在前面**。
- 📌 教训:**守着一条边界时,要把这条边界说出来**,否则它看起来像疏漏。
