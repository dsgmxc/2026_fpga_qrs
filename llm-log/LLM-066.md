## 模型回答

### 一、先回答「上电默认是多少」—— 分三层,别混

**① 芯片层(有手册出处)**:0 V。

| 出处(`dac1220.pdf`,SBAS082G) | 事实 |
|---|---|
| Table 13,bit 5 `DF` | `0` = Offset two's complement(**default**) |
| Table 13,bit 9 `CRST` 说明 | 「**If DF is 1, zero gives 0V; if DF is 0, zero gives VREF (mid-scale)**」 |
| p17 正文 | 「**After reset, the DIR contains zero.**」 |
| Table 9(20 位补码行) | `0x00000` → 芯片 **2.5 V**;`0x80000` → 芯片 **0 V** |

⇒ DIR 复位 = 0、DF 默认 = 0 ⇒ 芯片出 **中位 VREF = 2.5 V** ⇒ 模块层(−10…+10 V)
⇒ **模块 0 V / 栅极 0 V**。**芯片自己的上电态本来就是 0 V。**

**② 板上实际(改之前)**:🔴 **−100 V**。见下节,这是本轮的真发现。

**③ 用户量到的 +5 V**:不属于上面任何一种 ⇒ 待定位(见 §五)。

### 二、🔴 真发现:`cv_axi_lite_slave.v:514` 的复位值在 DF=0 下是 −10 V

```verilog
bias_code <= 32'h0008_0000;     // 中位码 = 0 V 偏压   ← 旧值
```

它上面那段注释的依据是**旧的 DF=1 传递式** `V_module = −10 + 20 × code/1048575`。
而 `dac_1220.v` 的 CMR 已于 **2026-10-12 由 `0x20A1`(DF=1) 改成 `0x2081`(DF=0)**,
⇒ **同一个码翻到了量程的另一端**:

| 码 | DF=1(注释的依据) | **DF=0(现用,已实测)** |
|---|---|---|
| `0x00000` | −10 V | **0 V** ← 现在 0 V 在这里 |
| `0x80000` | **0 V** ← 复位值想取的就是它 | **−10 V** ⇒ 栅极 **−100 V** |
| `0x7FFFF` | +10 V | +10 V |

**危险点**:那段注释自己的设计意图写着「上电停在 0 V 是无条件安全的中点」,
而 DF=0 之后它落在 **`Vgs` 绝对值最大的那一端**。若上电时 DUT 已接上,是真风险。

**消费时机**:该复位值只经「上电自动发一次 `bias_set`」下发,而该脉冲**门控在 `dac_init_done`**,
所以它恰好在 DAC 初始化跑完(含 CMR=0x2081 那次写)之后才被消费 ——
**即被消费时 DF=0 是确定的**,这正是该换成 `0x00000` 的理由(不成立的只有注释的算术)。

### 三、修复(用户指令)

| 位置 | 改动 |
|---|---|
| `qrs.srcs/sources_1/new/cv_axi_lite_slave.v:514` | `32'h0008_0000` → **`32'h0000_0000`** |
| 同处注释段(497–513) | 整段重写为 DF=0 口径:补上实测传递式、两个码各对应多少伏、**并把「由 DF=1 改来」这件事记在注释里**(不删旧结论,写明它错在哪) |
| `docs/dac1220_interface.md:237` | 「DIR=0 = **−10 V**」→ 更正为 0 V,并**解释当年量到恒定 −10 V 的真因**(DF 是**易失位**,是上一次成功写进去的旧 CMR `0x20A1` 留在芯片里,不是芯片默认) |
| `report/source_design_checklist.md:417` | `0x14` 行的旧传递式**标作废**,换成 DF=0 的实测式 + 新复位值 |

后四处是按本项目既有纪律做的:🔴 **同一句假话印在多处,改一处不改另一处 = 留下自相矛盾的证据。**

## 纠错轨迹

1. **我先按旧注释的口径给出了"上电默认 −10 V"的说法(说在"板子实际"那一层) ——
   方向对、数字错。** 真正的板子默认(改前)是 **−10 V 是模块端没错**,但我一开始
   还把它当成"设计有意为之的安全值",直到读到手写注释里那句
   「上电停在 0 V 是无条件安全的中点」才发现**它自己都不认为自己会出 −10 V**。
   ⇒ **注释里写着的"意图"和它当前"实际"打架时,后者才是要报的那个。**
2. **差点把 `qrs.v` 的硬编码 `20'hC0000` 当成"一直输出 5 V"的元凶。**
   `20'hC0000` 在 **DF=1** 下正好是 **+5 V**(与 2026-09-19 那次实测一致),看着极像真凶。
   **靠 `.hwh` 否掉的**:交付与构建两边的 `system.hwh` 里 `MODTYPE` 只有
   `cv_sys / proc_sys_reset / processing_system7 / smartconnect` ——
   **`qrs.v` 不是部署顶层**(它是 P1 时代的独立顶层,恰好在同一个目录里)。
   📌 教训与既有 memory 一致:**"看着最像"的线索要先证伪掉再往下报**。
3. **用错了传递式的年代,差点把 2026-09-19 的旧读数当今天的证据。**
   `project_state.md:791` 那句「`0x086666` = 模块 +0.500 V ×10 = +5.00 V」是
   **DF=1 时代**的;在 DF=0 下同一个 `0x086666` 是 **−9.56 V**。
   ⇒ 本项目**凡引用 2026-10-12 之前的码↔电压读数,必须先确认它属于哪个 DF**。
4. **★ 我重复造了一个本来就存在的构建脚本 —— 而且是在"交付仓库"这一层。**
   我断定「工程里原先没有综合脚本」(依据是上一次构建用的是 `/tmp/q_pull.tcl`,
   而 `/tmp` 跨重启会丢 —— memory 里已有这条,判断本身没错),
   **但我只在工作区 `~/Desktop/qrs_2026_fpga/` 里找了一遍就下了结论**,
   于是新写了 `build/run_impl.tcl` 并跑出位流。
   事后核对交付仓库才发现:**`build/build_bitstream.tcl` 早就在**,
   它 `source` 的 `build/report_summary.tcl` 产出 `build/summary.txt` ——
   正是 LLM-062 里引用过的那个「时序出处」。功能与我的重复件**完全等价**。
   ⇒ **已删掉重复件、用既有脚本把整条链重跑了一遍。**
   📌 教训与既有 memory 同款(**"别说'不存在',除非穷尽搜索"**):**这个项目有两棵树,
   `src/` `build/` `sim/` 是对称的** —— 在**一棵树里**找不到某东西,
   **不等于另一棵树里也没有**。判断"没有某个脚本"之前必须**两棵树都查**。

## 沉淀

→ `skill/`:可复用形态 **「量程旋转半格」** —— 当芯片的**数据格式位**(DF/极性/offset
binary)变更时,**所有以"码"为单位的既有常数(复位值、默认值、查找表、软件映射)
必须逐个复算**;同一个十六进制数在新格式下可能恰好是"另一个极端"。
判据:**格式变更的 commit 里必须列出"所有含码常数的位置",而不是只改那个"看起来相关"的。**
本项目这次就是:PS 侧映射当天改了,PL 侧复位值**漏了三天**。

→ `build/build_bitstream.tcl` 本身:可复用的是**「不复用旧 run」**这一条 ——
`reset_run` 每次都重来,代价是几分钟,换掉的是"工具静默跳过重建"这类
**无提示失败**。
