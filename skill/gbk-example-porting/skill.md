# gbk-example-porting

> 把**中文厂商的 GBK 编码例程**移植进 Linux 版 Vivado 工程时,
> 中文注释会因 UTF-8 解析而乱码。
> 处方:**先往返校验,再比对正文 md5 —— 确保只改编码,不改语义。**

## 适用范围

- 场景:从国内厂商(正点原子、野火等)的例程包里拿源码,导入 Linux 上的 Vivado / Vitis 工程。
- 触发条件:文件是 **GBK / GB2312 / GB18030** 编码,而工具链按 **UTF-8** 解析。
- 典型受害者:`.v` / `.vhd` / `.c` / `.h` / `.xdc` 里的中文注释与字符串。

**不适用**:本来就是 UTF-8 的源码;二进制文件。

---

## 使用方法

### 第一步:先确认文件真的是 GBK

```bash
file -i <file>            # 期望:charset=unknown-8bit 或 iso-8859-1 ⇒ 疑似 GBK
enca -L zh <file>         # 更准;会报 GB2312/GBK
```

⚠️ **不要凭"是厂商例程所以一定是 GBK"就动手** —— 有些包已经转过了。

### 第二步:转换 —— **往返校验通过才写回**

```bash
# 读原文件 → 转 UTF-8 → 转回 GBK → 与原文件逐字节比
iconv -f GBK -t UTF-8 "$f" > "$f.utf8" &&
  iconv -f UTF-8 -t GBK "$f.utf8" > "$f.roundtrip" &&
  cmp -s "$f" "$f.roundtrip" && echo "ROUNDTRIP OK: $f" || echo "ROUNDTRIP FAIL: $f"
```

**只有 `ROUNDTRIP OK` 的文件才允许覆盖原文件。**
往返失败说明编码判定错了(或有不可逆字符)⇒ 此时**不要转**,去查证。

```bash
# 校验通过后再落盘
mv "$f.utf8" "$f"
```

### 第三步:转换后**比正文 md5**

编码转换不应该改变任何语义。落盘后立刻核一次:

```bash
# 转换前记录:原文件的正文 md5(去掉注释行后更保险)
# 转换后记录:新文件的正文 md5
# 期望:两次一致
```

> ⚠️ **整文件 md5 在转换前后必然不同**(编码变了),所以要比的是**正文**
> —— 至少要有一个"语义没变"的独立证据,不能只看"文件能打开了"。

### 第四步:用工具自己回读一次

改完**让 Vivado 把工程重开一遍**并跑综合,确认:

- 退出码 0
- **零 ERROR / 零 CRITICAL WARNING**
- 时钟派生正确(本项目实测 5 路时钟全部正确,`spi_clk_50m = 20.000 ns`)

---

## 失效条件

- ⛔ **不做往返校验直接覆盖** —— 编码判错时,注释被静默毁掉,而且**不会报错**。
- ⛔ **只比"文件能打开了"** —— 那不构成"语义没变"的证据。
- ⛔ **在 Vivado 编辑器打开着该文件时从外部改写** ——
  Vivado **不会自动重载**外部修改;若在该标签页 Ctrl+S,会把**新版覆盖回旧版**。
  改前先关文件,改后重开工程。
- ⛔ **只改编码就以为移植完了** —— 编码只是第一道坎;
  厂商例程通常还带**注释掉的冗余模块、竞争顶层、依赖板载器件的固定参数**,
  需要逐个决定去留(删除是不可逆动作,**先摆清依赖关系再问,不要直接动手**)。
- ⚠️ **厂商例程里的引脚约束不一定是给这块板的**。

## 已验证的效果

| 项 | 结果 | 证据 |
|---|---|---|
| GBK → UTF-8,5 个文件 | ✅ **往返校验逐字节相同才写回**;转换后**正文 md5 比对一致** | `LLM-021` |
| 转换后的工程完整性 | ✅ Vivado 重开工程自检:`TOP=qrs`、`MISSING_FILE_COUNT=0` | 同上 |
| 综合 | ✅ 退出码 0,**零 ERROR / 零 CRITICAL WARNING**;LUT **1360(2.6%)**;5 路时钟全部正确派生 | 同上 |

⚠️ **本项目用到的规模有限**(5 个文件、一套例程)。
若你的例程包里混有多种编码(UTF-8 + GBK 混装),`iconv -f GBK` 会在已 UTF-8 的文件上报错
—— 那时要**逐文件判定**,不能一刀切。
