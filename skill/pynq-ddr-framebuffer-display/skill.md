# pynq-ddr-framebuffer-display

> **通用 PYNQ 技能** —— PS 渲染到 DDR 帧缓存、PL 实时取行驱动并行 RGB 屏。
> 不含任何本项目特有的器件参数,换屏、换图形库、换题目均可用。

## 适用范围

| 项 | 值 |
|---|---|
| 平台 | Zynq-7000(本项目 XC7Z020)+ PYNQ 2.7 + Vivado 2025.2 |
| 屏 | 并行 RGB(DE 模式)LCD,`PCLK = 50 MHz`;本项目为 1024×600 |
| 通路 | `PS 写 DDR → PL 通过 AXI 主机读 → 行缓冲 → LCD 时序发生器` |
| 已验证 | 单帧静态图案端到端;`S_AXI_HP0` @ 64 bit;双帧缓存换址硬件化 |

**不适用**:
- 屏是 MIPI-DSI / LVDS 等**串行**接口(需另加串化器)。
- 需要 PL 侧做图形合成(3D / 混合)的场景 —— 本范式只做**搬运**,渲染全在 PS。

---

## 使用方法

### 一、为什么必须走 DDR,而不是 BRAM

算一次就知道:**1024 × 600 × 24 bit(RGB888) = 14.75 Mb**,
而 XC7Z020 **全部 BRAM 只有 4.9 Mb** —— 装不下。

> 📌 这条算术在**"界面只需一条曲线"**的假设下是可以绕开的
> (曲线缓存 `1024 × 10 bit = 10 Kb`,PL 比较 `y == curve[x]` 描点)。
> 但一旦要跑**完整 GUI**(控件 + 中文字库 + 多页面),曲线缓存立刻不成立。
> **本技能给的是完整 GUI 的路子。**

### 二、带宽与位宽预算(先算再写 RTL)

设行周期 = 1344 clk @ 50 MHz,一帧 635 行:

```
一行像素          1024 px × 16 bit(RGB565) = 2 KB
行周期            1344 clk = 26.88 µs
消隐窗口          320 clk = 6.4 µs
取一行需要的拍数   ——————————————————————————————
  64 bit/拍       2048 B / 8 B = 256 拍 = 5.12 µs   ← 余量 25%
  32 bit/拍       2048 B / 4 B = 512 拍 = 10.24 µs  ← 超窗口,必失败
显示占用带宽      1024×600×2 B × 58.6 Hz ≈ 72 MB/s(峰值 144 MB/s)
```

**结论:走 `S_AXI_HP0` 并配成 64 bit。** 32 bit 不是"慢一点",是**根本来不及**。
代价:占用 HP 口后 PS 侧 DMA 不可用 —— 若 PS 不走 DMA,这笔代价为零。

> ⚠️ **取数要在上一行的扫描期内发起,不能等消隐。** 消隐只有 6.4 µs,取一行要 5.12 µs,
> 只靠消隐等于**零余量**,吸收不了 DDR 争用。

### 三、🔴 AXI3 是硬门,不是"宽度参数"

Zynq-7000 的 **HP / GP 口是 AXI3**。把主机接口声明成 AXI4,BD 会直接拒绝连线:

```
ERROR: [BD 41-1285] The protocols of the interfaces '/cv_sys_0/M_AXI'(AXI4)
       and '/processing_system7_0/S_AXI_HP0'(AXI3) are incompatible.
```

AXI3 的硬约束:**突发长度上限 16 拍**(`arlen` 4 位)。
⇒ 一行 256 拍必须拆成 **16 次 × 16 拍**,并加突发序号计数器。

**遇到这个报错时,摆在面前的是两条路,选之前先想清楚:**

| | 路 A:插 `axi_protocol_converter` | 路 B:把 RTL 改成原生 AXI3 |
|---|---|---|
| 改动量 | BD 里两行 Tcl | RTL 改 `arlen` 位宽 + 拆分突发 |
| 代价 | **变延迟 IP** | 多十几个 LUT 的计数器 |
| 适用 | 非实时通路 | **有硬截止期的实时通路** |

本项目选 **路 B**:行通路上的余量是按拍算的,插一个延迟不可预测的 IP
等于**用确定性换几个 LUT** —— 在别处划算,在这里不划算。

### 四、🔴 `ARPROT[1]`(NS 位)置 1 会导致**全量 DECERR**

这可能是 Zynq + PYNQ 组合里最贵的一个坑:**帧缓存整屏全黑,而握手指令完全正常**。

```verilog
// ✅ 可用
assign m_axi_arprot  = 3'h0;      // 各位全 0
assign m_axi_arcache = 4'b0010;
// ❌ 全黑:m_axi_arprot = 3'b010;  ← bit[1] = NS(非安全访问)
```

**2×2 单变量分离,四格全测**(每格先核综合后网表再上板):

| `ARCACHE` | `ARPROT` | 结果 | 位流 |
|---|---|---|---|
| `0010` | `000` | ✅ 有数据 | `a9636e0d` |
| `0011` | `000` | ✅ 有数据 | `62c0db66` |
| `0010` | `010` | ❌ DECERR | `0b9d1b82` |
| `0011` | `010` | ❌ DECERR | `298c8f1f` |

⇒ **只由 `ARPROT` 决定,`ARCACHE` 完全无关。**

**这个故障最阴的地方**:`BRESP`/`RRESP` 回 `DECERR(2'b11)` 且**返回数据全为 0**,
而**突发拍数照样满帧**。所以「拍数满了 ⇒ 通路正常」是**错的判据**。

**上板判据字段怎么选**(照这个来):

| 字段 | 可用性 |
|---|---|
| `beats`(取数拍数) | ❌ **无区分力**,四格全都 ≈100% |
| `rresp_lat` | ⚠️ 会随"刚加载 / 稳态"变化 |
| **数据非零标志**(`axi_or_nz` / `px_or_nz`) | ✅ **8/8 一致**,唯一可靠 |

> ⚠️ **机理无权威出处**(本项目机器上没有 UG585/TRM)。`ARPROT = 3'h0` 的取值属
> 「**与已验证参照物对齐**」(本机 Vivado 的 Xilinx AXI master 模板 + 厂商已验证例程),
> **不是**「已知原理」。写成报告时要如实标注这个差别。

### 五、Cache 一致性(默认的静默失败源)

PS 写 DDR 用的是**可缓存**映射,而 PL 是通过 AXI 读**物理内存**。

```python
# 用 pynq.allocate 管理(它会处理 cache 维护)
import pynq
fb = pynq.allocate((1024*600*2), dtype='u1')   # 物理连续 + 对齐
# ... 渲染进 fb ...
fb.flush()                                     # 🔴 写完必须 flush
```

**不 flush 不会报错,只会显示旧数据** —— 现象和"程序没跑起来"一模一样。

### 六、防撕裂:把"请求"和"生效"分开

```
PS 写 FB_BASE1 → 写 LCD_SWAP(请求)
                  ↓
PL 受理(swap_req)  但不立即生效
                  ↓
等到下一个场消隐首拍(frame_start)才真正切换
```

**若 PS 能在扫描中途改基址,撕裂就是必然的。** 把生效点锁在场消隐,
**PS 就无法绕过** —— 防撕裂从"软件自律"变成**硬件保证**。

### 七、让用户当观测者时,给**能一次区分多种故障的图案**

别问"屏亮了没有"(只能得到是/否)。用多元素图案:

```
整屏绿(底色) + 中间红横带(行 290–309) + 左上白块(行 40–119 / 列 40–199)
```

一次回报就能区分:
- 三元素全对 ⇒ 全通
- **少了角块** ⇒ 行内偏移
- **全黑** ⇒ 无数据
- **底色变了**(绿→红/蓝)⇒ **R/B 位序交换** ← 红横带顺带做了这项检查

## 失效条件

- ⛔ **声明 `PROTOCOL AXI4` 接 Zynq-7000 的 HP/GP 口** —— BD 拒绝连线。
- ⛔ **`ARPROT[1] = 1`** —— 全量 DECERR,且**握手正常、拍数满帧**,极易误判为"通路没问题"。
- ⛔ **PS 写完帧缓存不 flush cache** —— 静默显示旧数据,不报错。
- ⛔ **32 bit 位宽**跑 1024×600@50 MHz —— 取一行要 512 拍 > 行周期,必然 underrun。
- ⛔ **允许 PS 在扫描中途改基址** —— 撕裂。
- ⚠️ **`m_axi` 走直连还是过 `axi_smc`**:本项目把 HP0 直连写成"唯一找到的拓扑差异",
  **但从未证实它就是根因** —— 不要把它当结论引用。
- ⚠️ **`ARPROT[1]` 的机理未查明**(无 UG585)。别写成"因为非安全访问会被拒绝"这种原理性解释。

## 来源

1. **`LLM-031`(2026-10-02)** —— 选 HP0 而非 GP0(位宽直接决定余量);
   **BD 41-1285** 逼出"AXI3 是硬门",并在"插转换器"与"改 RTL"之间**选了后者**;
   测试台编译失败时 `xelab -R` **回放上一轮 PASS 输出**(判据 = 输出行数,不是有没有 PASS)。
2. **`LLM-033` / `20261003_ddr_hp0_decerr.md`(2026-10-03)** —— 全黑排障第一轮:
   把调试寄存器从"纯拍数"改成"低 18 位拍数 + 高 14 位**内容证据**",**一次实测**分开两个假设;
   9 点地址扫描(含 OCM 与越界地址)无一例外 ⇒ 拒绝发生在**端口层面**,与地址译码无关。
3. **`LLM-035` / `LLM-036`(2026-10-03)** —— 根因坐实。附带两条硬教训:
   ① **「握手 ≠ 数据」**:DECERR 回全零而拍数照样满帧;
   ② **判据字段要按"能不能区分两种情况"选** —— `beats` 四格全 100%,`axi_or_nz` 8/8 一致。
4. **`LLM-036` 纠错①②** —— 同一天内,模型先"以为改了没进去",又"以为没改其实进去了"。
   ⇒ 凡把 RTL 常量当**实验自变量**,必须**先核综合后网表再上板**。
   详见 `skill/rtl-constant-experiment-must-verify-netlist/`。
