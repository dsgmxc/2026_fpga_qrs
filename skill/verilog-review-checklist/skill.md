# verilog-review-checklist

> RTL 静态审查清单,按本赛道的考察侧重排序。
> **清单里每一条都对应一次真实踩过的坑**,不是从手册抄的通用建议。

## 适用范围

- 手工 RTL(Verilog-2001/2005),综合目标 Xilinx 7 系 + Vivado。
- 适用场景:**人(或 LLM)静态阅读代码**、给出修改意见时。
- 也适用于 LLM 协作流程:把这份清单作为**审查提示词的骨架**。

**不适用**:SystemVerilog 验证环境(UVM)、HLS 生成代码、厂商 IP 内部。

> ⚠️ **本清单的边界**:静态阅读能找出逻辑错误,**不能替代仿真**。
> 本项目多次验证过:审查指出的问题里,有些改对、有些"改了但没改对"、
> 有些改动**新引入了更隐蔽的 bug**。清单用来**排雷**,不是用来**签字**。

---

## 使用方法

按下面的**优先级顺序**过一遍。前两类是"上板必错"级,后两类是"上板难查"级。

### 第一优先:时序与跨时钟域

- [ ] **同一 `reg` 是否被多个 `always` 块驱动?**
  → 仿真竞态 + 综合报错。本项目 `spi_master.v` 的 `cs` 与 `delay_cnt` 两条属此类,
  清除后工程才可能通过综合。
- [ ] **组合信号是否被用作异步复位?**
  → 复位**撤销沿**与时钟不同步,有恢复/移除时间风险。
- [ ] **反馈回路是否构成组合死锁?**
  → 典型:`locked` 反馈进 `resetn`。`clk_wiz.resetn` 若接 `rst_n & locked`,
  形成「`locked` 依赖 `resetn`、`resetn` 又依赖 `locked`」⇒ MMCM **永远锁不上**,
  比原来的 bug 更严重。
  ✅ 正确写法:`wire rst_n_sys = rst_n & locked;` 只接给下游逻辑,
  **`clk_wiz.resetn` 保持接原始 `rst_n`**。
- [ ] **跨时钟域信号有没有同步器?** 单级同步触发器直接驱动 `case` 是危险信号。

### 第二优先:状态机合法性

- [ ] **每个 `case` 分支都有出口吗?有没有空 `else`?**
  → 本项目 `dac_1220.v` 首版:`init_cnt < 6-1` 且 `else` 为空 ⇒ `init_cnt=5` 时无出口,
  `DELAY` 永久停留。**死锁比语法错误隐蔽得多。**
- [ ] **`default` 分支可达吗?**
  → `sel_d` 是 2 位而 `case` 已覆盖 0~3 ⇒ `default` **不可达**,写了等于没写。
- [ ] **计数器位宽装得下判据吗?**
  → `$clog2(N)` 的取值域是 `0..N-1`,**永远够不到 `N`**。
  本项目:`BIT_CNT_WIDTH = $clog2(2*DATA_WIDTH)` 是 4 bit(0~15),
  而终止判据是 `>= 16` ⇒ **永不成立**,状态机到不了 `DONE`。
  最小修改:`$clog2(2*DATA_WIDTH + 1)`。
  > 💡 **改这类 bug 的正确入口**:问「**这个寄存器在比较那一刻可能取哪些值**」,
  > 而不是「判据该设多少」。用户当时把判据从 `2*N` 改成 `2*N-1` —— **改了表象没动根因**,
  > 因为 `bit_cnt` 在该状态只会以偶数值进入(`0,2,…,14`),**永远看不到 15**,
  > 而且 14 未命中后会被加到 16 → **4 bit 回绕成 0**,循环重来。
- [ ] **`else` 的就近配对与缩进一致吗?**
  → Verilog 的 `else` **不看缩进**。本项目 `DONE` 状态新增
  `if(start_r) next_state <= START;` 后,落进了 `if(CS_MODE)` 的 `else` 分支范围,
  导致 `CS_MODE=0`(默认值)时整个分支被跳过 ⇒ **状态机卡死,只能发第一帧**。
  ⇒ **往已有 if/else 嵌套里插语句后,必须复核绑定关系;必要时补 `begin/end`。**
- [ ] **对同一状态机的改动,症状会不会被上游 bug 掩盖?**
  → 上面那条"改 A 引入 B"要到"1 号 bug 修好之后"才暴露。

### 第三优先:位宽与符号

- [ ] **表项位宽 ≥ 表项最大值?**
  → 本项目 `dac_1220.v`:`init_delay[5] = 2100 × 50 = 105000 > 65535` ⇒
  截断成 39464(≈789 µs,而非 2100 µs)。**静默截断,综合不报错** ——
  **读综合 warning 比读代码更容易发现**。
- [ ] **数组长度 / 循环上界 / 表项数,四者一致吗?**
  → 本项目出现过 `7 项 / 7 项 / 6 项 / 上界 5` 四者互不一致。
- [ ] **切片有没有丢位?**
  → `code[19:12]/code[11:4]/{code[3:0],4'b0}` 是 DIR left-justified 规则;
  原写法**丢掉了 `code[11:4]`**。
- [ ] **常量比对时进制位数写对了?**
  → `28'h0AAAAAA` 是 **7 位**十六进制(11,184,810),
  **不是** `0xAAAAAAAA`(178,956,970)。本项目 tb 期望值一度按 8 位算 ⇒ 报了**假 FAIL**。
- [ ] **隐式线网**:例化端口连到的名字**声明了吗**?位宽匹配吗?
  → 6 个标识符未声明 ⇒ 隐式 1 位线网;把 8 位端口接上去,即便启动成功**发出去的也是 X**。

### 第四优先:接口握手

- [ ] **握手信号(`busy`/`done`/`valid`)有没有被赋值?复位后是 X 吗?**
  → `output reg` 声明后全文无赋值 ⇒ 复位后为 X。
- [ ] **跨模块的边沿检测,是否无条件在 FSM 之外锁存?**
  → 本项目 `adc_9833.v`:一帧要 ~1.3 ms,PS 打触发的时刻不受硬件控制,
  沿极可能落在**发射中途**。只在 `NORMAL_WAIT` 里判会**丢触发**。
  ✅ 写法:`set_pending <= 1` **写在 `case` 之后、无条件执行**。
  ⇒ 这条**已用变异测试坐实**:把后置锁存加 `&& state == NORMAL_WAIT`,
  落在 `GAP` 的那次触发**直接消失**。
- [ ] **表驱动只驱动了"等待",没驱动"发送"?**
  → 首版 `dac_1220.v` 的 `init_sclk[]` 存的是 sclk 电平(想手工翻时钟),
  而正确做法是存**命令字**,由状态机喂给 `tx_data` 并打 `start`,再等 `busy` 起落。
  **模型给的 6 状态骨架,用户只实现了其中 3 个。**

### 第五优先:风格与可维护性

- [ ] **标识符使用先于声明?** → `xvlog: [VRFC 10-3380] identifier 'x' is used before its declaration`。
  本项目反复踩过(`cv_sys.v`、`lcd_fb_reader` 的 TB)。
- [ ] **`reg` 声明却用 `assign`?** → `[VRFC 10-3236] concurrent assignment to a non-net`。
- [ ] **常量驱动警告("has no load" / "constant driving")是不是缺陷?**
  → **不一定**。本项目 `lcd_hs = 1'b1`(HSYNC 恒高,DE 模式)是有意为之,
  22 条 `Synth 8-7129` 已判**预期**。
  **正确姿势是判定并记录理由,不是无脑消除警告。**
- [ ] **改动之后复核了吗?** 尤其是"改了但没改对"与"改 A 引入 B"两种形态。

## 失效条件

- ⛔ **不能替代仿真**。本清单所有结论都是**静态阅读**得出的;
  本项目多次出现"审查结论未经波形验证"的情况,记录里必须如实标注。
- ⛔ **不能替代上板**。引脚约束、IOB、板级走线、时钟实际频率,静态阅读完全覆盖不到。
- ⛔ **代码重写后,旧结论作废而不是"已验证"**。
  `spi_master.v` 被用户重写后,`DATA_R` / `CS_MODE` / `next_state` 等标识符**全部消失**
  ⇒ 依附那些代码的结论**既不能被证实也不能被证伪**,只能标"作废"。
  **不得改写成"已验证"** —— 那是在给没被检验过的结论背书。
- ⚠️ **误报会伤害协作**:本项目出现过模型"纠正"项目常数结果**项目是对的**
  (`0x428F` vs 模型说的 `0x828F`,见 §来源)。

## 已验证的效果

本清单的条目在项目中**造成过真实后果**,不是理论风险:

| 条目 | 实际后果 |
|---|---|
| 同一 `reg` 多驱动 | `spi_master` 无法通过综合 |
| 计数器位宽不足 | 状态机永远到不了 `DONE`,只能发一帧 |
| `else` 就近配对 | `CS_MODE=0` 时状态机卡死(被上游 bug 掩盖) |
| 空 `else` | `dac_1220` 在 `init_cnt=5` 永久停留 |
| 表项位宽溢出 | 2100 µs 等待变成 789 µs |
| 隐式线网 | 发出去的是 X |
| 表驱动只做一半 | 校准命令实际没发出去 |
| 边沿检测位置错 | 发射中途的触发丢失(**变异测试坐实,见上**) |

**审查驱动的净收益**:用户采纳并修好 5 条(其中 **2 条是综合级致命项**),
清除后工程才可能通过综合 —— 这是本项目第一次代码审查最实的收益。

**同时如实记录失效案例**:审查也出现过「改了但没改对」(判据放宽)、
「改 A 引入 B」(新增 if 落错分支)、以及"纠正项目常数结果项目是对的"。
⇒ **审查的价值在于排雷密度,不在于结论可靠**。

## 来源

1. **`LLM-004`(2026-09-13)** —— `spi_master.v` 两轮审查。用户的修改
   **改了表象没动根因**(轨迹 B),且**新引入一条更隐蔽的致命项**(轨迹 C)。
   模型在此轮明确划界:`CPOL/CPHA` 取值必须对数据手册确认,**模型不对引脚时序作断言**。
2. **`LLM-005`(2026-09-15)** —— 首版 `dac_1220.v` 的 **6 条致命项**
   (死锁 / 表项溢出 / `start` 恒 0 / 输出悬空 / `init_done` 从未置 1 / 死代码)。
   ⚠️ 这 6 条**全部是静态阅读结论,未经仿真验证** —— 记录里已显式标注。
3. **`LLM-014`(2026-09-20)** —— 模型**差点冤枉项目自己的常数**:看到 init 第 3 帧是
   `0x428F`,按 `D15,D14` 解码后当场断言"应该是 `0x828F`,项目写错了"。
   **没直接改代码,先去翻手册表 9** —— `B28=1` 时两次写入的 `D15,D14` 必须相同(都是 `01`),
   所以 `0x428F` 是对的,`0x828F` 反而会把地址指到 FREQ1。
   > **"看起来该是这样"不等于手册是这样。差一步就改坏了。**
   同轮:模型报了一个**假 FAIL**,根因是期望值算错(7 位十六进制当 8 位算)。
4. **`LLM-025`(2026-09-29)** —— `swm.v` 的规格缺口:编译已通过,但
   **"先断后合 + >5 ms 死区"未落实**(需求明文要求硬编码互锁,不能靠软件自律),
   且 `default` 分支不可达。⇒ 清单里"状态机合法性"一节的来源。
