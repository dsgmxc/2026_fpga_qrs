# count-both-sides-of-interface

> **「一次调用 = 一笔事务」从来不是事实,是假设 —— 而它通常没被验过。**
> 本技能包收录本项目一次**代价最高的误判**:在 4 天里把症状归因给 FPGA 逻辑,
> 最后发现真凶是 PS 侧**换了一种写法多发了 1 笔总线事务**。
> 附带一条**同族但独立**的发现:某个 Python 标准库函数在设备映射上**会先写一个 0**。

## 适用范围

- 任何**分层系统**,症状出现在某一层,而你在那一层**数事件**、却从没在上一层数过:
  PS ↔ PL(Zynq)、驱动 ↔ 内核、应用 ↔ 网络、测试脚本 ↔ DUT、ORM ↔ SQL。
- 特别适合这种形状的现场:**"我明明只做了一件事,对面却看到了两件。"**
- 不限于硬件。任何"接口两侧计数对不上"的场合都适用。

## 使用方法

### 判据 0(总入口):先问"我数的这个量,是在接口的哪一侧数的?"

看到"对面多出一次"时,不要先问"对面为什么会多"。
**先问"我这边的『一次』是什么时候量出来的、量的是不是事务"。**

本项目里,`对 0x1C 的一次写 → PL 收到 2 个脉冲` 这个描述里:

| 词 | 数在哪一侧 | 量出来了吗 |
|---|---|---|
| "一次写" | PS 侧 | ❌ **从来没有。它被当成了前提。** |
| "2 个脉冲" | PL 侧 | ✅ 数了(而且数得对) |

**两个数里只有一个被量过。** 全部排查时间都花在"PL 为什么会出 2 个脉冲",
而没有任何人问过"PS 到底发了几笔"。

### 判据 1:把"一次调用 = N 笔事务"当成**待测项**,而不是公理

对同一个寄存器,用**不同写法**各写一次,看**结果**是否一致:

```python
# 现象:只有第 4 种会出问题;前 3 种都对。
mio.write(0x1C, V)                       # ① 库封装的整字写
mm[0x1C] = V                             # ② 单字节存
mm[0x1C:0x20] = struct.pack("<I", V)     # ③ 切片赋值
struct.pack_into("<I", mm, 0x1C, V)      # ④ ★ 会多发事务
```

**只要"换写法就变",就说明问题在你自己这一侧的调用方式,不在对岸。**

### 判据 2:用一个**锁存型证人寄存器**把"对面到底收到了什么"变成可读的数

找一个"整字锁存写数据、读回原值"的寄存器(`0x4C SCRATCH`)当证人。
它**不受**任何业务逻辑(合法性、互锁、状态机)干扰,所以你看到的就是总线真值:

```
写前把证人置成已知值 → 做一次可疑的写 → 读回证人
  = 载荷   ⇒ 一笔,正常
  = 别的值 ⇒ 载荷被拼接/清零了,或发了几笔
```

> ⚠️ **本项目的教训:证人寄存器选错了会白跑一轮。**
> `0x48` 是 VERSION(**只读,恒 `0x00010000`**),`0x4C` 才是 SCRATCH。
> 拿只读寄存器当证人,会得到"写不进去"的假象。
> ⇒ **先确认证人是 RW 的**(写一个值、读回来等于它,再开始用它)。

### 判据 3(具体到 Python + 设备映射):**设备 mmap 上不要用 `struct.pack_into`**

`struct.pack_into(fmt, mmap, off, v)` 在 CPython 上对 `mmap` 会发出**两笔**
总线事务:**先写一个 `0x00000000`,再写载荷**。

```python
# ❌ 会发两笔(第一笔是全 0)
struct.pack_into("<I", mm, off, value)
# ✅ 只发一笔
mm[off:off + 4] = value.to_bytes(4, "little")
```

**怎么一眼认出是这个坑:**

| 特征 | 说明 |
|---|---|
| 结果是 **0** 而不是你要的值 | 第一笔那个 `0` 生效了 |
| 与**写入值无关**、与**寄存器原值无关** | 恒为 0 ⇒ 第一笔是常数 0,不是"读-改-写" |
| 换成切片赋值/库封装立刻正常 | 判别式在这 |
| 目标寄存器**带"忙"互锁**时才显形 | 没互锁 ⇒ 后写覆盖前写 ⇒ 看不出来 |

### 判据 4:窄写(字节/半字)在设备映射上可能是**读-改-写**

`mm[off+3] = 0xAA` 之后,PL 锁到的是 `0xAA223344`(其余三字节来自器件**现值**)——
说明硬件层做了 RMW。**这本身不是错**,但它意味着:

- 你写 1 个字节,对面会看到 **1 笔整字写**,值和"旧值+新字节"有关;
- 若目标寄存器**忽略 `WSTRB`**(本项目的从机就是这样),那个拼接后的整字会被照单全收。

## 失效条件

- **对岸没有可观测的事件计数** ⇒ 判据 0 无法执行,只能挂 ILA/逻辑分析仪。
- **接口层本身有合法的合并/缓冲**(总线写合并、TCP Nagle、DB 事务批处理)⇒
  两次调用对一笔事务是**正常**的,此时计数不同**不构成缺陷**。
- **没有 RW 的证人寄存器**、且目标寄存器带副作用(写它会动硬件)⇒ 判据 2 不能用,
  只能改用"读回已生效值"来间接判断,而那样**分不清"第一笔生效"与"只有一笔"**。
- `struct.pack_into` 的具体行为**与 CPython 版本、对象类型有关**。本项目实测于
  **CPython 3.8(板载 PYNQ 2.7 venv)+ `mmap`**。换版本/换对象要**重测**,
  不要把结论当跨版本事实搬运。

## 已验证的效果

**设备与位流**:Zynq-7020(正领航者),位流 md5 `9613c2928a01f832b71aef7c45c4c0b9`。
**判据 1 的四路对照(每例前先把"忙"清干净并核对基线)**:

| 写 `0x1C = 0x61` | 结果 |
|---|---|
| 库封装整字写 | `0x61` / err `0x00` ✅ |
| 单字节存 `m[0x1C]` | `0x61` / err `0x00` ✅ |
| 切片赋值 `m[0x1C:0x20]` | `0x61` / err `0x00` ✅ |
| **`struct.pack_into`** | **`0x00`** / err **`0x03`** ❌ |

**"把 settle 设成 0(去掉忙互锁)"之后,四种写法全部得到 `0x61`** ——
⇒ 证明第 4 种**最后一笔是对的**,问题在**笔数**,不在"值送错"。

**判据 2 的证人读数**:`mm[0x4F] = 0xAA` → 证人读回 **`0xAA223344`**
(排除 `0xAA000000`、`0xAAAAAAAA`、`0x11223344` 三种模型)。

**判据 3 的收口(6 组,遍历基线与载荷)**:

| 寄存器原值 | 写入值 | 读回 |
|---|---|---|
| `0x10` / `0x61` / `0x7F` | `0x00000061` | **`0x00`** |
| `0x10` / `0x61` | `0x0000007F` | **`0x00`** |
| `0x7F` | `0x00000000` | **`0x00`** |

**与寄存器原值无关、与写入值无关** ⇒ 第一笔是**常数 `0x00000000`**(不是 RMW)。

**修后回归(两个后端各一遍,`tools/relay_rw.py --diagnose`)**:
★0 触发条件 2/2 ✅ · A 功能往返 11/11 ✅ · B 回归护栏 3/3 ✅ ·
C 非法组合被拒 6/6 ✅ · D1 Python 护栏 5/5 ✅ · D2 RTL 拒收 6/6 ✅ ·
E 稳定延时实测 40.2 ms / 100.4 ms(标称 40 / 100)—— **结果:全部通过(两后端一致)**。

**同一进程内的"修前/修后"对照**(最干净的归因证据):同一个类、同一次上电,
**只把 `write` 换成 `struct.pack_into`**,7/7 通过立刻翻转成 3/3 失败。

## 来源

从以下**失败链**中总结(全部为实测,非推测):

1. **2026-10-06 起**:观察到"写 `0x1C` 之后继电器停在 `0x00`"。
   当时的表述是「**一次** AXI 写 → PL 收到 **2** 个 `cfg_relay_set` 脉冲」。
   → 病根就埋在这一句里:**"一次"没量过。**
2. **排查方向被两处自我否证带偏**:
   - 源 RTL 与综合后网表逐拍推演都得出"一笔一个脉冲" ⇒ 于是归因给
     "PS 写通路"(`M_AXI_GP0` → SmartConnect → `S_AXI`),并计划**挂 ILA**(要重建位流);
   - 又断言"两条后端映射属性不同,不能互相代表" —— 实测**两条都是 `/dev/mem` + `O_SYNC`**,
     差别根本不在映射属性。**这条错判直接把方向引向了 ILA。**
3. **转折**:发现两份历史记录互相矛盾(同一份位流,一份说"全部通过"、一份说"全错")。
   ⇒ 正确动作不是挑一个信,而是**列出两份记录的差异项**,再做对照实验。
4. **走通**:性质隔离(每次只改一个性质)→ 公平四路对照(补齐"忙"窗口)→
   证人寄存器 → 遍历基线与载荷,四步把根因钉死。
5. **事后看得更清楚的一点**:`0x00` 恰好在继电器白名单里,所以第一笔被**受理**并锁住
   40 ms 忙 —— 若它不合法,第一笔会被拒、后续照常受理,**这个缺陷根本不会存在**。
   ⇒ "症状只在某一个寄存器上出现"有时是**白名单与互锁的巧合**,不是那个寄存器特殊。
