# silent-capacity-gates

> **改一个容量时,真正要改的不是那个容量的定义 —— 是它沿路经过的每一道
> `掩码 / 上限 / 截断`。这些关卡不报错,只会把数据悄悄换成另一份。**

## 适用范围

- 任何"**把一个缓冲 / 表 / 计数器改大或改小**"的改动,只要它跨了**两个以上的抽象层**
  (RTL ↔ 驱动 ↔ 中间件 ↔ 界面,或 库 ↔ 服务 ↔ 调用方)。
- 典型对象:`BUF_DEPTH` / `TABLE_SIZE` / `MAX_SAMPLES` / `QUEUE_LEN` / 分页大小 /
  协议字段宽度。
- 特别命中:**同一个数字在多个文件里各写一遍**的工程(这是本技能成立的前提)。
- 不限于 FPGA:任何"资源上限"沿调用链被复制的系统都适用。

---

## 使用方法

### 一、先列出这个容量沿路经过的所有关卡

改之前,**不要从"要改哪个文件"入手,从"谁读这个容量"入手**。
对本项目的一次真实改动(采集缓冲 `4096 → 8192`),关卡有 **三道**,分布在**三层**:

| # | 层 | 关卡 | 旧值 | 失效形状 |
|---|---|---|---|---|
| 1 | RTL | `cv_axi_lite_slave.v` 写掩码 | `32'h0000_0FFF` | 写索引 ≥ 4096 被**截成 `idx − 4096`** ⇒ 读到的是**另一个点的数据**,值域合法、不报错 |
| 2 | C | `adc_sample.c` `ADC_DEMOD_MAX_L` | `256u` | 建表函数**直接失败**(这条**会**报错:「窗长 6500 点,超出参考表上限 256」) |
| 3 | 界面 | `ui_demo.c` `UI_WAVE_MAX_SAMPLES` | `480` | 8192 点喂进图里**静默截断到前 480 点** ⇒ 屏上"波形是平的" |

### 二、按"失效形状"给关卡分类,处置方式完全不同

**① 静默型(最危险)** —— 第 1、3 道。不报错,数据变样。
- **只能靠枚举发现**,不能靠"跑一遍看报什么错"。
- 判据要选**能区分"改了"和"没改"的观测量**:
  第 1 道用的判据是 **"写 `0x1FFF` 能不能原值读回"** ——
  旧掩码下回读会变成 `0x0FFF`,**一个读数就分开两种假说**。

**② 报错型(相对友好)** —— 第 2 道。`build_table()` 会带着具体数字失败
(「窗长 6500 点,超出参考表上限 256」)。
- 留着它,**不要**为了"跑通"先去把它调大 —— 它挡住的是真问题。
- 注意:**报错型关卡是唯一的免费路标**。改容量后如果一路无错,
  往往说明静默型关卡才是真凶。

**③ 上限型 ≠ 容量型(最容易改错的一类)** —— 第 3 道。
`UI_WAVE_MAX_SAMPLES = 480` 与"波形图只有 480 像素宽"**绑死**。
⇒ **把上限调大解决不了任何问题** —— 8192 个点在一张 480 像素宽的图上**本来就画不下**。

> 🔴 **正解是"先算要显示多少,再抽稀",而不是"改大上限"。**
> 本项目改成两步:① 画 3 个激励周期(上限整窗);② 按 `ceil(显示点数 / 480)` 抽稀。
> **怎么证明它是数据驱动的**:三档激励的"显示前 N 点"实测是 **6500 / 1950 / 195** ——
> **各不相同**。写死任何一个常量,都会让另外两行对不上。

### 三、改完之后,主动反查"这个数字还在哪里被写死"

同一个数字在工程里通常**多处重复**。改完实现后**必须主动 grep 旧数值**,
否则会留下**语义已经变了、值还停在旧世界**的常量。本次抓到两处:

| 位置 | 症状 |
|---|---|
| `cv_regs.py::DDS_HZ_CHOICES` | 还留着**最初那套五档表**,与界面上的三档**完全不是一回事** ⇒ Python 侧**能下一个不存在的档** |
| `tools/adc_probe.py` 位流身份判据 | 写死旧位流的判据值 ⇒ 会在新位流上**印出"疑似旧位流"的假结论** |

📌 这两条的共同特征:**它们不参与编译,所以编译器不会提醒你。**

### 四、上板/运行时验收:判据必须能"二值分开"

容量类改动**不能靠"看起来正常"验收**。本次用的三条判据,每条都是**二值的**:

| 判据 | 二值观测量 |
|---|---|
| 掩码真的是 13 位 | 写 `0x1FFF` → 回读 **`0x1FFF` vs `0x0FFF`** |
| 缓冲真的是 8192 深 | `GO→done` 时延 = `DIV × BUF_DEPTH / f`;**"落在哪个假说上"**,不是"等于理论值" |
| 端到端真的用了新窗 | 解调日志的窗长 **6500 / 7800 / 8190**,**三档各不相同** |

⚠️ **第二、三条的写法值得抄**:
- 时延法**不要求"等于理论值"** —— 观测有轮询开销,实测普遍偏大;
  **判据是"实测落在 8192 假说还是 4096 假说上"**,两个假说差 2~8 ms,
  **远大于** 2 ms 的探针分辨率 ⇒ 结论稳健。
- 窗长法**不要求"数字对"** —— 要求**三档互不相同**。
  如果 `L` 被写死成常量,三档会**给出同一个数**。**"各不相同"比"等于设计值"更难伪造。**

## 失效条件

1. **容量没有跨层**:如果这个数字只在一个文件里出现,本技能不适用,直接改即可。
2. **关卡是"软"的**:若上层用动态分配 / 迭代器而不是固定上限,就没有可枚举的关卡,
   但仍然要查**协议字段宽度**(那是最常见的静默掩码)。
3. **"上限型"关卡被误当"容量型"处理时,改大了会引入新缺陷** ——
   第 3 道若不改成抽稀而只是调大,屏上不会报错,只会**变慢且画得更糊**。
4. **只改实现、不反查引用**(第三节)会让本技能只做了一半 ——
   编译期不参与的那些常量,是事后才咬人的那一批。
5. **本技能不提供"容量到底该取多少"的判断**。那是数值问题
   (本项目是 `L = ⌊n/q⌋·q` 的整窗覆盖要求),与本技能正交。

## 已验证的效果

**项目**:MOSFET C-V 在线监测平台(Zynq-7020),采集缓冲 `4096 → 8192`。
**范围**:RTL(`adc_capture.v` / `cv_axi_lite_slave.v`)+ C(`adc_sample.c`)+ 界面(`ui_demo.c` / `pynq_protocol.c`)。

| 验证项 | 手段 | 结果 |
|---|---|---|
| 三道关卡全部找到并改到位 | 静态核对 + 板上探针 | ✅ 掩码回读 `0x1FFF`;建表不再失败;**抽稀日志三档各异** |
| 掩码(静默型) | `wr 0x94 0x1FFF` → 回读 | ✅ `0x00001FFF` |
| 缓冲深度 | `GO→done` 时延,DIV = 65 / 130 / 255 三档 | ✅ **4096 假说被排除**(分别差 2 / 4 / 8 ms,探针分辨率 2 ms) |
| 端到端窗长 | 触摸逐档点测(三档) | ✅ `6500/1`、`7800/12`、`8190/126` —— **六个数逐位一致,且三档互不相同** |
| 采集可靠性 | 同一次会话统计 | ✅ **成功 = 6,失败 = 0** |
| 代价 | Vivado 2025.2 实现后报告 | BRAM **2.5 → 4 tile(2.86%)**;WNS **+1.023 ns** / WHS **+0.067 ns** / 失败端点 **0 / 4976** |

**证据**:
`report/measurements/20261008_65msps_window_board_acceptance.md`(完整记录)、
`report/measurements/artifacts/20261008_adc_window_probe.out`(探针原始输出,md5 `9c24a3b9…`)、
`report/measurements/artifacts/20261008_cui_4slot_window_taps.log`(三档窗长日志,md5 `0164ff13…`)。

⚠️ **如实标注的两处边界**:
- 交互记录里明确写了哪一层是**用户手点**测的(C 侧解调)、哪一层是**模型探针**测的(RTL)——
  因为 `0x68/0x6C/0x70` 在 fabric 里是只读的,**触摸事件 PS 侧注入不了**。
- `report/llm-log/LLM-055.md` 的纠错轨迹第 1 条,记的是本技能的**反面**:
  数字域全算对了、模拟域根本出不来(10 MHz 档)。
